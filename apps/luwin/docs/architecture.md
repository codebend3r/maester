# Architecture

## Components

```
                ┌──────────────────────────────────────────────┐
 chat app ────▶ │ chat/      chat service, identity, console    │
                │    │                                          │
                │    ▼                                          │
                │ agent/     Messages API loop ── tools/ ───────┼──▶ clients/ ──▶ Seerr, Sonarr, Radarr,
                │    │        registry, tiers, guardrails       │                SABnzbd, Tautulli, Plex, Wizarr
                │    ▼                                          │
                │ store/     SQLite: users, conversations,      │
                │            audit_log, reports, pending        │
                │                                               │
 Seerr/Tautulli │ web/       FastAPI: /api, webhooks, /health   │
 webhooks ────▶ │ jobs/      digests, sweeps, reminders         │
                └──────────────────────────────────────────────┘
```

One process, one container, one SQLite file on `/data`. The FastAPI app and the scheduled jobs share an asyncio loop. luwin's chat app, standalone or a helper window inside raven and rookery, comes next and talks to `chat/` through `/api`; until then only `/api/me` and the admin's tier route are served. Sign-in is rookery's (below).

## Instance registry

Two NAS hosts each run their own Sonarr, Radarr, SABnzbd and Tautulli (see `wizteros/docs/arr-stack.md`). Seerr, Plex and Wizarr are single. luwin never talks to "Sonarr"; it talks to `sonarr[meleys]` or `sonarr[vermithor]`.

- Instances are declared in env as `SONARR_MELEYS_URL`, `SONARR_MELEYS_API_KEY`, and so on.
- Every tool that touches an arr instance takes `host` and logs it in the audit row.
- A title's owning host is resolved per copy (standard or 4K) through Seerr, the one ownership rule described under Tools. When it can't be settled, the tool refuses rather than guessing.

## Permission tiers

| Tier      | Who                         | Can                                                                                     |
| --------- | --------------------------- | --------------------------------------------------------------------------------------- |
| unlinked  | Signed in, not on Seerr     | Get help and setup guides; told whom to ask for an invite                               |
| friend    | A Plex account Seerr knows  | Search, request 1080p, check availability and status, report problems, see own stats    |
| trusted   | Friends the admin trusts    | Everything above, request 4K (goes to approval), request invites for others            |
| admin     | The server owner            | Everything, approve, kill switch, tier overrides, audit log, download history           |

Tiers are resolved on every request (`chat/identity.py`): a per-user override in SQLite wins; then the account that owns the Plex server is the admin; then a user whose Plex account matches a Seerr user is a friend; anyone else is unlinked. Trusted comes only from the override. The tool list sent to the model is filtered by tier, and the server rejects out-of-tier calls independently of the model.

## Sign-in

luwin runs no sign-in. rookery, the suite's sign-in app, signs people in with Plex and sets the `maester_session` cookie for every app in the suite; luwin trusts it (the design is `docs/superpowers/specs/2026-10-09-shared-sign-in-design.md` at the repo root).

- **Whose a session is.** `web/auth.py`'s `SessionVerifier` reads the cookie and asks rookery at `ROOKERY_URL` (`clients/rookery.py`: `POST /internal/session` with the token in the body, `ROOKERY_SERVICE_TOKEN` as the bearer). Each answer is cached for 30 seconds by the token's hash, so a page's burst of requests costs one lookup and a short rookery outage goes unnoticed; a session past its `expires_at` is signed out at once, cached or not.
- **Who they are here.** `IdentityService.refresh` upserts the user under rookery's user id with the Plex id, username, email and avatar from the session, and checks their Seerr match when due: daily once matched, so someone Seerr drops loses access, and at most once a minute while unmatched, so someone invited a minute ago gets in on their next message. Only verified Plex facts match: the account's email against a Seerr user's email, and its Plex username against a Seerr user's Plex username, never a display name a local Seerr user chose. The Tautulli user id is found beside it.
- **The admin.** The owner is `PLEX_TOKEN`'s account on plex.tv (`/api/v2/user`), asked once before the server starts and again at most once a minute while plex.tv couldn't say.
- **Refusals**, as JSON from `Auth` (the seam every route depends on): 401 `{reason: "signed_out", sign_in}` with rookery's login page when there's no live session; 503 `{reason: "sign_in_unavailable"}` when rookery can't be asked and nothing is cached, so the page doesn't loop through sign-in; 403 `{reason: "unlinked", admin}` on the chat and inbox routes, naming the owner to ask for an invite; 403 `{reason: "not_admin"}` on admin routes. Writes take `application/json` only (415 otherwise), and luwin sends no CORS headers, so another site on the same parent domain can't write as a friend. `/api/*` answers `Cache-Control: no-store`.
- **Routes.** `GET /api/me` (who is signed in, and their tier) and `POST /api/admin/users/{user_id}/tier` (`{tier: friend | trusted | admin | null}`, the admin's alone, audited as `/tier`). luwin has no sign-out: its page links to rookery's.

If the apps ever live on unrelated domains, a verifier speaking signed tokens or OIDC replaces `SessionVerifier`, and nothing behind `Auth` changes.

`english_dub` on either request tool adds the `DUB_TAG` tag to the Seerr request (Seerr passes request tags to Sonarr or Radarr, where a release profile can prefer dual-audio releases) and picks the `DUB_PROFILE` quality profile when the server has one. English audio is read from Sonarr's analysis of each episode file (`mediaInfo.audioLanguages`), with the language rule of the `anime-missing-dub` audit (`luwin/dub.py`).

A title's owning host is resolved per copy (`luwin/library.py`), as a `MovieOwner` (Radarr) or `ShowOwner` (Sonarr) that speaks its arr's API for the copy's files, deletes and searches. Seerr records, for the standard and the 4K copy, which of its Radarr/Sonarr servers took it and the title's id there (`serviceId`/`externalServiceId` and their `4k` twins). Each Seerr server (`/api/v1/settings/radarr` and `/sonarr`) is matched to the registry host whose URL has the same host, port and base path, so a title with a 1080p copy on one host and a 4K copy on the other resolves correctly for each. A title Seerr never sent anywhere is looked up by TMDB or TVDB id on every instance that is not one of Seerr's 4K servers. A Seerr server matching no configured instance, two instances holding the title, or an instance that can't answer is `OwnerUnknown`: refused, never guessed.

## Destructive actions

Deleting a file, blocklisting a release, issuing an invite, changing a share: all of these are `destructive=True` tools.

1. The tool does not act. It returns a pending action with a human-readable summary.
2. The chat layer renders Confirm/Cancel buttons that only the asking user can press, expiring after 5 minutes.
3. On confirm, the action runs, is audited, and the admin is notified.
4. Some actions (4K requests, invites) go to the admin approval queue instead of the user's own confirmation; a replacement over the daily cap goes there after the friend confirms it.
5. A global kill switch (`KillSwitch`, checked by the runner) disables every destructive tool immediately, including a button-only one an admin's Approve would run. The admin flips it with `/kill`, and it's kept in the store (`flags`), so a restart can't turn it back off.
6. Destructive runs (only button presses make them) go one at a time in the runner, the kill switch checked as each one's turn comes and each audited before the next starts, so a cap counted from the audit log can't be raced.

Every tool refuses one way: `Result.refusal(reason)` (a `Result` with `is_error=True`) reaches the model as an error and is audited as not ok, so a daily cap never counts it; bad arguments are refused this way at the tool boundary too, and a caller with no Seerr link (`NotLinked`, raised by `ctx.linked_user()`) is turned into the same refusal by the runner. A refusal is for an action that can't be taken (nothing left to request, a quota, the wrong host, no evidence); a lookup that finds nothing (no search results, no open requests, no collection) answers with that. Such a failure is final unless the tool marks it `retryable` (a service that didn't answer); a raised exception always is retryable. A result can't both ask the admin and fail.

The model never sees a confirmation as something it can perform; the button press is out of band.

## Notices and approvals

Anything sent outside the current reply is a notice (`luwin/notify.py`), one of four kinds: `AdminPost(text)`, `ApprovalPost(text, pending_id)` (a note for the admin with Approve/Deny), `Announcement(text)` (for every friend), or `DirectMessage(to, text)`. Replies, decisions, webhooks and scheduled jobs all produce notices and hand them to the app's `Notifier`. Until luwin's chat app delivers them, `LogNotifier` writes each to the log and counts it as delivered. Delivery is best effort per notice: `deliver()` never raises and returns the notices it could not send. A reply is sent first, then its notices.

A decision names its pending action by id, so one made after a restart still lands. A pending action's own expiry decides when a decision is too late.

A button press always runs a tool call through the runner, with the same checks and audit as the model's calls. The two kinds of pending action differ only in who presses and what runs:

- **Confirm**: the requester presses Confirm, and the destructive call they asked for runs as them (Cancel runs nothing). The outcome goes into their conversation, so their next turn sees it. The runner adds a "confirmed" admin post unless the tool posted its own (an `AdminPost`, or an `ApprovalPost` when the confirmed call went to the admin instead, which the requester is told plainly).
- **Approve**: an admin presses Approve or Deny, and a button-only admin tool runs as that admin with `approved` set by the press. Button-only tools (`@tool(..., tier=Tier.ADMIN, button_only=True)`) are never shown to the model and never run from a model call. `decide_request`, `decide_4k_over_storage`, `decide_replacement`, `decide_invite` and `decide_access` are the five today.

A tool asks the admin by returning `Result(content, notices=(), approval=None)`:

- `notices` go out as they are (an `AdminPost`, a `DirectMessage`).
- `Approval(notice, summary, decide, args, subject)` names the decide tool and its arguments. The runner checks `args` against that tool's schema, stores the pending action, posts `notice` with Approve/Deny buttons, and tells the model the action waits on the admin. If the approval cannot be raised, the admin still gets `notice` as a plain post, and the call is an error.
- With a `subject` (`seerr-request:42`), at most one approval about it is open at a time (a unique index over open actions): whoever raises it second, a tool or a webhook, gets the open one back and posts nothing. A failed press can't reopen over a newer approval of the same subject.
- The call that raised the approval is audited with the approval's id, so daily caps never count a call that only asked. The decision is audited under the decide tool's name.
- A press whose run fails in the tool itself (Seerr down) is reopened, so the admin can press again; decide tools must be safe to run twice. A press whose tool no longer exists is closed.
- If a turn fails after a tool acted (a model error, say), the agent raises `TurnFailed` with the partial reply, and the error reply still carries its confirmations and notices.

A DM about a title carries it as `DirectMessage.about` (a `Titled` copy), so luwin's chat app can offer to report a problem with that copy straight from the message.

Tools act as the friend through `ToolContext.linked_user()`: the caller's link, whose `seerr_user_id` goes out as Seerr's `X-API-User` on a request and as an issue's `userId`; `ctx.link_of(user_id)` gives anyone else's, for a tool acting on someone's behalf. Callers without one are refused with `NotLinked`. "Linked" is one rule in the store (the user's Plex account matched a Seerr user), behind `Store.active_link()` and `Store.active_link_by_seerr_id()`, which tiers, tools and the ready DM all use. A Plex account is one rookery user, and a Seerr user matches one Plex account, so a request and its ready DM belong to one person; should two users ever match the same Seerr user, the one seen last gets its notices. A `ToolContext` always carries the real store and settings; nothing mints its own.

## Prompt injection

Friends' messages and every tool result (titles, overviews, file names, Seerr issue text) are untrusted. The system prompt states that tool results are data. The registry has no shell, HTTP passthrough or filesystem tools, so the worst an injected instruction can do is call a scoped tool the user already had access to, and destructive ones still need the button. The eval harness keeps an injection case.

## Playback reports and the replace flow

```
report ──▶ identify item (recent_sessions: Tautulli plays on every host) ──▶ friend confirms the copy
       ──▶ report_problem(item, kind)
              wont_play: player check against CLIENT_LIMITS
              │ player limit found ──▶ the fix, Seerr issue, stop
              ▼
              file health check (ffprobe + short decode, read-only mount)
              subtitles / audio: track listing ──▶ for_admin: Seerr issue, admin asked, stop
              wrong-file kinds: the friend's word
       ──▶ decision from stored evidence for that file
              │ no failed check and one reporter ──▶ recorded, Seerr issue, stop
              ▼ failed check, or 2+ reporters: replaceable, Seerr issue
       ──▶ replace_media(report, host)   [destructive: Confirm; re-checks evidence; capped; audited]
              │ over REPLACE_DAILY_CAP ──▶ admin approval ──▶ decide_replacement
              ▼
              mark grab failed (blocklist) ──▶ delete file ──▶ search, on the owning host
```

A report is one model (`luwin/playback/`) about a `Copy` (`luwin/media.py`, a leaf module every layer shares: a movie, a show or one episode, in its 1080p or 4K copy), whose file its owning arr locates (`MovieOwner.locate`, `ShowOwner.locate`), and a kind whose policy (`reports.POLICIES`) names its diagnosis strategy and whether a new copy fixes it. Kinds: `wont_play`, `wrong_title`, `wrong_episode`, `cam`, `hardcoded_subs`, `subtitles`, `audio`, `other`. Each strategy returns its own result (`diagnosis.py`: `PlayerLimit`, `FileChecked`, `TrackList`, `TheirWord`), which carries its summary, its data for the model and its lines for the Seerr issue.

- **Which play.** Plex runs on every NAS, and each host's Tautulli watches its own host's server, so a rating key names an item on one server only. A play is identified through the Tautulli that saw it: a live session carries its server's guids, a finished play's item is asked of that Tautulli (`get_metadata`), and the title's TMDB id finds it in Seerr; luwin's own Plex server isn't asked. Seerr's rating keys (which Plex item is the 1080p copy, which the 4K) belong to the server luwin reads (`PLEX_URL`), so they're compared only for plays on the hosts whose Tautulli watches it (`library_hosts`: `get_server_identity`'s machine identifier matches Plex's own). Elsewhere a play is matched by title and episode, and which copy it was is asked. Plays are kept one per item on each host.
- **Player first.** `client_limits.CLIENT_LIMITS` is a table of known player limits, each a match on a play's facts (`Playback`: client, codecs, and the server's decision per stream, from a live session or a finished play's history row and `get_stream_data`) plus its cause and one concrete fix: Dolby Vision profile 7 off a Shield, HEVC the player can't play as it is (its codec, HDR or 4K; not counted for a stream relayed, or converted below the file's bitrate away from home, which may be the connection), TrueHD/DTS passed through, PGS subtitles burned in. A rule `explains` another its effect would trip (burning subtitles in forces the video transcode), so the friend hears the real cause once. The play (Tautulli) and the file (ffprobe) are read at once, and the file's Dolby Vision profile fills in a finished play, whose history doesn't keep it. Tautulli gives no transcode reasons, so the decisions per stream stand in. Only when no rule matches is the file checked. A player fix must not shield a broken file for good, so a friend who already got one for this file and reports it again has the file checked instead (the policy's `after_advice` strategy). The lag advice (Performance diagnostics) reuses `Playback`, `playback_of` and two of the table's rules.
- **File health.** `health.check_health` decodes around the moment a friend named ("freezes at 1:12:30"), or the start, middle and end, and returns `ok`, `truncated`, `corrupt` or `unreadable` with the evidence. Only the file can fail the check: `truncated` needs a movie under 70% of its runtime or a stretch inside the file's claimed length that decodes nothing, and `corrupt` needs a known sign of a damaged stream (`CORRUPTION`). A moment named past the file's end is only noted. Known ffmpeg noise is ignored, and anything else ffmpeg prints (a read error, a missing decoder, an unknown line) makes the check `unreadable`, which never justifies a replacement.
- **Evidence, not the model's word.** A report is stored with the file's host, id, release group and health verdict, and its `decision` (`advised`, `replaceable`, `recorded`, `for_admin`), written once from the evidence each report of that file testifies to (`Testimony`, `Evidence`). A replaceable report may be replaced only when a stored check of that very file failed, or two or more people reported it; a report the player explains doesn't testify, nor does one whose Seerr issue was resolved or whose replacement the admin declined. `replace_media` checks this again when the friend presses Confirm, and acts only on the friend's own report, only while the file is still the one reported.
- **Status.** A report's replacement has a `status` (`open`, `escalated`, `replaced`, `declined`) that moves only by `ESCALATE`, `DECLINE`, `REOPEN` and `REPLACE` (`reports.py`), each a compare-and-set in the store (`move_report`), so no stale read or second press can undo a newer move. `MAY_REPLACE` says a friend may replace from `open` and an admin's approval from `escalated`. The admin's Deny declines that report only: a later report of the same file stands on its own evidence. An escalation whose approval lapsed, or whose approved run stopped for good, moves back to `open`.
- **Seerr issue.** Every report opens a Seerr issue as the friend against Seerr's media id, naming the season and episode, with the diagnosis, the decision and, for track problems, the file's tracks. The friend is named as `userId` in the body, not with `X-API-User` as requests are: Seerr's issue route files as `userId` for a caller with MANAGE_ISSUES (luwin's key), so the issue is the friend's whatever their own issue permissions. A replacement adds a comment with every step. Resolving the issue in Seerr resolves the report.
- **Replacement.** Steps run in order and stop at the first that doesn't go through: the grab behind the file (found through the arr's import history, `fileId`) is marked failed, which blocklists the release (a file with no grab behind it stops here and is left to the admin; a release already marked failed isn't marked twice); the movie or episode file is deleted (`MovieOwner` or `ShowOwner` speaks its arr's API); the movie, or every episode the file held, is searched. The arrs take no reason for a blocklist entry, so the reason stays on the report and in the admin's notice. An arr that didn't answer before anything was deleted leaves the press open to try again (`Result.retryable`). The friend is told which copy and every step; the admin gets one notice with path, size, reason and release group. Once the owning arr holds a new file for the copy, everyone who reported the old one gets one DM about it (`jobs/landed.py`, following replacements for two weeks), so a report about it reaches the new file.
- **Cap.** At most `REPLACE_DAILY_CAP` friend-confirmed replacements in any 24 hours, counted from the audit log (refusals and calls that only asked for approval don't count). Past it, the report escalates and goes to the admin; what they approve is their call and isn't counted. The runner runs destructive tools one at a time, so two confirmations at once can't both slip under the cap.

`find_gaps` compares Sonarr's episodes with the files on the owning host: aired, monitored episodes without a file are searched and listed; a season missing every aired episode goes to the admin instead of being searched blindly.

### File access

There is no filesystem tool. The health check and `list_tracks` name a title and copy; the path always comes from the owning arr's file record, and `MediaPaths` maps it onto the container's read-only mounts (`MEDIA_PATH_MAP`, for arrs that see the shares under other names) and refuses anything that resolves outside `MEDIA_ROOTS`, symlinks and `..` included. `MEDIA_ROOTS` itself refuses `/` and relative paths, and a decode checks its path against the roots again. ffprobe and ffmpeg run without a shell as async subprocesses, each capped by `PROBE_TIMEOUT_SECONDS` and two at a time, with the path passed as `file:<path>`; a process whose asker was cancelled is killed.

## Performance diagnostics

"It's laggy" is answered from live data, not guesses (`luwin/perf/`).

- **Server load.** `server_status` reads every Plex host's Tautulli at once, with the fleet monitor, and a host that can't answer is named rather than hiding the rest (`perf/load.py`). A host is busy when a conversion (a transcode) runs slower than playback without being throttled (a throttled transcoder is ahead and resting), which is the one direct sign a server can't keep up whatever its hardware, or when its CPU reaches `BUSY_CPU_PERCENT` (85) or its memory `BUSY_MEMORY_PERCENT` (90). The reply says whether load is a plausible cause, in three states rather than two: yes, unlikely (every host answered and none is busy), or unknown (a host went unseen). It says "fine" only of CPU and memory it actually read.
- **Fleet monitor.** CPU and memory per NAS come from wizteros' fleet monitor (`clients/fleet.py`), read from `/fleet/cpu` and `/fleet/memory` (and `/fleet` for the weekly NAS report) only, with a static bearer token (`FLEET_MONITOR_TOKEN`), and only when `FLEET_MONITOR_URL` and the token are set. The monitor has no guard for such a token yet (its routes want an admin's Supabase session, which also reads every member's play history), so it stays unset until wizteros adds one; without it, load rests on Tautulli alone and says CPU and memory are unknown. A host's vitals are the last reading of the past five minutes, so a host the collector hasn't reached lately has none rather than an old number.
- **Speed test.** `speed_test(host)` runs Ookla's speedtest CLI inside luwin's own container (`clients/speedtest.py`): the Dockerfile pins version 1.2.0 by checksum, and it runs the way ffprobe does (`clients/process.py`: no shell, a fixed argv, a timeout, killed if its asker goes away). There is no generic command runner. It can only test from `SPEEDTEST_HOST`, the NAS the container runs on; the hosts share one internet connection, so that stands for all of them. The test shares the upload with the streams already going out, so the upload it finds is the headroom, put next to every host's remote streams (their bitrates, read while it runs) in plain words (`perf/uplink.py`). A test briefly fills the upload for everyone, so a result is reused for 10 minutes (`REUSE`) and a new test runs at most every 20 (`MIN_GAP`), failed or not; in between, the last result comes with its age and when the next can run.
- **Lag advice.** `session_report` reads the friend's live streams from the same per-host read as the load, so each stream comes with its host's other streams (`HostLoad.without`), the last speed test while it's within 10 minutes (never a new one), the title's versions, and away from home what its connection is known or taken to carry (`Stream.limit`: the tightest of a typical connection away from home, Plex's relay, and the servers' free upload plus what this stream already takes, since the test ran alongside it) (`perf/lag.py`). `Playback` is the one model of a stream's facts, now with LAN or internet, relay, the bitrate sent and the file's, and how fast its video is converted (set only when the video is; Tautulli gives a speed for any transcode). Each rule finds its cause in a stream or doesn't, says the cause and the fix in words only when it applies, and names a typed `Fix`: `subtitles_off`, `avoid_relay`, `original_quality`, `lower_quality`, `other_version`, `other_player`, `wait`.
  - Tautulli says whether a stream is converted and how fast, not why; its `quality_profile` is only its own label for the bitrate sent (`pmsconnect.py`), so luwin doesn't read it. At home the HEVC rule reads a conversion as the player's (its codec, HDR or 4K), which a home quality set below the file would misread; its fix names an H.264 version only when there is one, and otherwise another player. Away from home a video converted down (`Playback.squeezed`, as is anything relayed) may be the app's remote quality or the player, so the fix given is the one right either way, an H.264 version that plays without converting. Only an H.264 file, which every player decodes, converted down away from home and falling behind is put down to the remote quality (`original_quality`). Advice to lower the quality always names a Plex quality below what the stream gets now, since one above it would leave the stream as it is.
  - A stream at home and one away from home have a table each (`AT_HOME`, `AWAY`), picked once. A table's order is precedence: burned-in picture subtitles (whose conversion another version wouldn't avoid) first, then, away from home, the relay (at most 2 Mbps, for Plex Pass and Remote Watch Pass subscribers alike, per Plex's relay article); HEVC the player can't play as it is (at home); a conversion falling behind with an H.264 version to switch to; an H.264 file below its quality; a remux its connection doesn't carry; a nearly full upload; a conversion falling behind with nothing to switch to; and a busy server last, "busy with other streams" only when other streams are the load. The friend gets the first finding, in a line with what the stream is doing; every finding and the stats come only with `details=true`, which the model calls when asked.
- **Versions and connections.** A title's versions come from both copies' Plex items and are named as friends name them (`luwin/plex_versions.py`, shared with `check_availability`). They're read from the Plex server luwin reads (`PLEX_URL`) by Seerr's rating keys, so a stream is offered versions only when it was served from that server and its file is one of them. A version fits a connection when its average bitrate times `PEAK_ALLOWANCE` (1.5) is under the tightest known limit; away from home with nothing measured, a connection is taken to carry `REMOTE_COMFORT_KBPS` (20 Mbps). A remote quality to set is one of Plex's own steps, which cap a converted stream's bitrate. `pick_version` recommends against the tightest of the speed the friend gives, Plex's relay on their last play away from home, and the servers' free upload at the last speed test; with none, it assumes a typical connection away from home and says so. A stream already lagging away from home is held to that typical connection as well. Movies only.
- **Re-encode candidates.** When a friend's lag report finds their stream playing a version at `HEAVY_KBPS` (40 Mbps) or more whose Plex item holds no lighter version of its resolution (`perf/reencode.py`), that item's history is read in the Tautulli that played it. Watched away from home `WAN_WATCHES_TO_FLAG` (3) times in `REENCODE_WINDOW` (30 days), it's flagged: the admin gets an `AdminPost` with the file and bitrate, once per window per item (a claim, source `reencode`). Tautulli groups a play resumed soon after into one history row, so these are watches, not plays. `session_report` is the only trigger; `pick_version` only reads, and no job sweeps the whole library yet.
- **Service health.** Every client has one liveness call, `ping`, on the cheapest route that shows it is up: a client's `health_path` read by `HttpClient.ping`: Seerr's `/api/v1/status`, Wizarr's `/api/status`, each arr's `/api/v3/system/status`; Tautulli's `status` command; Plex naming itself (`machine_identifier`); and a one-slot SABnzbd queue, which refuses a wrong key in its answer rather than with an HTTP error. All but Seerr's and Plex's check the key too. The fakes share one `Downable` mixin. `service_health` pings them all at once, each under `PING_TIMEOUT` (5 s) so one hung service can't hold up or hide the rest, and keeps the answer for 60 s (`HEALTH_TTL`). An open maintenance window is named first, with the admin's reason.
- **Shared answers.** Answers worth sharing across calls (a speed test, a health check) are kept in the agent's `Memo`, handed to tools as `ToolContext.memo`. A typed key (`Key[T]`: `SPEED_TEST`, `HEALTH`) names each question and the type of its answer; a tool keeps an answer for as long as it chooses, and callers asking while one fetch runs share it. It lives in memory; a restart only costs one more lookup.

## Admin console

Everything the admin does from chat (`luwin/chat/admin.py`, `luwin/jobs/`, and the admin tools). The console's commands live in `AdminConsole`, which talks to no chat platform; the app that shows luwin offers each command, answers privately, and delivers its notices.

- **Commands.** `/kill on|off [reason]`, `/tier @member`, `/audit [n]` (the latest audit rows, named as the admin knows people), `/pending`, `/forecast` and `/maintenance start|end [message]`. Every one is admin-only and audited under its own name (`/kill`), refusals included.
- **Approval queue.** Every approval reaches the admin with Approve/Deny. Beyond replacements over the cap, every request Seerr leaves pending does: a friend's request tool raises it, and Seerr's `MEDIA_PENDING` webhook raises the same one (one per request, by subject) for a request made anywhere else (Seerr's page, a collection, someone not linked here), naming the requester as Seerr does. A decision made in Seerr itself (`MEDIA_APPROVED`, `MEDIA_DECLINED`) closes the approval here and tells the friend. `/pending` lists every open approval and shows each again privately with its buttons (a press there is answered privately too), and raises one for any request Seerr still holds pending without one (the webhook was missed), sent to the admin like the rest. The webhook checks Seerr again after raising one, and closes it instead of posting when the request was decided meanwhile (the admin's Approve on a held 4K request makes the request and approves it at once). A request deleted in Seerr closes its approval for good. The digest lists them daily.
- **Storage-aware 4K.** `luwin/storage.py` reads free space per volume: each arr's root folders mapped to the disk they sit on (the longest mount path), merged when two arrs or two hosts see one disk (same path and size, free space within 10 GB). Before a 4K request goes to Seerr, the volume Seerr's 4K server puts it on (its root folder, or the arr's only one) is checked: at `STORAGE_PAUSE_4K_PERCENT` or past it, or when it can't be read, nothing is sent, the friend is told why, and the admin's Approve (`decide_4k_over_storage`) requests it as the friend and approves it in Seerr.
- **Stalled-download sweeper.** Every `SWEEP_MINUTES` (`jobs/sweep.py`), each host's Radarr and Sonarr queue is read. A download is stuck when its arr flags it (warning or error) or when it stops moving while downloading; paused, queued, delayed or a client that can't be reached is waiting, not stuck, and a download the arr didn't grab for a title it knows (added to the client by hand) isn't the sweeper's to touch. `queue_watch` times each download across sweeps and restarts. Stuck past `STALLED_HOURS`: removed from the client with its release blocklisted, and its movie or episodes searched again on the same host; if the search then doesn't start, the admin is told to run it, since the download is out of the queue. A title that stalls again within 30 days of a re-search is posted to the admin once instead. A download one queue read misses keeps its row a day, so it isn't timed or surfaced again from scratch. The kill switch holds removals; a maintenance window pauses the sweep. Each action is audited (`sweep_stalled`) and kept in `stalls` for the digest.
- **Disk forecast.** At 03:00 each volume's free space is sampled into `space_samples` (keyed by path, size and the hosts that see it; a day an arr can't answer is skipped, since a shared volume would come back looking like another). The forecast fits a straight line through the last 30 days (least squares) and says when each volume reaches zero at that rate, once it has 7 days of samples. `/forecast` lists them; the digest carries any under 30 days.
- **Bad releases.** A report stores its file's release group: the arr's, or the `-GROUP` at the end of the file name (`luwin/releases.py`). A group with `BAD_RELEASE_REPORTS` distinct reported files in 30 days (a report the player explains doesn't count) gets a block suggestion in the digest, a custom format or a release profile, once per 30 days (claim source `bad_release`).
- **Download history.** `download_history` (admin) reads the owning host's arr history and queue for one copy, and SABnzbd's history and queue on that host for the same download ids: its failure message and the repair and unpack steps that went wrong. A named host must hold the copy; with none named the owner is found. The model gives the admin the cause and the next step.
- **Maintenance windows.** `/maintenance start` raises the `maintenance` flag and announces it to every friend. While it's up, tools marked `held_in_maintenance` (the request tools, `follow_show`, `find_gaps`, `replace_media`) don't run: the runner saves the call in `held_calls` (a destructive one once the friend confirms; the press is what's held), audits it with `held_id` so daily caps don't count it, and the model tells the friend it runs afterwards. `/maintenance end` lowers the flag and runs each held call as its caller, at the tier they have then (their tier is read again), with the runner's usual checks; a call is marked run before it runs, so two ends can't run it twice. It's remembered in their conversation like a confirmation, led by a plain message saying what it was, so a window longer than the idle reset still leaves it in view; each friend then gets a turn so the model tells them in a DM how it went. A call that failed in a way worth trying again (a service still starting, the kill switch still on) stays held, and `/maintenance end` runs what's left even after the flag is down.
- **Daily digest.** At `DIGEST_TIME` in `TZ` (`jobs/digest.py`), one admin post: switches left on, approvals waiting (and for how long), the last day's requests and where each stands, Seerr's open issues, the last day's replacements, per host the sweeper's actions, what an arr flags as stuck and SABnzbd's failures, every volume's free space with any forecast under 30 days, release groups to block, and anything that couldn't be read. A section with nothing to say is left out.
- **Weekly NAS report.** On `NAS_REPORT_DAY` at the digest's time (`jobs/nas.py`): each NAS from the fleet monitor's `/fleet` (heard from or not, `/volume1` usage, memory, load, the hottest chip, containers down or unhealthy, uptime over the last day) and the media volumes from the arrs, anything past a limit first. SMART isn't read (the monitor has no SMART probe and luwin no SSH), and the report says so.
- **Scheduled jobs.** `luwin/jobs/` runs each job `At` a time of day in `TZ` (daily, or one day a week) or `Every` so often, on the app's loop: the sweeper, the free-space sample, the digest, the NAS report, the check for replaced copies that landed, and the expiry reminders. A slot is claimed (source `job`) before it runs, so a restart never runs one twice, and a slot missed while down still runs on start within 6 hours. A job that fails is logged and runs at its next time.

## Onboarding and accounts

Access in this deployment is Wizarr's (invites, one user record per Plex server, an expiry per record) and plex.tv's (which libraries each friend is shared, per server); wizteros runs the paid tiers on top of both. luwin asks the admin before changing either, and changes only what was asked.

- **Invites.** A trusted friend asks with `request_invite` (who it's for, and a note); it waits in the approval queue, one per friend and person. The admin's Approve (`decide_invite`, destructive) creates a Wizarr invite from the servers `INVITE_SERVERS` names, scoped to the libraries an invite shares there (`luwin/access.py`: `INVITE_LIBRARIES` by name, or every enabled library that isn't 4K or private), with the link's expiry (`INVITE_EXPIRES_DAYS`, snapped up to one Wizarr honors) and the access it grants (`INVITE_ACCESS_DAYS`). Wizarr's API gives the link as a path on its own host, so it's built on `WIZARR_PUBLIC_URL`; it goes to the friend to forward, with both dates, and into the admin's reply in case the DM doesn't land. A create Wizarr didn't confirm isn't retried, since it may exist already: the admin checks Wizarr, and the friend hears it's in hand.
- **Setup help.** `luwin/guides/` holds a markdown guide per device (Apple TV, Roku, Fire TV, Android TV and Shield, phones, the web), each ending with what they share: quality at home and away, the relay (the server's setting, as the lag advice says), Direct Play, subtitles and sound. The model answers from `setup_guide`, not from memory, and `ChatService.setup_guide` hands anyone the guide, linked or not.
- **Access changes.** A friend asks for another library or for 4K with `request_access`, which checks the ask first. The admin's Approve (`decide_access`, destructive) adds the library, or every 4K library, to the friend's share on each server they're shared that holds it, through plex.tv as the owner (`luwin/clients/plextv.py`, `PLEX_TOKEN`): the share's library list is replaced with what it had plus what's added, as Plex's own apps and plexapi's `updateFriend` do, so their other libraries and their Wizarr expiry stay as they are. Wizarr has no call that changes a member's libraries, only a new invite, which would also reset their expiry. 4K also puts them on the trusted tier, which is what lets them request 4K (and ask for invites, which the admin's approval post says), as a stored tier override; one already trusted or above keeps theirs. A server they aren't shared at all takes an invite, and private libraries (`PRIVATE_LIBRARIES`) are never added. A friend is found on plex.tv by their Plex account's email, from sign-in, never by a username, which a Seerr user without a Plex account chooses. An approval that can't be carried out still tells the friend.
- **Expiry reminders.** Daily at the digest's time (`jobs/expiry.py`), Wizarr's users are matched to linked friends by their Plex account's email, from sign-in; a friend's access ends at the earliest of their records' expiries. A DM goes out on each of `EXPIRY_REMIND_DAYS` before (7 and 1 out of the box), once each per expiry, in `EXPIRY_REMINDER`'s words, pointing at `CONTRIBUTION_URL` when there is one. Access that renews monthly for 35 days is always within a week of its end before it renews, so such a deployment sets `4,1`.

## Storage

SQLite, migrations numbered under `luwin/store/migrations/` (one so far: luwin's store started fresh, and a database from before that is refused on open), and one store module per table (`luwin/store/`) joined into `Store`. Tables: `users`, `conversations`, `audit_log`, `reports`, `pending_actions`, `claims`, `flags`, `held_calls`, `queue_watch`, `stalls`, `space_samples`, and later `preferences`. Nothing in the file is a source of truth for media; Seerr and the arrs are.

`reports` holds every playback report: who, which copy (title, TMDB id, 4K or not, season and episode) and which file (host, arr file id, path, release group), the health verdict and diagnosis, the friend's description, its decision (written once) and status (moved by compare-and-set), its Seerr issue and when it was resolved. `claims` holds what's done once a window, per source and key: Seerr webhook deliveries acted on (source `seerr`), heavy remuxes flagged to the admin (source `reencode`, once a month per Plex item), scheduled job slots run (source `job`), release groups suggested for a block (source `bad_release`, once a month per group), replaced copies friends were told landed (source `landed`), and expiry reminders sent (source `expiry`, per friend, expiry and reminder). Each source prunes its own claims older than its window as it claims. `flags` holds the kill switch and a maintenance window while they're up; `held_calls` the calls a window held; `queue_watch` and `stalls` the sweeper's view of the queues and what it did; `space_samples` a day's free space per volume.

## Seerr webhook

`POST /webhooks/seerr` serves every Seerr notification type. The `Authorization` header must equal `SEERR_WEBHOOK_SECRET`; with no secret configured, every call is refused. The payload is parsed into a `SeerrNotification` and dispatched by type through `seerr_routes()` (`luwin/seerr_events.py`); a route's handler returns notices, which go out through the app's `Notifier`. Types without a route are acknowledged and ignored.

Deduplication is opt-in per route, for handlers whose repeat would reach a person twice. Such a route claims the event in `claims` (source `seerr`; the key is the type plus the request or issue it concerns) before its handler runs, so a repeat inside its window (15 minutes for the ready DM, sized for Seerr's rescans) is acknowledged without acting. A later repeat is news and gets through, and idempotent routes (a report-row update) take every delivery. The claim is released when the handler fails or one of its notices could not be delivered.

| Type              | Handler         | Effect                                                                   |
| ----------------- | --------------- | ------------------------------------------------------------------------ |
| `MEDIA_AVAILABLE` | `ready_to_watch`| DMs the linked requester: title, version (1080p or 4K), a Plex deep link; dedupes for 15 minutes. The DM carries the title, so luwin's chat app can offer to report a problem with it |
| `MEDIA_PENDING`   | `pending_request` | Raises the admin's approval of a request Seerr left pending, unless one is open (a tool raised it); idempotent by subject |
| `MEDIA_APPROVED`  | `decided_in_seerr` | Closes the request's open approval here and DMs the requester; idempotent, no dedupe |
| `MEDIA_DECLINED`  | `decided_in_seerr` | The same, declined |
| `ISSUE_RESOLVED`  | `issue_status`  | Marks the reports behind the issue resolved and DMs each reporter once; idempotent, no dedupe |
| `ISSUE_REOPENED`  | `issue_status`  | Clears the reports' resolved time; idempotent, no dedupe |

## Deployment

Docker Compose on Meleys, run from `apps/luwin/` in the repo copy at `/volume1/docker/maester`, next to `stripe-bridge`.
