# Claude context for raven

## Hard rules

- Do not commit, push, branch, merge, or open a PR unless told to.

## What this is

A self-hosted video library and web player: direct play, with an on-the-fly remux or transcode for what the browser cannot play. See README.md for how playback, scanning and thumbnails work.

## Structure

raven's projects live in the workspace described by the root `CLAUDE.md`, which covers Nx, the project table and how to run tasks: `@raven/server` in `apps/raven/server`, `@raven/web` in `apps/raven/web`, `@raven/core` in `libs/raven/core`, the shared player `@raven/ui` in `libs/raven/ui`, the libmpv addon `@raven/mpv` in `libs/raven/mpv`, and raven player, the macOS app, `@raven/desktop` in `apps/raven/desktop`. The server also depends on `@shared/server` (`libs/shared/server`), which it shares with rookery: it serves the built web app, compresses responses, opens SQLite and runs `MIGRATIONS`, reads the listen config, and compares the PIN and the unlock cookie in constant time.

`libs/raven/core` must stay platform-agnostic: no DOM, no Node APIs, not even `URLSearchParams` (use `toQueryString`). Its tsconfig has `lib: ["ES2023"]` and no `types` so a slip fails the typecheck.

The image builds from the repo root: `docker build -f apps/raven/Dockerfile .`. `Dockerfile.dockerignore` allowlists what it copies; a new path the image needs goes there too.

Supabase Auth preparation lives in `@raven/supabase` (`apps/raven/supabase`). Its runbook is `supabase/README.md`, and its raven-first design is `docs/superpowers/specs/2026-10-17-supabase-sign-in-design.md`. Membership is pending until the explicitly bootstrapped owner approves it; user metadata never grants ownership. With accounts `ready` the server enforces them: see "Accounts" below. No cloud deployment or owner bootstrap happens as part of a PR.

## Conventions

The TypeScript, code style and CSS rules are in the root `CLAUDE.md`. raven adds:

- The API contract is `libs/raven/core/src/contract.ts`. Each shape is written once, as its `is<Type>` guard built from the combinators in `schema.ts` (`object`, `oneOf`, `nullable`, `listOf`, `union`, `exactPartial`), and its type is read off the guard: `export type MediaItem = Infer<typeof isMediaItem>`. A new API type is a new guard there, never a hand-written type beside a hand-written guard. A union of literals is an `as const` object and a guard built from it, `export const isScanState = oneOf(Object.values(SCAN_STATES))`. Code compares against the object (`SCAN_STATES.idle`), and the guard's `.values` is the list for a menu or a loop. Request bodies get guards there too, so the server checks a body with the guard the client's call is typed by.
- What each type of library allows (its sorts, views and groupings, and whether it is matched) lives in `KIND_RULES` in `libs/raven/core/src/libraryKinds.ts`; `coherentSettings` applies it.
- Narrow with the guards in `@raven/core` wherever data crosses the network.
- The web app is also served from Netlify, whose CDN proxies `/api` to raven (README, "On Netlify"). A response that depends on the browser's cookies, the PIN's or the admin lock's, or on the account's, is never `public` in `cache-control`, or Netlify's cache hands it to everyone.
- The media plane routes are the ones marked `@MediaPlane()`: `stream`, `file`, `subtitles` and the ping. They answer CORS for `RAVEN_WEB_ORIGINS` and open for a `?t=` ticket: an account ticket under `ready`, the legacy HMAC ticket only when accounts are `off`. Thumbnails and JSON stay on the same origin as the page. A new route that streams bytes to the player gets the mark.
- raven is reachable from the internet, so every route that is not a GET says who it is for: `@AdminOnly()` or `@ForViewers()`. `@AdminOnly()` is the owner once accounts are `ready` and the admin lock on a server without accounts; a GET that only a managing screen reads is `@AdminOnly()` too. The server refuses to start with a write route marked neither, as it does with a route the PIN lock has not been told about. Never ask the admin lock directly: `Management.canManage({ request })` answers for both.
- Server constructors inject with explicit `@Inject(Token)`, so DI never depends on decorator metadata, which neither vitest nor `tsx` emits.
- Every raven project imports its own modules via `@/` with no extension; `tsconfig.json` uses `"moduleResolution": "bundler"` so TypeScript allows it. The server's `dev` runs through `tsx`, and its `build` is `tsc` then `tsc-alias`.
- Every search box is a `SearchField` (`components/SearchField`) held by `useSearch`, or `useAddressSearch` when it rides in the address as `?q=` (`lib/useSearch.ts`), so every one is debounced: it searches once typing pauses, or at once on Enter. Never a bare `<input type="search">`, and never a search that runs on each keystroke.
- The tokens are in `libs/raven/ui/src/styles/globals.scss`, and element defaults in `elements.scss` beside it. The web `/design` page reads the shared `globals.scss` through `@raven/ui/designTokens`, so a new token shows up there with no extra step.
- Every colour comes from a token a theme can redefine. `themes.scss` beside `globals.scss` gives each of the seven themes in `THEMES` (`libs/raven/core/src/themes.ts`) its values under `[data-theme='…']`; a new themable colour goes in `:root` and in every theme block (a test checks they match). What sits on a picture uses the fixed `--color-on-picture*` and `--color-picture-*` tokens, and anything on a `--color-leaf` fill is `--color-on-leaf`. The web app keeps the viewer's choice in `stores/theme.ts`.

The shared player has no web app imports. Hosts give it an `Engine` and their `PlayerServices`, which reach the player's parts through the `usePlayerServices` store (`libs/raven/ui/src/stores/playerServices.ts`), never a context: the component that renders `<Player>` calls `useHostPlayer(services)` and renders the player only once it answers true, so the player's first render reads that host's services, never the last host's. Call it in the component whose lifetime is the player's: a host that swaps one player for another hosts each in a component of its own, as the desktop's `NativePlaying` and `HtmlPlaying` do. The browser keeps its singleton, queries, invalidation and WatchPage services. Import built `@raven/ui` exports and `@raven/ui/styles.css`, never alias UI sources from another project. See `libs/raven/ui/README.md` for peer dependencies and test ownership.

## Accounts

- **The gate is default-deny.** With accounts `ready` the `AccountGuard` holds every route to an approved account unless its handler is marked `@OpenToAnyone()`; `@AdminOnly()` means the owner, and `GET /api/me` is the one `session` route. A new route is approved-only the moment it exists. One that must be open to anyone gets `@OpenToAnyone()` and a row in the inventory in `appEnforcement.test.ts` (`ROUTES` in `src/test/enforced.ts`), or CI fails: the inventory, the anonymous sweep and the owner sweep run every row.
- **The auth state is effective, not configured.** Read `AUTH_STATE`, never `config.auth`: it folds in the enforcement record (`accounts.enforcedAt`, written on the first `ready` start) and `RAVEN_ACCOUNTS=off` (`isAccountsOptedOut`, `hasEnforced`). A server that once enforced and lost its Supabase settings is `unavailable` (503), never `off`.
- **One caller per request.** `callerOf({ request })` is `legacy` (accounts `off`), a `session` (Bearer, or the cookie on `GET`/`HEAD`) or a `ticket` (an `account.` ticket on a media-plane route). The PIN lock, `Management`, the listings and the rechecks read it. Code that treats `legacy` as "the browser's rules" must branch on the auth state first and never fail open.
- **The PIN follows the account.** Only the owner unlocks; the `raven_unlock` cookie carries the account id; members never see locked libraries (404, not 423). A legacy HMAC ticket opens nothing under `ready`, the owner included.
- **Open responses are rechecked.** SSE and `file`/`stream` responses end through `AccessRechecks` every `DEFAULT_ACCESS_RECHECK_MS` (60 s, injected as `ACCESS_RECHECK_MS`); an `unavailable` recheck keeps an already-authorized stream until the last-known token expires, while removal and integrity failures end it at once. A client resumes a cut media response by range with a new ticket.
- **Membership lookups go through `MembershipLookups`** (shared in flight, 5 s). A change made through raven calls `forget`; never call `AuthBackend.current` directly from a request path.
- **Never log or store** a JWT, refresh token or ticket.
- **Viewing data is per account.**
  - `playback_progress`, `plays`, `favourites` and `item_favourites` carry `account_id`, the Supabase user UUID (`'local'` for rows from before accounts).
  - Every statement over them binds `@account`, taken only from `ViewingAccounts.keyOf({ request })` (`media/viewingAccounts.ts`), never from a body, query, header or claim; the only statements without it are the account migration, the adoption transaction and `ON DELETE CASCADE`.
  - The rebuilt tables are `WITHOUT ROWID` with their cascade indexes so the planner searches them by key. A new per-viewer table gets `account_id` in its primary key and a row in the isolation suite (`appAccountData.test.ts`), and its queries are added to the plan assertions.
  - The account migration is a normal `MIGRATIONS` entry with no down migration.
  - The approved owner's first request under `ready` runs `ViewingAdoption.adopt`: one transaction that merges every `'local'` row into the owner's (newer spot, earlier favourite time), then records `{ ownerId, adoptedAt }` under `SETTINGS_KEYS.viewing`. A failure rolls back, is retried at most once per request and after `ADOPTION_RETRY_MS`, and logs only the SQLite code and counts, never an id.
  - Under `off` the shared viewer is the recorded owner, else `'local'`; under `ready` or `unavailable` an unbound request stays on `'local'`.
  - Library view settings stay shared.

## Desktop

raven player (`@raven/desktop`) plays local files and server titles under raven's own controls, on macOS arm64, and keeps server titles on disk to play with no server. Its design is `docs/superpowers/specs/2026-10-12-raven-desktop-design.md`; the downloads' is `docs/superpowers/specs/2026-10-17-raven-desktop-downloads-design.md`.

- **The UI lives in `@raven/ui`.** The desktop renderer imports the same Player, chrome, primitives and tokens as the web; only the Home, Play, Server, Downloads and Settings screens and the Shell are its own. Two player engines sit behind the shared `Engine` and `PlayerServices` contracts: html (Chromium's `<video>`, the fallback) and native (libmpv through `@raven/mpv`, drawn under the page). The `Platform` seam, `RavenProvider` and the library hosts are phase 2 (the spec's D1 to D4) and do not exist yet.
- **Main owns everything that can reach outside the window:** file paths, servers, cookies, the network and mpv. The renderer holds only ids: a granted `fileId`, a `serverId`, a media id, a `downloadId`. It loads from `app://raven` under a CSP with `connect-src 'self'`.
- **The bridge.** The player talks to main over one MessagePort, and main acts only on a `PlayerCommand` that `isPlayerCommand` in `@raven/core` accepts. Server calls go through the page's `ApiClient` to main, which runs only the sixteen calls in `src/main/servers/allowlist.ts` (`getMedia`, `getTracks`, `saveProgress`, `recordPlay`, `getLock`, `unlock`, `getAdminLock`, `unlockAdmin`, the downloads' `getItem`, `getLibrary`, `getSagas`, `getMediaOrigins`, `getMediaTicket`, and the accounts' `getAuthConfig`, `getMe`, `getAccountTicket`) in that server's own session, and refuses and logs the rest. `getMediaOrigins`, `getMediaTicket`, `getAuthConfig`, `getMe` and `getAccountTicket` are main's alone: `isPageCall` refuses a page that asks for any of them, so the page never holds a ticket, a media origin or an account token.
- **Main owns the account sessions and the relay.** A server whose `GET /api/auth/config` answers `ready` is pinned in `desktop-config.json` (version 4) with its Supabase address, publishable key and web origin, validated at the trust boundary. A later config that names other endpoints asks in main's own sheet before any password goes there, and only a yes re-pins. Main holds one `@supabase/auth-js` client per ready server (`src/main/accounts`) and adds `Authorization: Bearer` to every allowlisted call to it, refreshing once on a `signed_out` refusal. The renderer sees an `AccountView` (state, email, whether the sign-in is remembered, the sign-in host), never a token. Create account and Forgot password open the server's web origin in the browser. A server that answers `off`, `unavailable` or 404 (older than the accounts) gets no Bearer and no sign-in UI and keeps the cookie, PIN and admin password paths (decision D1); on a `ready` server main refuses `getAdminLock` and `unlockAdmin` before any request goes out.
- **Sessions are encrypted with `safeStorage`.** Each server's session is one encrypted file under `userData/accounts`, named by an opaque id; a corrupt or undecryptable file reads as signed out and is removed, and a removed server's file goes with it. When encryption is unavailable (or `RAVEN_DESKTOP_SAFE_STORAGE=off`) sessions live in memory alone: nothing is written, a relaunch is signed out and the sign-in form (Settings, the server page, the download dialog) says the sign-in is not remembered. A keychain refusal also signs the person out.
- **Server titles with accounts play through a loopback relay.** For a `ready` server mpv opens `http://127.0.0.1:<port>/<secret>/file`, never the server's address. The relay (`src/main/servers/mediaRelay.ts`) forwards only GET and HEAD, with the `Range`, to the server with an account ticket from `accountTickets.ts`, so every seek, reconnect and sidecar gets a live ticket and no ticket, token or cookie enters an mpv URL, header or log. A ticket is reused for 240 s (`ACCOUNT_TICKET_RENEW_MS`, under the server's five minutes), then minted again, and a `401` mints once more and repeats. A refusal (`403`, or a second `401`) is read off the relay, not off mpv, which ends such a file as a plain eof; it surfaces as an `account` player error. The secret is 43 characters, per load, retired when the title leaves the screen; the page never learns the relay's port. Whether a server is `ready` is a read bounded at 3 s (`accountsReady.ts`) shared by playback and downloads.
- **Test hooks are read only unpackaged** (`app.isPackaged` false): `RAVEN_DESKTOP_USER_DATA` (a throwaway profile), `RAVEN_DESKTOP_MPV` (`headless` runs mpv with no video or audio output for e2e, `off` leaves the html engine), `RAVEN_DESKTOP_RELEASES_URL` (the release check's URL, and the only way an unpackaged launch checks at all), `RAVEN_DESKTOP_BUDGET_MS` (shortens the budget windows), `RAVEN_DESKTOP_SYNC_RETRY_MS` (shortens the five-minute retry that sends the downloads' plays and positions to their servers: a whole number of milliseconds from 100 to 300000, anything else ignored) and `RAVEN_DESKTOP_SAFE_STORAGE` (`off` forces the memory fallback for account sessions, as when the keychain is unavailable). A packaged app reads none of them.
- **Downloads live in `src/main/downloads`,** wired by `downloadService.ts`. On disk they are `userData/downloads/<serverId>/<mediaId>/video.<container>` (`.part` while it downloads) with `subtitles/<trackId>.vtt` beside it, and their state is `userData/downloads.json`. Paths come from the path builders in `space.ts`, which refuse an id, container or track id their guards do not pass; the launch sweep joins only folder names that pass the same guards. A download from a server with accounts `ready` fetches with an account ticket (`mediaAccess.ts`'s `account` access) from the media origin `pickOrigin` picks, or from the server's own address when none answers: a fresh ticket per fetch run, shared by the file and its subtitles, which download first. Each server's downloads mint at most 16 in any five minutes (`DOWNLOAD_MINTS`, a ticket's life), so a queue never uses up the account's 32 live tickets, and a run past that waits, abandonably. A `401` resumes from the bytes on disk with a new ticket once, and so does a response the server cuts after the fetch wrote bytes (its body breaks, or ends short of what it promised), at once and with no pause; a cut with no new bytes is an outage, as on the other paths. A second `401`, a `403` or a refused mint fails the file and its queued group-mates with the account copy ("Sign in to X again", "Your access to X was removed"), and signing out or removing the server ends the running ones the same way. Any other server fetches with a ticket from the media origin that core's `pickOrigin` picks, as the web player's does, or from the stored origin with the cookie when it lists none (or none answers the probe). A ticket never reaches `downloads.json`, the page or the log. `downloads.json` is version 2: each entry's pending play carries `accountId` (the signed-in account's id, `null` for a server without accounts or a version 1 file, which `upgradeDownloads` reads as before accounts), and `owed` plays are kept per title and account. A play is tagged with the account signed in when its title was opened (`playback.ts`'s sittings), so a title left open while another account signs in sends its later positions and its close only to the account that opened it, through `owed`; a play made while signed out of a server with accounts is not queued. A server title's page reports are held the same way: main records the account when the page opens the title (`titleSittings.ts`), keeps it through every reload of the player until the page says it left (`leaveServerTitle`, sent when the page leaves the title or stops letting the account in) or a new page loads, and `callFromPage` sends its `saveProgress` and `recordPlay` only under that account's token, refusing them once another is signed in. `sync.ts` sends an item only when its `accountId` is `null` or the account now signed in, checks again before every call, and `ServerCalls` verifies the token's own `sub` against the item's account, so one account's play never goes out under another's token. When the server's account changes (`accountSwitches`), `downloadService.accountSwitched` moves the other accounts' pending plays to `owed` and syncs what the incoming account is owed, and `desktopService.accountSwitched` drops that server's recents; the renderer is told only the server id (`accountSwitched`) and invalidates that server's cached queries with `refetchType: 'none'`, so a title being watched is not torn down; its title query never refetches on focus or reconnect, which would reload the player. An older raven player cannot read a version 2 store and sets it aside.
- **Never build libmpv or the addon without the toolchain.** `fetch:libmpv` and `build:native` need the pinned sources, Xcode's Metal toolchain and `native-build/prefix`; CI builds them (`.github/actions/raven-desktop-native`). Locally, use the CI-built `libs/raven/mpv/resources/darwin-arm64` (gitignored). `stage:mpv` copies it into `staging/mpv` for `package` and `make`, and fails when a Mach-O file is missing.
- **Logs** go to `~/Library/Logs/raven` (`raven.log`, then `raven.log.1` to `raven.log.4`, 1 MiB each), crash dumps to `~/Library/Application Support/raven/Crashpad`, never uploaded. Every line is redacted first: no cookie values, PINs, passwords, request bodies, file paths, file names, access or refresh tokens, `Authorization` headers, JWTs, account tickets or `?t=` parameters, relay secrets, or email addresses. A new log line goes through the log, never around it.
- **Releases.** A pushed `vX.Y.Z` tag runs `release.yml` and `.github/workflows/desktop-release.yml` together; the desktop workflow builds, audits and smoke-tests the app, then attaches `raven-player-<version>-arm64.dmg`, the zip, `raven-player-<version>-sources.tar.gz` and `SHA256SUMS` to the tag's release. A pull request that touches the release's files, or a dispatch from the Actions tab, is its dry run, which never publishes. The app is signed ad hoc: Developer ID signing and notarization are wired behind `RAVEN_SIGN_IDENTITY` and `RAVEN_NOTARIZE_PROFILE` and stay off, since no certificate exists, and no workflow sets them.
