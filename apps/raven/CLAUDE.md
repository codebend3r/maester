# Claude context for raven

## Hard rules

- Do not commit, push, branch, merge, or open a PR unless told to.

## What this is

A self-hosted video library and web player: direct play, with an on-the-fly remux or transcode for what the browser cannot play. See README.md for how playback, scanning and thumbnails work.

## Structure

raven's projects live in the workspace described by the root `CLAUDE.md`, which covers Nx, the project table and how to run tasks: `@raven/server` in `apps/raven/server`, `@raven/web` in `apps/raven/web`, `@raven/core` in `libs/raven/core`, the shared player `@raven/ui` in `libs/raven/ui`, the libmpv addon `@raven/mpv` in `libs/raven/mpv`, Raven, the macOS app, `@raven/desktop` in `apps/raven/desktop`, and the device app for iPhone, iPad, Apple TV and Android TV, `@raven/app` in `apps/raven/app`. The server also depends on `@shared/server` (`libs/shared/server`), which it shares with rookery: it serves the built web app, compresses responses, opens SQLite and runs `MIGRATIONS`, reads the listen config, and compares the PIN and the unlock cookie in constant time.

`libs/raven/core` must stay platform-agnostic: no DOM, no Node APIs, not even `URLSearchParams` (use `toQueryString`). Its tsconfig has `lib: ["ES2023"]` and no `types` so a slip fails the typecheck. So a server address is read with core's `serverOriginOf` and `isServerOrigin`, WHATWG's host rules written out without `URL` (React Native's `URL` normalises nothing), and every client shares them.

The image builds from the repo root: `docker build -f apps/raven/Dockerfile .`. `Dockerfile.dockerignore` allowlists what it copies; a new path the image needs goes there too.

Supabase Auth preparation lives in `@raven/supabase` (`apps/raven/supabase`). Its runbook is `supabase/README.md`, and its raven-first design is `docs/superpowers/specs/2026-10-17-supabase-sign-in-design.md`. A confirmed sign-up is approved while `private.enrolment`'s `approve_until` is in the future (Dec 1 2026, New York time) and pending after it, until the explicitly bootstrapped owner approves it; either way the `signup-alert` Edge Function emails the owner. User metadata never grants ownership. With accounts `ready` the server enforces them: see "Accounts" below. No cloud deployment or owner bootstrap happens as part of a PR.

## Conventions

The TypeScript, code style and CSS rules are in the root `CLAUDE.md`. raven adds:

- The API contract is `libs/raven/core/src/contract.ts`. Each shape is written once, as its `is<Type>` guard built from the combinators in `schema.ts` (`object`, `oneOf`, `nullable`, `listOf`, `union`, `exactPartial`), and its type is read off the guard: `export type MediaItem = Infer<typeof isMediaItem>`. A new API type is a new guard there, never a hand-written type beside a hand-written guard. A union of literals is an `as const` object and a guard built from it, `export const isScanState = oneOf(Object.values(SCAN_STATES))`. Code compares against the object (`SCAN_STATES.idle`), and the guard's `.values` is the list for a menu or a loop. Request bodies get guards there too, so the server checks a body with the guard the client's call is typed by.
- What each type of library allows (its sorts, views and groupings, and whether it is matched) lives in `KIND_RULES` in `libs/raven/core/src/libraryKinds.ts`; `coherentSettings` applies it.
- Narrow with the guards in `@raven/core` wherever data crosses the network.
- The web app is also served from Netlify, whose CDN proxies `/api` to raven (README, "On Netlify"). A response that depends on the browser's cookies, the PIN's or the admin lock's, or on the account's, is never `public` in `cache-control`, or Netlify's cache hands it to everyone. The one public kind is a capability picture (`PICTURE_PATHS`, `PicturesController`): its address names a version `PictureVersions` keys with the server's secret, so the address alone is the permission, and the web build on Netlify sends it through the Image CDN. A new picture an item or a person shows gets a capability address; one only an account may see (a thumbnail, a manage screen's preview) stays private.
- **A transcode can burn a picture subtitle in.** The HLS master and the browser's `/stream` take `?burn=` (core's `HLS_PARAMS.burn`), an embedded picture track's id (Blu-ray PGS, VobSub), for a transcode only; a remux, a text track (a rendition of its own) or a track that is not there is a 400, and both routes read it through `burnSubtitleOf` (`playback/conversion.ts`), which adds the canvas. The stream gives the same timestamps with a burn as without (`streamArgs` moves a burn's output by `streamShift + start`), even for a file whose clock starts late. The run lays the subtitle over the frame in a filter graph before it is scaled (`transcodeVideo`'s `burn`, mapped as `[vout]`), decoding on the CPU under VAAPI, and gives ffmpeg the canvas (`-canvas_size`, the video's size), which it can not find for a track whose first cue lies past its probe. ffmpeg 5.1 lays no picture subtitle after a seek on the file's clock, so a burn reads the file without `-copyts`, on a clock from the point it sought to, and moves its output back onto the file's with `-output_ts_offset` (`burnCut` in `hlsArgs.ts`); a transport stream's audio input is moved onto the video's with `-itsoffset`. The route tests burn a PGS track `writePgs` (`src/test/clips.ts`) writes, since ffmpeg makes no picture subtitle from text.
- **A Dolby Vision HEVC copy keeps its Dolby Vision.** The HLS remux, the browser's `/stream` remux and the device MP4 copy all go through `copyVideo` (`ffmpeg/args.ts`), which tags a copy of HEVC with a Dolby Vision record (`dolbyVisionOf` in `ffmpeg/probe.ts`, `VideoStream.dolbyVision`) `dvh1` under `-strict unofficial`, so ffmpeg writes the `dvcC`/`dvvC` box beside `hvcC` and AVPlayer renders profile 5 itself instead of showing its IPTPQc2 picture as plain HEVC, purple and green; plain HEVC stays `hvc1`. Profile 7 (a 4K Blu-ray's, `DOLBY_VISION_PROFILES.dualLayer`) is the exception: no Apple device or browser decodes it (AVFoundation answered a `dvh1` copy of Game of Thrones' S05E03 "Cannot Decode", 2026-11-13), so its copy is the HDR10 base layer alone, `hvc1` with `-bsf:v filter_units=remove_types=62|63` taking out the RPU and the enhancement layer (`isDualLayerCopy`), as Android TV's player plays it, and the master names it `hvc1` with `VIDEO-RANGE=PQ`. The segment muxer hands its MP4 muxer no compliance level, so the HLS run repeats `strict=unofficial` in `-segment_format_options`. The HLS master names the variant `dvh1.PP.LL` (core's `dolbyVisionCodecString`) and declares `VIDEO-RANGE` (`PQ` for Dolby Vision and HDR10, `HLG`, else `SDR`; always `SDR` for a transcode, which is 8-bit H.264). The browser path is unchanged: the web still transcodes profile 5 with its tone map, and thumbnails never touch the record. A browser's offline copy is the one place profile 5 is converted properly: the SDR copy below reads the Dolby Vision metadata through libplacebo.
- **A device download has two copies, and `sdr` is the browser's.** `copy` (the default, what the iPhone and iPad app asks for) keeps the picture and goes through `copyVideo`. `sdr` (`ffmpeg/sdrDownloadArgs.ts`) is an MP4 any browser plays offline: libx264 on the CPU (High profile, 8-bit `yuv420p`, CRF 20, `veryfast`, fitted inside 1920 by 1080 and never enlarged), every audio track as AAC stereo with the file's default first and alone flagged default (Chrome and Firefox play the first track and offer no choice; Safari lists them), text subtitles as `mov_text`, `+faststart`. `sdrPictureOf` picks the filter: an SDR picture is only scaled, and an HDR one goes through the zscale `TONEMAP_FILTER` when `canTonemap`. Dolby Vision profile 5 has no `sdr` copy: only libplacebo reads its RPU, and on Vhagar it ran at 1.7 frames a second for 1080p (measured 2026-11-11, on Mesa's software Vulkan device, since the UHD 600 fails on 10-bit frames), a day for a film. So the prepare route answers `failed` with `DEVICE_DOWNLOAD_FAILURES.dolbyVision` and encodes nothing, and the image carries no Vulkan drivers. Both copies sit in one media folder (`<mtimeMs>.mp4`, `<mtimeMs>.sdr.mp4`) under the one `deviceDownloadCacheBytes` cap, and an audio container is a 409 for either.
- The media plane routes are the ones marked `@MediaPlane()`: `stream`, `file`, `transcode`, `device-download/file` (a video's MP4 copy for a device that cannot play the original, made by `GET /api/media/:id/device-download` in `media/deviceDownloadCache.ts`, which keeps its copies, as `music/transcodeCache.ts` keeps its tracks, in a `media/outputCache.ts` of its own: the versioned folders, the temporary-then-rename write, the hold while a response sends a file and the sweep to a cap; `?variant=` on both routes, core's `DEVICE_DOWNLOAD_VARIANT_PARAM` and `DEVICE_DOWNLOAD_VARIANTS`, names the copy, `copy` when absent and a 400 when unknown), `subtitles`, the six HLS routes under `/api/media/:id/hls/` (the master playlist, and each session's video playlist, init, segments, subtitle playlists and subtitle segments) and the ping. They answer CORS for `RAVEN_WEB_ORIGINS` and open for a `?t=` ticket: an account ticket under `ready`, the legacy HMAC ticket only when accounts are `off`. Under `ready` an HLS master opened with an account ticket gives its session a capability (`hls/hlsCapability.ts`: `hls.` and 32 random bytes), and the session's five routes, marked `@OpenedByPass(PASS_KINDS.capability)` and listed in `PASS_ROUTES` (`src/test/enforced.ts`), take only that capability, in the same `?t=` so every client's ticket redaction covers it, until `ACCOUNT_PASS_MS` (12 h) after the master. There a wrong, expired or foreign capability gets 404, as do an account ticket, a Bearer and the cookie on a session that has one; no credential, a legacy ticket or a repeated `?t=` gets 401 `signed_out`. `file`, `transcode` (a track as AAC from `music/transcodeCache.ts`) and `device-download/file` are marked `@OpenedByPass(PASS_KINDS.ticket)`: once an account ticket has opened any of them, `FilePasses` (`media/filePasses.ts`) keeps that ticket opening that media's file and transcodes for its account past its five minutes (and through an outage inside them), for 12 h from that first open, and nothing else; a ticket that never opened its file still expires at five minutes, and on another media or route a bound one gets what it always got. The passes live in memory, at most 8 per account and 256 in all, the least recently used going first. Both kinds are one `AccountPass` (`auth/accountPasses.ts`'s `openPass`): the secret compared with `sameSecret`, the deadline, the account's recheck, and the owner's PIN unlock the ticket carried, all read off the ticket's caller by `TicketAccesses` (`auth/ticketAccesses.ts`). Thumbnails and JSON stay on the same origin as the page. A new route that streams bytes to the player gets the mark.
- raven is reachable from the internet, so every route that is not a GET says who it is for: `@AdminOnly()` or `@ForViewers()`. `@AdminOnly()` is the owner once accounts are `ready` and the admin lock on a server without accounts; a GET that only a managing screen reads is `@AdminOnly()` too. The server refuses to start with a write route marked neither, as it does with a route the PIN lock has not been told about. Never ask the admin lock directly: `Management.canManage({ request })` answers for both.
- Every request from the internet is rate limited per client, in memory (`RequestCounts` and `limitRequests` in `rateLimits/limitRequests.ts`). The Fastify hook `limitRavenRequests` (`rateLimits/limitRavenRequests.ts`) counts only the `standard` and `media` tiers, before the route runs, and never the home network (`isLanRequest`). The whole `strict` tier is `AccountRateGuard`'s (`rateLimits/accountRateGuard.ts`), counted after the account gate, so a strict request the gate refuses spends nothing: by address first, the home network's too, so nothing that passes for home can guess a secret, then (once the tier is full) every new address in the shared overflow window, then per signed-in account. A client is its address, an IPv6 one by its /64 (its /48 on the `strict` tier), and a visitor of the Netlify site by the address Netlify passes on, `x-nf-client-connection-ip`, believed only beside a valid `x-nf-sign` signature keyed with `RAVEN_PROXY_SECRET` (`rateLimits/netlifyClient.ts`); no place in `X-Forwarded-For` is taken on trust. Each tier counts in a map of its own and never drops a running window to make room: full, `strict` counts every new client together in one shared window (`overflowLimit`, 600 a minute), past which `AccountRateGuard` refuses a request with no account while a signed-in account goes by its own budget, so a flood of strangers never locks it out, and the others let new clients through uncounted (`WHEN_FULL`). A route's tier is read through `routeMarks.ts` (`rateTierOf`): `strict` (120 a minute per address, and 30 per signed-in account through `AccountRateGuard`, after the account gate) when marked `@StrictlyLimited()`, `media` (3,000 a minute) when marked `@MediaPlane()`, and `standard` (1,200 a minute) otherwise. Past a limit a request gets 429 with `Retry-After`. A new route that checks or hands out a secret (a PIN, a password, a nonce, a ticket) gets `@StrictlyLimited()` and a row in `RATE_ROUTES` (`src/test/enforced.ts`), or the inventory in `appEnforcement.test.ts` fails; a new media plane route joins `RATE_ROUTES`' `media` list.
- **The web app installs as a PWA.** `public/manifest.webmanifest` and `public/icons/` make it installable; `src/serviceWorker/sw.ts` builds on its own to `/sw.js` (vite.config.ts's second entry, core's `SERVICE_WORKER`, typed by `tsconfig.worker.json` against the WebWorker library), and `src/lib/serviceWorker.ts` registers it in a production build outside Raven. It keeps only the shell and static files (`strategyFor`): never `/api`, a ranged request, another origin or a write, so no account's data, ticket or stream is ever cached. A navigation tries the network first and falls back to the kept index offline. Playwright's e2e blocks it, but for the one suite that opens the app with no network (`e2e/downloads.e2e.ts`). A download never goes through it: the browser's downloads keep their own files (below), and with no network the kept shell opens to Downloads.
- **The page's downloads go through a downloads host.** `stores/downloadsHost.ts` holds one `DownloadsHost` (`apps/raven/web/src/downloads/host.ts`), set once before the first render: Raven's (`downloads/desktopHost.ts`, which hands every request to main as it is) or the browser's (`browserDownloads/host.ts`). Every host answers the desktop's protocol (`DownloadsRequest`, a slice of `DesktopRequest`, answered with `DesktopReply`), so the Downloads page, the dialog, the Download button, Settings' Downloads section and their hooks (`desktop/downloadsApi.ts`) are written once and read `useDownloadsHost`, never `useDesktop().client`. What differs is data on the host: `canKeepMusic`, `canShowFolder` and `canAutoDelete` (whether albums and playlists download and the music mode has a Downloads page, whether there is a folder to show, whether a download deletes itself once watched), `offlinePages` (the routes `AuthGate` opens with no server) and `pictureUrl` (a saved picture's address by its opaque id: `raven-picture://` in Raven, an object URL in a browser, null until read). The page shows or leaves out by those three and words itself from a copy map keyed by `DOWNLOADS_HOSTS`; it never branches on `useIsDesktop` for a download. With no host there is no Downloads route, no nav entry, and the Download button falls back to the `raven://download` link where the browser says Raven is installed.
- **A browser downloads videos and plays them offline.** `startBrowserDownloads` (`browserDownloads/start.ts`) makes the engine where `canKeepDownloads` says the browser can (a secure context, `navigator.storage.getDirectory`, and `createWritable` on the file handle), outside Raven. The engine (`browserDownloads/engine.ts`) is the queue and what the page reads of it, over a module each for the asks (`asks.ts`), the index (`store.ts`), the server's copy (`prepareCopy.ts`), the file's bytes (`fetchBytes.ts`), the pictures (`pictures.ts`) and the subtitles (`subtitles.ts`). It takes its disk, server, clock, tabs, object URLs and ids as injected types (`disk.ts`, `server.ts`, `clock.ts`, `tabs.ts`), so its tests run on fakes (`src/test/browserDownloads.ts`, `src/test/opfs.ts`).
  - **Where.** The Origin Private File System: `downloads/<accountId>/<downloadId>/media.<ext>` with `subtitles/<n>.vtt` beside it, a title's poster and title art once under `downloads/<accountId>/pictures/item-<id>/`, and one `downloads/index.json` that `readIndex` checks entry by entry (a mid-flight download reads back as queued, an entry its guard refuses is left out alone). A file is written on the main thread through `createWritable({ keepExistingData: true })`, whose bytes join the file only when it closes, so a download commits each time it has doubled (`COMMIT_MIN_BYTES` at least): a closed tab loses at most half of what was fetched. It resumes with `Range` from the bytes on disk, and a response that sends nothing for `STALL_MS` (30 s, Raven's own wait, timed by the injected clock) is given up as a cut one is: asked for once more when it had sent new bytes, else paused as a lost connection. `navigator.storage.persist()` is asked for at the first confirmation, and the space is `estimate()`'s: an ask that would not fit says so and offers no Download, and a quota error pauses the download with why.
  - **Which bytes.** `downloadWayOf` (`ways.ts`): the original when `checkDirectPlay` with `browserCanPlay` says the browser plays it; for a Dolby Vision only title the `copy` variant where the browser says it plays `dvh1` and never the original; the `copy` variant when it plays the picture but not the container; else the `sdr` variant. A Dolby Vision only title has no way where the browser does not play `dvh1` (`isKeepable`): the host's `canKeepDolbyVision` is false there, so `DownloadButton` greys Download out and `DolbyVisionNote` says DV5 downloads are unsupported, opened by itself the first time (`stores/downloadNotes.ts`) and by the button after; a season or show leaves those episodes out, and an ask left with none is refused in the same words. A copy is prepared by polling `getDeviceDownload` first, its progress told to the page (`stores/downloadPreparing.ts`, "Preparing 42%" on a queued row, since the protocol's statuses are Raven's and stay as they are), its size corrected once it is ready, and a `failed` answer fails the download in the server's words.
  - **Who.** Videos only (`canKeepMusic` is false, so an album or a playlist keeps its browser behaviour). One file at a time, in confirm order, only while a tab or the installed app is open; a cut-off download takes up again the next time it is. Several tabs share the one disk and index, so `tabs.ts` (`browserTabs`, over the Web Locks API and a broadcast channel, each feature-detected) keeps them apart: the tab that holds the `raven-downloads-queue` lock, until it closes, is the only one that downloads or fetches pictures, and every tab changes the index as a read, change and write of the file under the `raven-downloads-index` lock (`store.ts`), never as a write of what it has in memory, then tells the others, which read it again. The index names no download as on its way: the queue's tab says which one is and how far (`Running`), on the channel, and a pause or a delete made in another tab stops its run. A browser with no locks has one tab's word for it, as before. Downloads belong to the account: `downloadsAccountOf` (`account.ts`) is the signed-in account, the one shared `local` with accounts off, and, while the server is out of reach and a session cannot be renewed, the account that last signed in (`stores/browserDownloads.ts`), which `signOut` forgets. Another account sees none of them and a sign out hides them; the files stay.
  - **Media rules are the player's.** On the page's own origin the session cookie opens the file; through a media origin (`useMediaOrigin`'s pick) an account ticket rides as `?t=`, minted for the fetch, used again for `TICKET_REUSE_MS`, at most `MINTS_PER_WINDOW` in five minutes, and once more after a `401`. No ticket reaches the index or a log, and every file request says `?purpose=download` so Streams lists it apart from a play.
  - **Everything shown is saved.** Each entry keeps its group, label, facts, `MediaItem`, tracks, library (`isPrivate` from `settings.locked`) and saved pictures, filed by core's `desktop/downloadTitles.ts` as Raven's main files it (`browserDownloads/expand.ts` only reads the server through the page's API client), so both Show modes and the private hiding work with no server; a title in a locked library is refused at the ask as Raven refuses it. Text subtitles are saved as WebVTT once the file is whole (every sidecar, and the first `EMBEDDED_SUBTITLES_KEPT` embedded tracks, read a window at a time), since a browser draws none of an MP4 copy's own, and the shared player's file source takes them as `FileSubtitles`, so the normal subtitle menu offers them. A picture or a subtitle that fails never fails the download.
  - **Playing.** `/downloads/play/:downloadId` (`BrowserPlayPage`) plays the html engine on an object URL of the OPFS file, which stays on disk behind it and is let go of on leaving. While the list is still being read it waits; an id the browser does not hold is refused with the way back to Downloads. The position is kept with the download; while the server answers, the play and each position also go to it as `WatchPage`'s do, and what is watched out of its reach stays on this browser (there is no queue of owed plays, as Raven has). `watch/:id` with the server out of reach plays the title's ready download (`OfflineWatch`), else goes to Downloads.
  - **Offline.** `BrowserDownloadsHost` follows `useServerReach` as `DesktopHost` does, and also the device's network (`shouldFollowDevice`), so the installed app with no network opens the host's `offlinePages` (Downloads, a download playing, a watch page, Settings) with no account read, and any other page goes to Downloads. The worker keeps a build file only once it sees it fetched, so `keepOfflinePages` (`browserDownloads/keepOffline.ts`, called from `AppRoutes` with its `OFFLINE_PAGES`) fetches again what the page already loaded and asks for those pages' chunks once the worker answers for the page, and only from the first download on (`useKeepOfflinePages`): asked on every visit, the player's and the watch page's chunks took the sign-in page to 230 requests and Lighthouse's mobile score under its floor; a new page a server out of reach should show joins `OFFLINE_PAGES` and the host's `offlinePages`. `e2e/downloads.e2e.ts` downloads the fixture's film in Chrome, reloads and plays it, then does the same with the network off.
- Server constructors inject with explicit `@Inject(Token)`, so DI never depends on decorator metadata, which neither vitest nor `tsx` emits.
- Every raven project imports its own modules via `@/` with no extension; `tsconfig.json` uses `"moduleResolution": "bundler"` so TypeScript allows it. The server's `dev` runs through `tsx`, and its `build` is `tsc` then `tsc-alias`.
- Every search box is held by headless `useSearch` (`@raven/ui/headless`), so every one is debounced: it searches once typing pauses for core's `SEARCH_DELAY_MS`, or at once on Enter. On the web it is a `SearchField` (`components/SearchField`), and web's `useAddressSearch` (`lib/useSearch.ts`) holds one that rides in the address as `?q=`; in the device app it is the layouts' `SearchField`. A search box is never a bare `<input type="search">` or `TextInput`, and no search runs on each keystroke. The shell's `SiteSearch` passes `shouldWaitForEnter`, so home's results and the address change only on Enter or a picked suggestion, while the box itself offers the first titles found once three letters are typed and the typing pauses.
- The tokens are in `libs/raven/ui/src/styles/globals.scss`, and element defaults in `elements.scss` beside it. The web `/design` page reads the shared `globals.scss` through `@raven/ui/designTokens`, so a new token shows up there with no extra step; the device app reads it and each theme's colours (`themeTokens`) from the same entry, and wears the theme picked in its Settings (`useTheme`, `apps/raven/app/CLAUDE.md`, "Themes").
- Every colour comes from a token a theme can redefine. `themes.scss` beside `globals.scss` gives each of the seven themes in `THEMES` (`libs/raven/core/src/themes.ts`) its values under `[data-theme='…']`; a new themable colour goes in `:root` and in every theme block (a test checks they match). What sits on a picture uses the fixed `--color-on-picture*` and `--color-picture-*` tokens, and anything on a `--color-leaf` fill is `--color-on-leaf`. The web app keeps the viewer's choice in `stores/theme.ts`.
- **Music has a mode of its own at `/music`.** `PlayerLayer` holds the audio host and the now-playing bar over both shells (`AppShell`, `MusicShell`), so switching modes keeps playing; `MUSIC_PATHS` lists its pages and `useMusicLinks` picks album, artist, playlist and Now Playing links for the mode the page is in. The browser's `AudioHost` levels through each element's volume and routes through Web Audio (`soundGraph`) only once the EQ or a crossfade needs it.

The shared player has no web app imports. Hosts give it an `Engine` and their `PlayerServices`, which reach the player's parts through the `usePlayerServices` store (`libs/raven/ui/src/stores/playerServices.ts`), never a context: the component that renders `<Player>` calls `useHostPlayer(services)` and renders the player only once it answers true, so the player's first render reads that host's services, never the last host's. Call it in the component whose lifetime is the player's: a host that swaps one player for another hosts each in a component of its own, as the desktop pages' `NativePlaying` and `HtmlPlaying` in `apps/raven/web/src/desktop` do. Progress is reported the same way by every player: headless `useProgressReport` turns the shared video state into `ProgressSink` calls (the web's `useWatchProgress` is it with the page's `pagehide`; the device app passes `AppState`), and every host starts where core's `resumeAtFor` says. The browser keeps its API singleton, its one query cache and WatchPage services; the queries, invalidation, optimistic edits, data hooks, selection store and page backdrop live in `@raven/ui/headless`, and web's `lib/queries.ts`, `lib/useMediaMutations.ts`, `lib/useWatchedChange.ts`, `lib/useItemFavourite.ts` and `lib/useServerEvents.ts` bind those factories to web's client. Import built `@raven/ui` exports and `@raven/ui/styles.css`, never alias UI sources from another project. See `libs/raven/ui/README.md` for peer dependencies and test ownership.

## Remote access

raven is reached from the internet as Plex is: a router port forward to DSM's reverse proxy, which terminates TLS for a DDNS hostname, in front of raven's `8484`. Its design is `docs/superpowers/specs/2026-11-04-raven-remote-access-design.md`.

- **The settings are the owner's.** `SETTINGS_KEYS.remoteAccess` holds core's `RemoteAccessSettings` (enabled, hostname, public and private port, upload speed, remote limit); `GET` and `PUT /api/remote-access` (`REMOTE_ACCESS_PATHS`) are `@AdminOnly()`, and Admin's Remote Access section (`apps/raven/web/src/pages/SettingsPage/RemoteAccessSection.tsx`) reads and writes them. A `PUT` always checks again; an empty one only checks.
- **The check runs outside.** The server can not test its own public reachability from the LAN, so `Reachability` (`src/remoteAccess/reachability.ts`) mints a 30 second nonce and asks the web app's Netlify function (`apps/raven/web/netlify/functions/reachability`, at `RAVEN_WEB_URL` + `REACHABILITY_CHECK_PATH`) to fetch `/api/remote-access/echo/:nonce` at the public origin. Only raven holding that nonce answers 204; the echo is `@OpenToAnyone()` and `@Public()`, in the route inventory, and says nothing else. The server signs each ask: `signature` is the HMAC-SHA256 hex of the nonce keyed with `RAVEN_PROXY_SECRET` (`checkSignatureOf`), and without `RAVEN_PROXY_SECRET` or `RAVEN_WEB_URL` no check is made and the status is `unchecked`. The function (which reads its own `RAVEN_PROXY_SECRET`, at Netlify's Runtime scope) answers an unsigned or wrongly signed check 403, so it is no open probe. It refuses a hostname that resolves to a private address (`isPrivateAddress`, which takes a name or anything else that is not an IP as not private, so a caller resolves first) and connects to the address it vetted (`node:https` with a pinned `lookup`, `servername` the hostname, so TLS still checks the name), so a second lookup can not rebind it. It reports the caller's address, the home network's WAN IP. An answer stands a minute.
- **The public origin is a media origin.** `publicOriginOf` (core) is `https://<hostname>[:<port>]` while enabled and configured, and `GET /api/media-origins` lists it after `RAVEN_MEDIA_ORIGINS`. The origin kinds are `lan` and `public`; no other kind is accepted.
- **The remote limit caps transcodes away from home.** `streamSizeFor` (`src/remoteAccess/remoteCap.ts`) lowers an HLS master's or `/stream`'s transcode to core's `remoteQualityFor` (the lower of the limit and the whole upload, as Plex does) when the request is not from the LAN. `isLanRequest` (`src/remoteAccess/clientNetwork.ts`) reads `request.ip`, which Fastify's `trustProxy` walks from the socket through `X-Forwarded-For` past the proxies `RAVEN_TRUSTED_PROXIES` names (`docker-compose.vhagar.yml` pins the network and names its gateway), so a client's own header can not pass it off as at home. A private socket raven does not trust that forwards the header is the internet, never home, and an entry that is no address is never home. A remux and a direct play are the original and are not capped.
- **Players transcode away from home; the server sizes it.** `GET /api/media-origins` tells every viewer `remote: { limit, isOutside }` (`isRemotePlayback`): the ceiling as a `STREAM_QUALITIES` size and whether that request came from outside the LAN. core's `readMediaOrigins` hands it to clients as `RemotePlayback | null` (an older server's missing `remote` reads as null). Clients decide only the mode, with core's `planForNetwork`, `remoteLimitApplies` and `remoteTranscodeFor` (`libs/raven/core/src/remoteAccess.ts`, beside `PlayNetwork` and `AT_HOME`): away from home (a `public` origin, or the server's own address when `isOutside`) a file whose bitrate is over the limit starts as a transcode, the plan's other ways behind it. `streamSizeFor` / `sizeForNetwork` on the server is the only place the limit's size is applied; no client lowers a quality for it. A new client plans through core too, never a copy of the rule.
- **The event stream says `X-Accel-Buffering: no`,** so DSM's nginx passes each event on at once. It carries five events (`SERVER_EVENT_TYPES`): `library` to every stream, and `viewing` (a spot saved, a play counted, a mark made), `binge` (the list changed), `captions` (the account's subtitle look changed) and `notification` (one the server logged for the account, which its screens show as a toast) to the streams of that account alone (`ServerEvents` envelopes each with its viewing key, `EventsController` filters by the caller's), so every device of an account keeps its Continue watching and Binge in step with the others and nothing of one account reaches another. headless `useServerEvents` reads the right caches again on each (`afterWatched`, `afterBingeEvent`, `afterCaptionStyle`), except that a host playing a video passes `isWatching` and lets `viewing` pass while it does, since the event is its own save coming back and its player reads everything again as it closes; the binge list's key is `queryKeys.bingeState` on web and app alike.

## Accounts

- **The gate is default-deny.** With accounts `ready` the `AccountGuard` holds every route to an approved account unless its handler is marked `@OpenToAnyone()`; `@AdminOnly()` means the owner, and `GET /api/me` is the one `session` route. A new route is approved-only the moment it exists. One that must be open to anyone gets `@OpenToAnyone()` and a row in the inventory in `appEnforcement.test.ts` (`ROUTES` in `src/test/enforced.ts`), or CI fails: the inventory, the anonymous sweep and the owner sweep run every row.
- **The auth state is effective, not configured.** Read `AUTH_STATE`, never `config.auth`: it folds in the enforcement record (`accounts.enforcedAt`, written on the first `ready` start) and `RAVEN_ACCOUNTS=off` (`isAccountsOptedOut`, `hasEnforced`). A server that once enforced and lost its Supabase settings is `unavailable` (503), never `off`.
- **One caller per request.** `callerOf({ request })` is `legacy` (accounts `off`), a `session` (Bearer, or the cookie on `GET`/`HEAD`) or a `ticket` (an `account.` ticket on a media-plane route, its pass on `file`, or an HLS session's capability on that session's routes, standing for the account and unlock of the ticket that opened it; a ticket caller holds no token). The PIN lock, `Management`, the listings and the rechecks read it. Code that treats `legacy` as "the browser's rules" must branch on the auth state first and never fail open.
- **The PIN follows the account.** Only the owner unlocks; the `raven_unlock` cookie carries the account id; members never see locked libraries (404, not 423). A legacy HMAC ticket opens nothing under `ready`, the owner included. Nothing opened past the PIN outlives it: `POST /api/lock/lock` (`LockService.relock`) tells `relocks` the account, whose live tickets give the unlock back (`AccountTickets`), and a pass ends as its unlock goes, by that relock or its lapse (a timer, and `grantFor` for a host that slept), when its media's library is locked then (`LockService.unlockNeedOf`, which finds the library at open and reads its lock at the end, since a library may be locked or opened meanwhile); a pass on an unlocked library drops the unlock and plays on, so `LockGuard` holds it if the library is locked later. A `file` range still streaming as its pass ends, by these or any other way, is cut then (`FilePasses.hold` answers the pass's end, which the route hands `trackStream` with the recheck). The next request is refused as one without the unlock is, and the player reopens and meets the lock. Under `off` no pass exists and a relock only clears the cookie.
- **Open responses are rechecked.** SSE and `file`/`stream` responses (each media response through `trackStream`, which destroys it once the `ended` it is handed emits), and the account passes (HLS sessions opened with an account ticket, and the passes tickets earn on `file`), end through `AccessRechecks` every `DEFAULT_ACCESS_RECHECK_MS` (60 s, injected as `ACCESS_RECHECK_MS`); an `unavailable` recheck keeps an already-authorized stream until the last-known token expires, while removal and integrity failures end it at once. A client resumes a cut media response by range with a new ticket, and the browser's `/stream` from the end of what it has buffered (`createStreamSession` in `@raven/ui`'s `streamSource.ts`, which fails only after `MAX_CUTS` cuts in a row deliver nothing); an ended HLS session's routes answer 404, and the player opens the master again with one. The capability dies with its session (ended, forgotten, evicted by the cap, dropped with its media, past its 12 hours, its PIN unlock gone on a locked library, or a restart), a file pass the same ways, after which its file answers 401 `signed_out` and the player mints again; neither is ever logged.
- **Membership lookups go through `MembershipLookups`** (shared in flight, 5 s). A change made through raven calls `forget`; never call `AuthBackend.current` directly from a request path.
- **Never log or store** a JWT, refresh token or ticket.
- **The subtitle look is per account.** `caption_styles` holds each account's `CaptionStyle` (core's `contract/captions.ts`: a size and a colour), `GET` and `PUT /api/caption-style` (`captions/`) read and write the caller's own, and every player draws its text subtitles in it, in the display face: the web's overlay, mpv on the desktop (`subtitleStyle`, with `sub-ass-override` so a file's own styles give way) and the device app.
- **Scrobbling is per account** (`src/scrobbling`). ListenBrainz tokens and Last.fm session keys are sealed in `scrobble_links` and never logged or answered. Last.fm's `@OpenToAnyone()` callback takes the account from its signed, one-use `state` (`LastFmSignIns`, one per account, 10 minutes), and links only once the account's freshest live token in `AuthSessions` (`freshestFor`, as `AccessRechecks` reads it) finds it approved again: none live is a 400 to sign in again, a refusal a 400, an outage a 503. Known limit: a state names the account, not the browser, so whoever is handed a started sign-in's Last.fm page and allows raven there links their own Last.fm to the starter's account (login CSRF in reverse); it needs the victim to approve on Last.fm, and the link shows in Settings.
- **Viewing data is per account.**
  - `playback_progress`, `plays`, `favourites` and `item_favourites` carry `account_id`, the Supabase user UUID (`'local'` for rows from before accounts).
  - Every statement over them binds `@account`, taken only from `ViewingAccounts.keyOf({ request })` (`media/viewingAccounts.ts`), never from a body, query, header or claim; the only statements without it are the account migration, the adoption transaction and `ON DELETE CASCADE`.
  - The rebuilt tables are `WITHOUT ROWID` with their cascade indexes so the planner searches them by key. A new per-viewer table gets `account_id` in its primary key and a row in the isolation suite (`appAccountData.test.ts`), and its queries are added to the plan assertions.
  - The account migration is a normal `MIGRATIONS` entry with no down migration.
  - The approved owner's first request under `ready` runs `ViewingAdoption.adopt`: one transaction that merges every `'local'` row into the owner's (newer spot, earlier favourite time), then records `{ ownerId, adoptedAt }` under `SETTINGS_KEYS.viewing`. A failure rolls back, is retried at most once per request and after `ADOPTION_RETRY_MS`, and logs only the SQLite code and counts, never an id.
  - Under `off` the shared viewer is the recorded owner, else `'local'`; under `ready` or `unavailable` an unbound request stays on `'local'`.
  - Library view settings stay shared.
  - **The play history** is `play_history`: a row for every sitting with a video or a track, however short. Like `plays` and `playlists` it is keyed by a global `id`, not `(account_id, id)`: the id grows as sittings start, so it is both the history's order and its page cursor, everyone's page reads it backwards and an account's reads it through `play_history_account`, and adoption only moves rows. `kind` says how a row is kept: a `video` follows its play (`keepVideoSitting`, an upsert on `play_id` inside `ViewingRepository.notePlay`, for videos only); a `listen` is one the music hosts start and report (`useTrackListening`, which also counts the play: `POST /api/media/:id/listens`, then `PUT /api/history/listens/:id`). `GET /api/history` is the caller's own; `GET /api/admin/history` is `@AdminOnly()` and the one viewing read that names its account in the query (`?account=`). Both page by a cursor and leave out libraries the caller may not see, and the web shows them at `/history` and `/history/everyone`.
- **Notifications are per account.** Every toast an account's screens show is logged in `notifications` (`account_id`, a global `id` that is its order, the newest `NOTIFICATIONS_KEPT` kept): a toast a screen raises is posted by web's `useLogToasts` to `POST /api/notifications`, and one the server sends (`Notices.notify`, as smart match does for each album) is logged before it goes out on the event stream, so it is there when no screen is open. `GET /api/notifications` answers the caller's own and no one else's, and the web shows it at `/notifications`.
- **Playlists are per account, and may be shared.** A shared one (`playlists.is_shared`) is read, played and copied by every account through `Playlists`' `VISIBLE`, and written only by its owner: a write on another's answers 404 (`findOwn`), as if missing. A locked library's tracks stay out of a shared playlist and its copies.

## Desktop

Raven (`@raven/desktop`) is the `@raven/web` build in an Electron window on macOS arm64, plus mpv, downloads, local files and links. It has no UI of its own: the same pages, look, Supabase sign-in, server and database as the web. Its design is `docs/superpowers/specs/2026-10-12-raven-desktop-design.md`, whose dated note at the top (2026-10-22) supersedes the player-first scope and D1/D4; the downloads' is `docs/superpowers/specs/2026-10-17-raven-desktop-downloads-design.md`.

- **A loopback web host serves the page.** Main serves `@raven/web`'s build from `http://localhost:47484` (`src/main/webHost.ts`; `WEB_HOST`, `PAGE_ORIGIN` and `WEB_HOST_PORT` in `libs/raven/core/src/desktop/webHost.ts`), the window's only origin. The port is fixed so cookies, local storage, the theme and the player prefs survive a relaunch; a custom scheme cannot be used, because Chromium keeps no `document.cookie` there and the Supabase session lives in it. `localhost`, not `127.0.0.1`, keeps it a secure context. A request for another `Host` gets 421 (DNS rebinding), and the CSP's `connect-src` is `'self'` plus `https://*.supabase.co`.
- **`/api/*` goes to one fixed server.** The web host streams it both ways to `RAVEN_DESKTOP_SERVER_ORIGIN`, injected by `build:main` (an input of the Nx `build` target). Unset, it is `DEFAULT_SERVER_ORIGIN` (`libs/raven/core/src/desktop/webHost.ts`), raven's public origin `https://raven-player.synology.me:8443` (DSM's reverse proxy in front of raven), so every build reaches the web's server, accounts and viewing data at home or away. Set it, or the unpackaged hook, to `http://localhost:8484` to run against a local server. `fixedServerFrom` (`src/main/origins.ts`) gives the default server the web app's Netlify site as a built-in alias (`DEFAULT_LINK_ORIGINS`), since its watch pages build `raven://` links naming `window.location.origin`; `RAVEN_DESKTOP_LINK_ORIGINS` (comma separated) adds more. An unreachable upstream is a 502 `{"error":"server_unreachable"}` (`WEB_HOST_ERRORS`); the page also reads a 502, 503 or 504 with a non-JSON body (Netlify's or DSM's proxy in front of a down raven) as unreachable (`isUnreachableAnswer`), and shows the offline shell: Downloads, On this Mac, `/play/:fileId` and Settings, nothing that needs the server.
- **Sign-in is the web's own.** The page signs in to Supabase (`stores/authSession.ts`) and sends its session to main as an `accountToken` request (`isPageSession`: the access token and the account id). Main holds it in memory (`src/main/accounts/pageAccount.ts`), checks that the token's `sub` names that account and never writes a token, so a relaunch waits for the page to send it again. Main uses it as the Bearer on its own calls to the server: tickets, the relay, downloads, syncing plays. `lastAccountId` in `desktop-config.json` outlives a sign out, so what is played before the page signs in again waits for that account.
- **The PIN is asked for only when the owner presses Unlock,** on the web's pages (which Raven shows) and in the device app (`apps/raven/app/CLAUDE.md`, "A locked library offers the owner its Unlock"). `LockedLibrary` gives the owner an Unlock button when `GET /api/lock` says `available` (the owner, with `LIBRARY_PIN` set); a member or an unset PIN gets only the message. Nothing opens the PIN pad (`PinPadDialog`) on its own: not a locked page, not a refused request, not a relock. Elsewhere a locked library stays unavailable and its title is refused (`TITLE_REFUSALS.locked`) with a message. Main still reads the page's `raven_unlock` cookie from its cookie jar on every call of its own (`src/main/servers/pageUnlock.ts`) and forwards it when one is there, so an unlock entered on the page holds for main's calls. There is no unlock request of main's own.
- **Desktop-only web UI lives in `apps/raven/web/src/desktop/`,** active only when `window.ravenDesktop` passes `isRavenDesktopBridge` (`startDesktop.ts` puts it in `stores/desktop.ts`); in a browser it renders nothing. It holds Downloads (`/downloads`), On this Mac (`/local`: local files, drag and drop, recents), `/play/:fileId`, the download dialog, Open Link, the Settings sections (Downloads, This computer for audio output, Updates), the update toast and the offline shell. New desktop-only UI goes there; a shared page branches on `useIsDesktop` or `useDesktopBridge`, never on the user agent. The downloads' pages there (Downloads, the dialog, Settings' Downloads section) are the exception that a browser shows too: they read the downloads host (above), not the bridge.
- **The bridge contract lives in `@raven/core`** (`libs/raven/core/src/desktop/`: `protocol.ts`, `bridge.ts`, `webHost.ts`), shared by web and desktop. The preload exposes `window.ravenDesktop` only on `PAGE_ORIGIN`, and main acts only on a request that `isDesktopRequest` accepts. No variant carries a path or names a server: main owns file paths, the server, the network and mpv, and the page holds only ids (a granted `fileId`, a media id, a `downloadId`). The player talks to main over one MessagePort, and main acts only on a `PlayerCommand` that `isPlayerCommand` accepts.
- **Every title plays in mpv.** The web `WatchPage` renders `DesktopWatch` inside the app, which asks main for `playTitle`: a ready download as a granted file, else the server's title once its first account ticket says the account may play it, else a `titleRefused` with a `TITLE_REFUSALS` reason (signed out, denied, locked, gone, unreachable). A server title's progress and plays are the page's own `/api` calls through the web host. A download's are main's, held for sync (below). The html engine (`RAVEN_DESKTOP_MPV=off`, or a file Chromium plays when mpv is unavailable) is the fallback for local files only.
- **Music plays in a second mpv.** `attachMusicPlayer` (`src/main/player/audioPlayer.ts`) opens an `audio` surface (`vo=null`, `vid=no`, `gapless-audio`) beside the window's video engine and hands each page load a port of its own (`IPC_CHANNELS.audio`, `WINDOW_MESSAGE_TYPES.audioPort`), driven by `AudioCommand`s (`libs/raven/core/src/audioPlayer.ts`) the page's `DesktopAudioHost` (`apps/raven/web/src/desktop/audio`) sends from the shared `audioQueue` store. The queue stays on the page: main's `audioService` hears the playing track and the one after it, keeps both in mpv's playlist so they run together, and sends `advanced` when mpv moved on by itself. Tracks go through a music relay of their own (`capacity: 2`), so a video and a track never retire each other's secrets. The addon owns macOS's Now Playing and transport controls (`nowplaying_mac.mm`, MediaPlayer.framework; the page sends the cover's bytes), with Chromium's `HardwareMediaKeyHandling` and `MediaSessionService` switched off in `main.ts`; `nowplaying_win.cpp` is a no-op. Without the engine (`RAVEN_DESKTOP_MPV=off`, or mpv failing) the page plays music through its own `<audio>` host. Playing music holds `prevent-app-suspension`, never the display. mpv's replaygain is off: each `loadfile` carries its own `af` (`soundFilterOf`: the page's levelling factor as dB, then the ten EQ bands), so a queued track starts at its level from its first note; Raven's mpv does not crossfade.
- **Server titles play through a loopback relay.** mpv opens `http://127.0.0.1:<port>/<secret>/file`, never the server's address. Away from home (the picked origin is `public`, or none answers and `remote.isOutside`) a video whose bitrate is over `remote.limit` plays as the server's HLS transcode instead (`serverSources.ts`: `originPicks.placeOf` gives the origin and `remote`, `getMedia` the bitrate, asked only when core's `remoteLimitApplies`, and core's `remoteTranscodeFor` the size the master's URL must name, which the server holds it to anyway): mpv opens `<secret>/hls/master.m3u8`, the relay asks the master with a ticket and `?mode=transcode&quality=`, rewrites each playlist to its own names (`video.m3u8`, `init.mp4`, `segment/<n>.m4s`; `servers/hlsRelay.ts`), drops the subtitle renditions (sidecars stay as for a file) and asks the session's parts with the session's key, which never reaches mpv; a session the server lost (`404` or `401`) is reopened from the master once (`servers/hlsSessions.ts`, which owns the sessions). Only the server's own tags pass (`HLS_TAGS`), comments are dropped, and a URI may stand only as a segment or variant line or as the one `URI="..."` of `#EXT-X-MAP`; a playlist with any other URI (a second attribute, another tag, other quoting or case, another host, session or media) is refused whole, a 502. Music and downloads keep the original file. The relay (`src/main/servers/mediaRelay.ts`) forwards only GET and HEAD, with the `Range`, with an account ticket from `accountTickets.ts`, so every seek, reconnect and sidecar gets a live ticket and no ticket, token or cookie enters an mpv URL, header or log. It fetches from the media origin `originPicks.ts` picks (the downloads' own pick: `getMediaOrigins` probed and `pickOrigin`ed, held `PICK_FRESH_MS`, let go of when a title fails, a download meets an outage or the Mac wakes), or the server's own address when none is listed or answers; a picked origin that fails to connect, or gives no answer in `ORIGIN_ANSWER_MS` (5 s), gives way to the server's own address for the rest of the load. A ticket is reused for 240 s (`ACCOUNT_TICKET_RENEW_MS`, under the server's five minutes), then minted again, and a `401` mints once more and repeats. A refusal (`403`, or a second `401`) is read off the relay, not off mpv, which ends such a file as a plain eof; it surfaces as an `account` player error. The secret is 43 characters, per load, retired when the title leaves the screen; the page never learns the relay's port.
- **Main's own server calls are an allowlist.** `src/main/servers/allowlist.ts` has eleven calls (`getMedia`, `getTracks`, `saveProgress`, `recordPlay`, `getItem`, `getLibrary`, `getSagas`, `getAlbum`, `getPlaylist`, `getMediaOrigins`, `getAccountTicket`), each built from its fields alone with the page's Bearer and unlock cookie; main refuses and logs the rest.
- **`raven://play` and `raven://download` links are accepted only for the fixed origin or an alias (for the default server, also the web app's Netlify site)** (`namesServer` in `desktopConfig.ts`, `servers/linkOpener.ts`); any other server's link is refused. A play link navigates the page to `/watch/<id>` (with its `WATCH_PARAMS`), a download link asks for the download.
- **Config is version 5** (`desktop-config.json`): the output settings, the update settings, `lastAccountId` and one `server` (`{ id, origin }`, the id being what the downloads are filed under). Versions 1 to 4 upgrade on read: a version 2 to 4 server whose origin matches the fixed origin or an alias is adopted with its downloads (`downloads/adopt.ts` moves their folders under the one id), and any other is dropped. A build that names another origin keeps the server's id and `lastAccountId` and writes only the new origin, so no download moves. An older Raven's per-server partitions and `userData/accounts` are removed at launch. A version 5 install naming the Netlify origin keeps its id, `lastAccountId` and downloads, and only its origin is rewritten.
- **Test hooks are read only unpackaged** (`app.isPackaged` false): `RAVEN_DESKTOP_USER_DATA` (a throwaway profile), `RAVEN_DESKTOP_MPV` (`headless` runs mpv with no video or audio output for e2e, `off` leaves the html engine), `RAVEN_DESKTOP_SERVER_ORIGIN` and `RAVEN_DESKTOP_LINK_ORIGINS` (replace the built values), `RAVEN_DESKTOP_AUTH_ORIGIN` (another Supabase Auth origin the CSP lets the page call: e2e's fake Auth on `127.0.0.1`), `RAVEN_DESKTOP_RELEASES_URL` (the release check's URL, and the only way an unpackaged launch checks at all), `RAVEN_DESKTOP_BUDGET_MS` (shortens the budget windows) and `RAVEN_DESKTOP_SYNC_RETRY_MS` (shortens the five-minute retry that sends the downloads' plays and positions to the server: a whole number of milliseconds from 100 to 300000, anything else ignored). A packaged app reads none of them. e2e (`apps/raven/desktop/e2e`) drives the real web pages against a fixture server and that fake Auth.
- **Downloads live in `src/main/downloads`,** wired by `downloadService.ts`. On disk they are `userData/downloads/<serverId>/<mediaId>/video.<container>`, or `media.<container>` for an audio container (`mediaPathFor`; `.part` while it downloads) with `subtitles/<trackId>.vtt` beside it, and their state is `userData/downloads.json`. Paths come from the path builders in `space.ts`, which refuse an id, container or track id their guards do not pass; the launch sweep joins only folder names that pass the same guards. A download fetches with an account ticket (`mediaAccess.ts`) from the media origin `servers/originPicks.ts` picks (shared with the relay), or from the server's own address when none answers: a fresh ticket per fetch run, shared by the file and its subtitles, which download first. The server's downloads mint at most 16 in any five minutes (`DOWNLOAD_MINTS`, a ticket's life), so a queue never uses up the account's 32 live tickets, and a run past that waits, abandonably. A `401` resumes from the bytes on disk with a new ticket once, and so does a response the server cuts after the fetch wrote bytes; a cut with no new bytes is an outage. A second `401`, a `403` or a refused mint fails the file and its queued group-mates with the account copy, and a sign out ends the running ones the same way (`accessEnded`). A ticket never reaches `downloads.json`, the page or the log. An album or a playlist (`expand.ts`, through `getAlbum` or `getPlaylist`) downloads each track's original file, in disc or playlist order, under an `album:<id>` or `playlist:<id>` group that carries the album cover Downloads shows (a playlist's first track's); a track held twice is fetched once, and one already downloaded stays in the group it came with.
- **A download keeps its pictures and its library.** Each entry in `downloads.json` carries, beside `artwork` and `facts`, its `library` (`{ id, name, isPrivate }`, private when the server's `settings.locked` holds it behind the PIN), its `titleItemId` (the item whose art it wears: its show's for an episode, its own for a movie, core's `artItemIdOf`) and its `pictures`; all three are optional, so the file needs no new version. `downloads/pictures.ts` saves a title's poster and title art, and an album's cover, under `userData/downloads/<serverId>/pictures/<item-or-album>/<pictureId>.<ext>` (`item-<id>` or `album-<id>`, `picturePathFor` in `space.ts`), once for every download that shares them, at the versions `getItem` or `getAlbum` names now, with a bare fetch of the capability address on the server's own origin (no cookie, ticket or Bearer: the version is the key). A fill runs at launch, after a confirmation, when the page lists its downloads and when the account changes; it asks nothing while the page is signed out and ends when the server does not answer. A picture that fails never fails a download: its entry stays not `isComplete` and the next fill asks again. An entry from before is filed the same way first (`getMedia`, then `getLibrary`), and until then its `library` is null. A title's folder goes with its last download (`pictures.sweep` after a removal and at launch). The page reads a saved picture as `raven-picture://<pictureId>` (core's `PICTURE_SCHEME`, `pictureUrlFor`; `pictureProtocol.ts`), an opaque id main gave it, so no path or origin crosses; the CSP names the scheme in `img-src`.
- **The Downloads page shows progress, pictures and a Watch grid.** A `DownloadView` carries `artwork` (a title's poster or an album's cover as ids and a version, or none; the page builds the capability address itself, so no origin or path crosses), `pictures` (`{ art, logo }`, the ids of the poster or cover and the title art saved on disk, each null until saved), `library` (null until known), `facts` (year, score, bitrate, pixels, added and changed: what a library sorts on) and `createdAt`. Main keeps `artwork` and `facts` on each entry in `downloads.json` from the file it expanded (core's `desktop/downloadTitles.ts`, which files a title, its group, labels, order, pictures and facts, the same for every host that keeps downloads); an entry written before they existed has neither and reads as `none` and as facts dated by `createdAt`, so the file needs no new version. A show's or season's files share its poster; a movie, an episode or a saga's film shows its own; an album's or playlist's tracks share its cover (`coverOf`). The Watch grid holds videos only, since a track plays in the music queue. Speed is not main's: the page reads bytes a second off the bytes main reports between its progress events (`stores/downloadSpeeds.ts`, `desktop/downloadSpeed.ts`), smoothed, and shows none once a download has been quiet for 3 s. The page has two tabs, Manage (the list) and Watch (a grid of every download, sortable by every field of `SORT_FIELD_NAMES`, sorted by `desktop/DownloadsPage/sortDownloads.ts`). A row, a tile and an album's head show the saved picture first and fall back to `artwork`'s address (`DownloadArtwork`); a video group's heading is its saved title art when all its files share one, and the player's header draws a download's from `LocalFile.logo`, so both are there offline. One Show choice for both tabs (`stores/downloadsShow.ts`, kept across visits) lays the downloads out all together or a section a library, by name, those with no known library last under "Other" (`DownloadsPage/libraries.ts`), in the device app's words. A private library's downloads are left out of the lists and every count unless `GET /api/lock` says `unlocked` (`useDownloadsUnlocked`): hidden while it is locked, on its way, or out of reach with no earlier answer, with one line saying some are hidden; nothing there opens the PIN pad, and the side menu's badge still counts them.
- **Plays follow their account.** `downloads.json` is version 2: each entry's pending play carries `accountId` (`null` for a version 1 file, which `upgradeDownloads` reads as before accounts), and `owed` plays are kept per title and account. A play is tagged with the account signed in when its title was opened, else `lastAccountId` (`playback.ts`'s sittings), so a title left open while another account signs in sends its later positions and its close only to the account that opened it, through `owed`. `sync.ts` sends an item only when its `accountId` is `null` or the account now signed in, checks again before every call, and `ServerCalls` verifies the token's own `sub` against the item's account, so one account's play never goes out under another's token. When the account changes (`accountSwitches`), `downloadService.accountSwitched` moves the other accounts' pending plays to `owed` and syncs what the incoming account is owed.
- **Never build libmpv or the addon without the toolchain.** `fetch:libmpv` and `build:native` need the pinned sources, Xcode's Metal toolchain and `native-build/prefix`; CI builds them (`.github/actions/raven-desktop-native`). Locally, use the CI-built `libs/raven/mpv/resources/darwin-arm64` (gitignored). `stage:mpv` copies the running machine's target (`darwin-arm64` or `win32-x64`) into `staging/mpv/<target>` for `package` and `make`, clearing `staging/mpv` first so one target ships, and fails when one of its binaries is missing. `build` also needs `@raven/web`'s build (an Nx dependency), which `package` and `make` copy into the app's resources and the web host serves.
- **The Windows libmpv is a pinned prebuilt.** `libs/raven/mpv/native/windows.lock.json` names one mpv-winbuild-cmake release archive by digest; `fetch:libmpv:windows` places `libmpv-2.dll` and its headers under `libs/raven/mpv/resources/win32-x64` and `audit:native:windows` checks the DLL (digest, x64, imports, exports) and the addon beside it. Change the lock, never the files; CI's `🪟 Windows native` job proves a new pin.
- **The window's chrome follows the platform.** `windowChromeFor` (`libs/raven/core/src/desktop/bridge.ts`) says who draws the window's controls: `inset` on macOS (`hiddenInset`, the traffic lights over the page) and `drawn` on Windows, where the window is frameless and the page draws its controls. Both windows are `transparent` from the start so mpv's video shows under the page: a macOS window made opaque and only cleared with `setBackgroundColor` leaves ghosts of whatever moves over the video, the scrubber's head first. On Windows the page draws minimize, maximize and close (`apps/raven/web/src/desktop/WindowControls`) and sends a `windowControl` request. The bridge carries one fact, `platform` (`DESKTOP_PLATFORMS`, from `desktopPlatformFor`, which the preload and main both call on `process.platform`), and everything else is derived from it: main makes the window from its chrome (`chromeOptionsFor`, `src/main/windowChrome.ts`), the page draws the controls and marks `:root[data-desktop]` with the chrome (`inset` or `drawn`), and the copy names the computer from `COMPUTER_NAMES` (`useComputerName`), so "On this Mac" reads "On this PC" on Windows. The page's controls hide with the player's (`useWindowChrome`, fed by the player services' `chrome.shown`), as the traffic lights do.
- **One addon, a surface per platform.** `libs/raven/mpv/native/addon.cpp` is shared; `surface_mac.mm` puts a CAMetalLayer under Chromium's content view, and `surface_win.cpp` hands mpv the BrowserWindow's HWND with `gpu-api=d3d11`, under which mpv makes its own child window that Chromium's transparent output composites over. `build:native:windows` compiles it with MSVC against an import library made from the DLL's export list. `nativeTargetOf` (`@raven/mpv`) names the build a process can load.
- **Main follows the platform too.** `main.ts` reads `platform` and `nativeTarget` (`nativeTargetOf`, `@raven/mpv`) once and passes them down: mpv's audio output is `coreaudio` and `avfoundation` on macOS and `wasapi` on Windows (`outputOptions`), the addon is `resources/mpv/<target>` (`addonPathFor`, which throws where raven has no build), the update check wants the target's asset (`appAssetNameFor`: the arm64 dmg, or `raven-player-<version>-x64-setup.exe`), and the menu has an app menu on macOS only (`menuTemplate`; on Windows Settings, Check for Updates and Quit end File). macOS hands a `raven://` link to `open-url`; Windows passes it as an argument, at launch and through `second-instance`, which `linksFromArgv` picks out, and a packaged Windows app registers `LINK_SCHEME` itself, since Forge's `protocols` writes only the Info.plist.
- **Logs** go to `app.getPath('logs')`, which `logsDirFor` sets: `~/Library/Logs/raven` on macOS, `%APPDATA%\raven\logs` on Windows. They are `raven.log`, then `raven.log.1` to `raven.log.4`, 1 MiB each; crash dumps go to `<userData>/Crashpad` (`~/Library/Application Support/raven/Crashpad`, `%APPDATA%\raven\Crashpad`), never uploaded. Every line is redacted first: no cookie values, PINs, passwords, request bodies, file paths, file names, access or refresh tokens, `Authorization` headers, JWTs, account tickets or `?t=` parameters, relay secrets, or email addresses. A new log line goes through the log, never around it.
- **Packaging on Windows.** On Windows, `make` builds Squirrel's installer (`@electron-forge/maker-squirrel`, package id `raven`, Raven's `resources/icon.ico`) and a portable zip; the packaged app is `out/Raven-win32-x64/Raven.exe`, with the engine in `resources/mpv/win32-x64`. Squirrel runs the app with `--squirrel-install`, `--squirrel-updated`, `--squirrel-uninstall` or `--squirrel-obsolete` and waits for it to exit, so `main.ts` first takes `squirrelStepFor`'s step (`src/main/squirrel.ts`): it makes or removes the Start menu and desktop shortcuts through `Update.exe` and quits before anything starts. `electron-winstaller` is in the root `trustedDependencies`, since its install script places the `7z.exe` Squirrel packs with. `audit:bundle` reads every `.node` and `.dll` of the engine with `@raven/mpv`'s `readPe`: each is x64, the addon imports only Windows' DLLs, `libmpv-2.dll` and `node.exe`, and `libmpv-2.dll` has the lock's digest. `smoke:packaged` launches `Raven.exe`, reads `%APPDATA%\raven\logs`, finds a running Raven with `tasklist`, and asks it to quit with `taskkill` without `/F`, which posts WM_CLOSE, since Windows delivers no SIGTERM to a GUI app (`SMOKE_STOP_NAMES`). `release:assets` names the Windows assets `raven-player-<version>-x64-setup.exe` (Squirrel's `Raven-<version> Setup.exe`, renamed) and `raven-player-<version>-x64.zip`, with no sources tarball (the release notes name the pinned mpv-winbuild-cmake release instead) and no `SHA256SUMS` of its own; the setup exe's name is `appAssetNameFor`'s, which the update check looks for. CI's `🪟 Windows app` job makes, audits and smoke-tests it and uploads the unsigned installer; the packaged app passed that smoke on `windows-2025`. Windows has no `e2e`: the Playwright harness assumes macOS. The installer is unsigned, so SmartScreen warns on it.
- **Releases.** A pushed `vX.Y.Z` tag runs `release.yml` and `.github/workflows/desktop-release.yml` together; the desktop workflow has a macOS arm64 build and a Windows x64 build (`windows-2025`, which also runs the native tests), each of which builds, audits and smoke-tests the app and uploads its assets as its own artifact, and a `publish` job that needs both. It attaches `raven-player-<version>-arm64.dmg`, `raven-player-<version>-arm64.zip`, `raven-player-<version>-sources.tar.gz`, `raven-player-<version>-x64-setup.exe` and `raven-player-<version>-x64.zip` to the tag's release, and writes the one `SHA256SUMS` over all five itself, since two builds' own would collide. The sources tarball is macOS's (mpv's GPL and FFmpeg's LGPL source offer); the Windows build ships a prebuilt libmpv, and the install notes name its sources, the mpv-winbuild-cmake release `windows.lock.json` pins. A pull request that touches the release's files, or a dispatch from the Actions tab, is its dry run, which never publishes. The app is signed ad hoc: Developer ID signing and notarization are wired behind `RAVEN_SIGN_IDENTITY` and `RAVEN_NOTARIZE_PROFILE` and stay off, since no certificate exists, and no workflow sets them.

## App

`@raven/app` is raven on iPhone, iPad, Apple TV and Android TV: an Expo app on the `react-native-tvos` fork, with `expo-router`. Its design is `docs/superpowers/specs/2026-10-17-raven-device-apps-design.md`; `apps/raven/app/CLAUDE.md` holds its pins and toolchain.

- **One route tree, layouts by platform.** `app/` holds each route once, with no `(phone)/` or `(tv)/` groups. A route renders a screen from `src/screens/`, and a screen renders the `src/layouts/` components, whose index picks the touch or the focus variant from `Platform.isTV`, and the player's controls by platform, since Apple TV's and Android TV's differ. A screen never reads `Platform.isTV` itself.
- **jest for files that render a native component, bun for everything else, never both for one file.** bun cannot load React Native's Flow source, so a test that renders is `*.render.test.tsx` and runs under jest-expo (`test:screens`); every other test is `*.test.ts` under bun (`test`), which skips the render tests.
- **Polyfills load first.** Hermes has no `Intl.RelativeTimeFormat` or `Intl.DisplayNames`, which `@raven/core` builds at module scope, so `index.ts` imports `@raven/native/polyfills` before `expo-router/entry`, and so before anything that imports core. Core stays as it is: the polyfills are the platform's concern.
- **Tokens come from `@raven/ui/designTokens`.** `designTokens` (from `globals.scss`) and `themeTokens` (each theme's colours from `themes.scss`, through core's `parseThemes`) are plain data in the built entry; `@raven/native/headless`'s `nativeTokens` turns them into React Native values (a translucent `rgb()` as `rgba()`) and drops what React Native cannot express, and `src/theme/appTheme.ts` names each theme's palette the screens paint with.
- **A signed-in account plays by its ticket.** The player asks `getMediaTicket` with the Bearer, which is an account ticket under `ready`, and plays by it from the picked origin or the server's own address with no cookie or Bearer. An HLS master gets the session's capability and a direct file its ticket's pass, so a film outlives the ticket's five minutes; a source the server lets go of mid-play (a 401, 403, 404 or 423 the native player reports) is opened again from the spot, and a ticket the server refuses is the account's refusal in the app's words (`apps/raven/app/CLAUDE.md`, "Media goes by ticket" and "The ladder is a reducer").
- **The app calls a fixed list of routes.** `APP_CLIENT_CALLS` in `libs/raven/core/src/appClientCalls.ts`, enforced in the app's fetch and checked against the server's route marks by `apps/raven/server/src/appClients.test.ts`, so no unlisted write can slip in, and no `@AdminOnly()` route but the owner's `APP_OWNER_CALLS`, which only Settings' Admin sections call, for the account `GET /api/me` names the owner. The PIN's `unlock` and `lock` are listed (`@ForViewers()`; only the owner's PIN opens anything), so the owner sees every library in the app, a locked one marked, and unlocks it there on the web's pad.
- **The native folders are generated.** `ios/` and `android/` come from the `prebuild:*` scripts and are gitignored, as are the simulator builds in `build/`. Change the Expo config or a config plugin, never the generated projects.
- **iPhone and iPad download.** Movies, episodes, seasons, shows, albums and playlists download to the device (`apps/raven/app/CLAUDE.md`, "Downloads"), the original file or the server's MP4 copy, and play from it offline.
