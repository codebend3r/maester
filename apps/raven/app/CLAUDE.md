# Claude context for raven's device app

`@raven/app` is raven on iPhone, iPad, Apple TV and Android TV. The rules that apply to it are in the root `CLAUDE.md` and in `apps/raven/CLAUDE.md` ("App"); this file holds what only the app needs.

## Pins

- **`react-native` is `npm:react-native-tvos@0.88.0-0`.** The fork has no separate stable 0.88 tag: `0.88.0-0` is its stable release (npm's `latest` and `0.88-stable` tags point at it), the `-0` suffix is how the fork names every release, and its release candidates are `-0rcN`. Its peer is `react ^19.3.0`, so the app's React is the repo's `19.3.0`.
- **Expo is `58.0.23`.** Every other Expo package (`expo-keep-awake` `58.0.3` among them), and React Native's own (`react-native-screens`, `react-native-safe-area-context`, `@react-native-community/netinfo`), is pinned to the version Expo 58.0.23's `bundledNativeModules.json` names. `react-native-video` is `6.19.3`, the version the spike played HLS with. A bump moves them together: take the new Expo's list, never `expo install`'s ranges.
- **The root `package.json` overrides `react-native` to the fork for the whole workspace.** `react-native-reanimated`, `react-native-worklets` and `react-native-gesture-handler` arrive because bun installs the required peers of `expo-router`'s drawer (`react-native-drawer-layout`), and the first two take `react-native` `0.86 - 0.88`, a range that excludes a prerelease such as `0.88.0-0`. Without the override bun installs upstream React Native beside the fork. The override also pins gesture-handler to Expo 58.0.23's `3.3.0`, where the peer would otherwise float to the newest.
- **`react-native-video` 6.19.3 carries one patch** (seven changes: the PCM-only audio sink below; FFmpeg for the audio the TV cannot decode, audio tracks listed and picked across every audio renderer, and Dolby Vision profile 7's base layer, all three in Playing; a text track `index` that counts across the track groups; sideloaded `textTracks` merged into a file played as it is, which the library has ignored since 6.16.0; and a `color` and `fontFamily` on `subtitleStyle`, under which ExoPlayer's subtitle view drops each file's own styles; see Playing), `patches/react-native-video@6.19.3.patch` (bun's `patchedDependencies` in the root `package.json`, and an Nx input of every `prebuild:*` and `build:*` target): its `DefaultRenderersFactory` builds a `DefaultAudioSink` with `AudioCapabilities.DEFAULT_AUDIO_CAPABILITIES` and no context, so ExoPlayer decodes every audio track to PCM and never passes one through encoded. On the Google TV Streamer an E-AC-3 track passed through (its Dolby MSD audio path) reported a playback head 2^32 frames out, ExoPlayer logged `Spurious audio timestamp (frame position mismatch)` twice a second and discarded the audio clock, and the picture drifted from the sound; decoded by `c2.dolby.eac3.decoder` the clock held. The library offers no prop for the sink, and its plugin interface gets the player only once it is built. A bump of the library rewrites the patch, or drops it if the library learns to. bun applies the patch only as it installs the package, so a checkout that pulled a changed patch without `bun install` builds the old one: `check:patches` (`scripts/check_patches.sh`, uncached, which every `prebuild:*` depends on) fails the build unless git can take each patch in `patches/` back out of the installed files.
- **`expo-file-system` is `58.0.13` in both apps.** Wren and the device app each pin it, the version `expo` 58.0.23 asks (`~58.0.13`), so bun links one store folder for both and autolinking takes it. A bump of either app's Expo checks both again.
- **The app uses neither the drawer nor the JS stack**, so `expo.autolinking.exclude` in `package.json` keeps those three out of the native projects. They stay installed, since bun installs a package's required peers and the root has no way to skip one. `expo.autolinking.android.exclude` repeats them and adds `@raven/audio`: the platform's list replaces the shared one rather than adding to it, and Android TV plays music through `react-native-video`, so the TV APK carries no idle media service of `@raven/audio`'s and none of its permissions.

## Bun's package store

Bun links the workspace in isolated mode: each package sits in `node_modules/.bun/<name>@<version>/node_modules/<name>` and sees only what it declares. Two things in the store require `react-native` without declaring it, and find nothing there, because the fork's folder is named `react-native-tvos`:

- React Native's jest preset, loaded by jest-expo.
- The fork's own podspecs, which `require.resolve('react-native')` from inside the store during `pod install`.

So `test:screens` and the Apple prebuilds set `NODE_PATH=$PWD/node_modules`, the app's own `node_modules`, where `react-native` links to the fork. It is absolute because `pod install` runs in `ios/`.

`react-native-svg`'s podspec finds React Native's version by resolving `react-native` and reading `react-native/package.json` beside it; Node resolves the link to the fork's store folder, whose sibling is not named `react-native`, so the Apple prebuilds also set `REACT_NATIVE_NODE_MODULES_DIR=$PWD/node_modules`, the podspec's own fallback. Without it `pod install` fails with "no implicit conversion of nil into String".

The jest config in `package.json` also lets Babel through `node_modules/.bun`, as jest-expo's default lets pnpm's `.pnpm` through. Babel's output imports `@babel/runtime` from the app's own files, so the app depends on it directly.

## Intl and the shared layer

- **What Hermes has.** On the Apple TV simulator and the Android TV emulator, RN 0.88's Hermes has `Intl.getCanonicalLocales`, `NumberFormat`, `DateTimeFormat` and `Collator`, and they handle every option core passes. It has no `Locale`, `PluralRules`, `RelativeTimeFormat` or `DisplayNames`. So `@raven/native`'s `src/polyfills.ts` loads formatjs's `getcanonicallocales`, `locale`, `pluralrules`, `relativetimeformat` and `displaynames` with their `en` data, in that order, and no `numberformat` or `datetimeformat`.
- **Hermes has no `Array.prototype.toSorted`** (it has `toReversed`, `toSpliced` and `with`), and core sorts with it, so the same polyfills also install `installToSorted` (`libs/raven/native/src/arrayToSorted.ts`) where the engine lacks it. Opening a grouped library crashed the Release build without it; jest runs on Node, which has it, so only a build on a simulator shows such a gap.
- **`polyfill.js`, not `polyfill-force.js`.** Each entry installs itself only when the engine lacks the constructor or its English data, so a Hermes that gains one keeps its own, and nothing is applied twice.
- **The `.js` subpaths.** formatjs's package `exports` list each polyfill and locale file only with its `.js`. Without it Metro warns and falls back to the files, so `src/polyfills.ts` is exempt from the no-extension import rule in `@raven/native`'s `.oxlintrc.json`.
- **Metro reads `@raven/core` and `@raven/ui` through Bun's workspace links** to their built `dist`, so `start`, `test:screens` and the `prebuild:*` and `build:*` targets depend on `^build`, which builds both first (`app.config.ts` reads the launch colour from `@raven/ui/designTokens` too). Both are ES modules and `@raven/ui`'s peers resolve from its own `node_modules`, which link to the same store folders as the app's, so there is one React.

## Servers and sessions

- **The app holds each server's cookies, never the system.** Every call goes through `apiFor({ server, session })` (`@raven/native`, `libs/raven/native/src/servers/serverClient.ts`), whose fetch (`serverFetch.ts`) sends `credentials: 'omit'`. On iOS and tvOS that turns off `HTTPShouldHandleCookies`, and on Android OkHttp gets no cookie jar, so the shared store neither keeps nor sends anything. The app adds both of core's `SERVER_COOKIES` (`raven_unlock`, then `raven_admin`) from its own jar, whatever it holds (the owner's PIN unlock sets the first; no screen enters the admin password) and applies what `set-cookie` says back, both only for the server's own `/api/`, the cookies' path: a media origin never gets them, and a response a redirect took elsewhere (its `url`) sets nothing. React Native follows redirects natively with the headers it was given and has no `redirect: 'manual'`, so the request itself cannot be held back; raven's API never redirects.
- **Sign-in asks only what the web asks.** The account's email and password go to Supabase through the fixed raven server's public auth config, and sign-in ends there, going back down to Home (`dismissTo`) rather than stacking another screen. It never asks for the PIN or the admin password, on any build; the PIN is asked for only when the owner presses a locked library's Unlock (see "A locked library offers the owner its Unlock"). The app calls `unlockAdmin`, `unlock` and `lock` (all `@ForViewers()`), and the only routes it calls that the server keeps for the owner are core's `APP_OWNER_CALLS`, which Settings' Admin sections call only for the owner, authorized by the owner's Bearer alone (see Settings). An end to end build sets `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN` to its accountless fixture, which `pinRavenServer` then pins as the active server, so it opens straight on Home.
- **`set-cookie` arrives folded.** React Native hands several `Set-Cookie` headers over as one value joined with `, `, and an `Expires` date holds a comma too, so `readServerCookies` splits only at a comma followed by `name=`. A cookie with an empty value or `Max-Age=0` is cleared and leaves the jar; the last word on each one wins.
- **Everything that must last is in `expo-secure-store`.** Each server's cookies are one JSON value under `raven.cookie.<serverId>`; the server list and the active id are one JSON value under `raven.servers` (`libs/raven/native/src/servers/activeServerStore.ts`). Both are guarded when read. The keychain on Apple keeps them on tvOS too, where AsyncStorage's caches folder may be emptied, and the keystore keeps them on Android. Only the player prefs, Settings' prefs (`useAppPrefs`) and the library views (`useLibraryViews`) are in AsyncStorage. `AppRoot` loads every store before any route renders.
- **A failing keychain degrades, never fails.** A store call that throws reads as empty and saves nothing, so the app works for the run and forgets on relaunch.
- **Simulator builds are signed ad hoc.** The keychain refuses an app with no signature ("A required entitlement is not present"), so `build:ios` and `build:tvos` pass `CODE_SIGN_IDENTITY=-` rather than turning signing off.
- **The fixed server id names its secure-store keys.** `RAVEN_SERVER` keeps one valid UUID for the server list and cookie jar, so its cookies survive a relaunch. Both a real build and an end to end build pin that server while stores load.
- **The jar's changes take turns per server.** Two responses that set cookies at once each read what the one before left, so neither writes over the other.
- **Plain http is for the development variant.** `APP_VARIANT=development` at prebuild sets `NSAllowsLocalNetworking` and Android's `usesCleartextTraffic`. Expo's template allows local networking in every build, so `app.config.ts` writes the whole `NSAppTransportSecurity` dictionary, which a release build keeps strict. Debug builds against Metro need the development variant too. The fixture build also sets `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN=http://127.0.0.1:8490`, which Expo writes into its bundle.
- **A form's buttons take a tone,** the web's `Button` tones: `primary` for the one action a step is for, `quiet` (a moss fill) for another way on, `ghost` (no fill) for a way out. Focus turns any button's edge to the text colour, drawn twice as thick on a TV (`SIZES.tvFocusRing`). Every control has the web's `--radius-md`; tvOS draws a focused text field as its own pill-shaped plate, so the TV field clips it to that radius. Android's text input pads itself top and bottom, so the TV field sets its own and lines up with the plate buttons beside it, its 1 pt edge aside.
- **Menu on tvOS's keyboard cancels the edit.** The native field goes back to what it held, but React Native reported every key as it was typed and reports nothing on the cancel, so the TV field takes the text it ends editing with (`onEndEditing`) as the field's value: what it shows is what Continue sends. Sign-in's fields and the search box are one TV field, `TvTextField` (`src/layouts/tvControls.tsx`).
- **React Native prop values are written inline** (`behavior="padding"`, `returnKeyType="go"`): each prop's own union type checks them, as an `as const` object would.

## Queries, pictures and events

- **One query client for the app's life, emptied on a server switch and on a change of account.** `AppRoot`'s `forgetAccount` runs `@raven/native`'s `forgetOnAccountChange`, as Wren does: whenever the signed-in account's id changes, signing out included, it clears the cache and the music queue and asks the downloads' `keepFor`, so the next account never sees what the last one read; a renewed token is the same account and keeps all of it. `AppRoot` wraps the routes in `QueryClientProvider` with headless `createQueryClient()`, and `clearOnServerSwitch` (`src/queries/serverCache.ts`) calls `clear()` from inside zustand's `set` whenever the active id changes, before React renders again. Every server answers under the same keys, so this is what keeps one server's answers off another's screen. A client keyed per server would remount the navigator on the activation in the middle of sign-in. TanStack binds each `useQuery` observer to the client it first saw, so a screen that reads a server reads it through `useAppQueries()`, which re-renders it on a switch and builds fresh queries; Home also keys its body on the server id.
- **`useAppQueries()`** (`src/queries/useAppQueries.ts`) gives the active server's `api`, `ravenQueriesFor(api)` and `useServerEvents`, made once per server (`@raven/native/headless`'s `lastPerServer`). The folder is `queries/`, not `data/`: the root `.gitignore` ignores every `data/`, raven's `DATA_DIR`.
- **A locked library offers the owner its Unlock, and nothing else asks.** The server lists a locked library to the owner (to a member it is not there at all, a 404), so Home, `/libraries` and both side menus show the owner every library (the server's search leaves every locked library out, for the web as well); a locked one wears a lock after its name in the side menus (`MenuLibrary['isLocked']`, read out "Films, locked") and "Movies · Locked" on `/libraries` (`LIBRARY_LIST_COPY`). `/library/[id]` asks headless `lockQuery` (`queryKeys.lock`, `GET /api/lock`) only when the library is locked, and headless `lockState` (`@raven/ui/headless`, `libs/raven/ui/src/lib/libraryLock.ts`, the one rule the web and the app share, tested under bun) says `open`, `checking` (the loading mark) or `shut`. Shut, `LockedLibrary` (`src/screens/LockedLibrary.tsx`) stands in place of the pages, a music library's too: the library's name, the layouts' `LockedNotice` (the lock, "Films is locked.", and an Unlock button only when the lock says `available`) and, once Unlock is pressed, the layouts' `PinPad` (`src/layouts/Lock.tsx`, sized per platform by `lockKitFor`: `touchLock`, `focusLock`), a React Native `Modal` holding the web's `PinPadDialog`: the title and hint, the digits as dots, 1 to 9 in rows of three over Backspace, 0 and Unlock as big round keys a finger presses and the remote moves through, the server's refusal of a wrong PIN as it said it (the digits cleared, a new press clearing the refusal), and Cancel. A right PIN closes the pad, keeps the lock's answer under `queryKeys.lock` and invalidates every query, which read again with the `raven_unlock` cookie the unlock's `set-cookie` left in the jar. An open locked library's pages carry the web header's Lock (`RelockButton`, a `ToolButton` that `PageTools` in `src/screens/PageTools.tsx` puts last in every page's toolbar, the music pages' included: each page's grid renders `toolbar={<PageTools frame={frame}>{its own buttons}</PageTools>}` over one `PageFrame`, the page open, the pages, their names and icons, the press between them, the library and the client, so no page threads buttons down as JSX), which calls `lock`, keeps its answer and invalidates every query, so the page shows the lock again. A 423 anywhere else (an item, the player) is that screen's error as any other is, with no unlock prompt.
- **Pictures are React Native's `Image` with the server's cookies.** Posters, backdrops and thumbnails are on the API (`PrivateBy`, not the media plane), so a locked library's need the cookie, and `cookieHeadersFor` adds it for the server's own `/api/` only. `expo-image` would add a native module for caching the versioned URLs do not need yet.
- **The jar says what it holds.** Every read from the store and every write or forget notes the server's cookies in `useCookieSnapshots` (`libs/raven/native/src/stores/cookieSnapshots.ts`, `noteCookies`; `unlockNow` reads it outside a render), and a write or forget also bumps `useCookieVersion` (`stores/cookieVersion.ts`). `useServerCookies` is a selector over the snapshots that reads the jar it is handed once and again on each bump, so pictures carry a new unlock cookie at once, and `@raven/native`'s `useServerUnlock({ serverId })` is `useServerCookies` read through `isUnlockedBy`, for the PIN unlock alone. A card remembers which picture and headers failed, so new headers ask again.
- **Server events ride `react-native-sse`**, adapted to headless `ServerEventSource` by `eventSourceFor` (`libs/raven/native/src/servers/eventSource.ts`). It opens once the jar has read the cookies and passes them as headers. The library retries only an error status, never a refused or reset connection, so the adapter reopens after every `error` itself (1 s, doubling to 30 s, back to 1 s only once a connection has held for 5 s, so a proxy that accepts and resets each one is not asked every second), closes in the background and opens again on return (telling headless it dropped, so it reads everything again), and keeps the stream through `inactive` (Control Center, a call), which is not the background, and never holds two connections or any after `close`. The library's XHR keeps React Native's default `withCredentials = true`, so the system jar is consulted for the stream; it stays empty, since every other request omits credentials and `/api/events` sets no cookie. `AppRoot` mounts the stream once per active server, so a spot, mark or binge change made on another device (or the web) reads Home, the listings and the binge list again here at once (apps/raven/CLAUDE.md, "The event stream").
- **A library has two pages, and a movie library a third.** `/library/[id]` (`LibraryPages` in `src/screens/Library.tsx`) opens on Continue watching, the library's own `GET /api/libraries/:id/in-progress` as wide cards like Home's shelf (`continueSectionsOf`), while anything in it is in progress, so a show is picked up in one press; with nothing in progress, or handed a search (`?q=`), it opens on the library itself, the listing sorted, laid out and searched as before. One `ToolButton` first in the toolbar, named for where it goes ("Library", "Continue watching"), is the press between them; the choice lasts while the page is open. Both pages wear the library's icon beside its name (`GridProps['icon']`, `libraryIconOf`, the same the side menu's pinned row wears). A library matched to movies (`hasSagas`, core's `matchTypeFor`, as the web's Sagas tab is) also has Sagas (`SagasGrid`, `src/screens/LibrarySagas.tsx`): its `GET /api/libraries/:id/sagas` as poster cards (the first movie's, the name, "2 movies, 2002 to 2026", `sagaCard` in `src/queries/sagaCards.ts`), each opening `/saga/[id]?library=` (`Saga`, `src/screens/Saga.tsx`), the saga's movies as a `Grid` of posters, oldest first, with Play all. Play all plays the first movie not yet watched in the saga's session (`sagaPlayTarget`: `?session=saga&scope=<tmdbId>` on the play route), so the player's Next walks the saga. The pages' buttons are one `ToolButton` to each of the other pages (`PageToggles`).
- **A library's Shuffle is a queue.** `shuffleDeal` (`src/screens/shuffleDeal.ts`) deals the library's videos into `useVideoQueue` (`src/stores/videoQueue.ts`, for the run) and plays the first in the `queue` session. There the player asks the server nothing: its Next (and autoplay at the end) is the video after this one in the queue and the back-to-the-start button plays the one before (`PlayerChromeProps['previous']`, `queueNeighbourOf`), each in this video's place, so going forward and back never loses the deal; a new Shuffle deals again.
- **A library's sort, view and grouping are this device's.** The web saves a viewer's change to the server (`PUT /api/libraries/:id/view`, `@ForViewers()`) for everyone, but that write is not one of the spec's, so `APP_CLIENT_CALLS` leaves it out. `useLibraryViews` (`src/stores/libraryViews.ts`) keeps a choice per server and library in AsyncStorage, guarded when read; the screen lays it over the server's settings and passes both through core's `coherentSettings`, so a choice the library's type cannot show gives way to its own.
- **Pickers are the platform's.** Touch screens (only iPhones and iPads) use `ActionSheetIOS`, a popover anchored on the chip on an iPad; tvOS has none (React Native builds `RCTActionSheetManager` out of it), so TVs use a `Modal` list with focus on the current option, closed by Menu or Back.
- **Every toolbar chip wears an icon, and under the thumb most wear only that.** `ToolButtonProps` and `PickerProps` take a required `icon` (an `IconName`, the web's drawing for the same control: shuffle, history and libraries for the page toggle, ascending or descending for the sort direction, the view's own icon for View, grouped for Group by, disc, music and list for the music pages), drawn by `Icon` in the text colour (`isOverPicture`'s on-picture colour over the video), decorative, with the chip's spoken label unchanged. The TV's `PlateButton` takes `text` and `icon` together for the same. On an iPhone or iPad every chip is one `Chip` (`src/layouts/Chip.touch.tsx`: `icon`, the spoken `label`, `text` or null for the icon alone in a square a finger wide, `lead` for a picker's muted word, `isOn`, `isDisabled`, `isOverPicture`), and the rule is the kit's, not each screen's: the touch `ToolButton` is always its icon alone (`text: null`), so Shuffle, the sort direction, the page toggles, Lock, Play all, Rename, Delete, Up and Remove show no words, the spoken label unchanged, so VoiceOver still says "Shuffle Films"; a `Picker` shows its word and its value unless `isIconOnly`, which View, Group by and Downloads' Show pass and Sort and Speed do not; a button that needs its words, Now Playing's Clear and its queue rows' Remove, is a `Chip` with `text` of its own. A library's toolbar runs page toggles, Shuffle, Sort, direction, View, Group by, then Lock last; the album page's actions are one row of `IconPlate`s (Play filled, then Shuffle, Play next, Add to queue, Add to playlist, Favourite and Download, each filled while on), and the touch `FavouriteButton`, the artist page's too, is that `IconPlate`.
- **A TV's library page is compact.** `Grid.focus` lays the Home plate and the page's buttons (the page toggles, Shuffle, Sort and its direction, View, Group by) along one top row, the buttons a `FocusBand` of their own; the library's name, its line and the jump strip share the next row; a library's own search box is the touch layout's alone, since a TV searches from Home. In the grid a poster (a show or a film) is its picture alone, its title said aloud (`hasCaptionOf`; `FocusCard`'s `hasCaption`), while a still or an album's cover keeps its words, and the cards are sized so the grid size's rows and a glimpse of the next fit the list's height (`cardWidthForRows`): a Size picker the grid adds to the toolbar wherever it lays out cards (`GRID_SIZE_FITS`) offers Small (three rows, at most a shelf's width), Medium (two, half again a shelf's, the default) and Large (one, half again Medium's), one choice for every grid on this device (`useAppPrefs`' `gridSize`). The line says what the library holds without its type, which its name says: a library of shows counts its shows once they are read, any other its videos, Continue watching its videos in progress, Sagas its sagas.
- **The TV side menu is folded unless pinned.** Home's `SideMenu` stands at its icons, drawn over the page's left edge (the page keeps `useSideMenuRoom` for it), and opens over the page with every label while the remote is on one of its rows (`useSideMenu`'s `hasFocus`, which waits `LEAVE_MS` before folding so moving from row to row keeps it open). Open, a long label takes two lines and the row the remote is on shows its label whole. The foot's toggle pins it open beside the page, kept on this device under `SIDE_MENU_KEY`, which names the pin, so every TV started folded once. Its rows are Search, Continue watching and Libraries, the pinned libraries, then Settings, the theme and the toggle; Continue watching, Libraries and Settings are an `OpenerRow`, which remembers itself as it is pressed, so Back from the screen it opened lands on it.
- **A list on a TV needs a height of its own.** The fork wraps a `FlatList`'s ScrollView in a `TVFocusGuideView` that takes no style, so `flex: 1` never reaches it and the list draws 1 pt tall. `Grid.focus` measures the room under its header and draws the list only once it has it, which also lets the first card mount asking for the focus and take it.
- **Moving the remote's focus on purpose.** `hasTVPreferredFocus` on a view that mounts asks before the view is in the window, and the fork's retry for that takes only the first time, so a card a jump lands on calls `requestTVFocus()` once mounted (`src/layouts/tvFocus.ts`, a guard, since the fork adds the method outside React Native's types). It does so once per jump: `useJumpFocus` asks only for a jump count newer than the grid's handled one, so the card never pulls the focus back as it mounts again (scrolled back to, its bucket reopened, a new sort). A view the remote must start on as it mounts (a form step's first field, the search screen's field, the player's catcher) also asks once mounted, through `useFocusOnMount` (`src/layouts/focus.ts`): on Android TV `hasTVPreferredFocus` alone left a sign-in step with nothing focused. Preferred focus is for the opening only, until anything on the screen has had the focus (a card, or a control in the header, whose focus bubbles up to it), so a card drawn later, after a sort, once a search finds some, or when Home's shelves are read again, leaves the viewer where they are.
- **One screen's focus is one store.** Each TV screen's opening focus and its opener live in `useScreenFocus` (`src/stores/screenFocus.ts`), by the route's key (`useRoute().key`), since the layout and every card on the screen read them. `src/layouts/focus.ts` holds the hooks: the screen's outermost focus layout (`Shelves`, `Grid`, `ItemLayout`, `SearchLayout`, `SettingsPage`) takes `useScreenFocusScope()` once, which gives its `isOpening` and `settle` and forgets the screen with the layout; a part inside it (each `Shelf`) reads `useOpeningFocus()`.
- **Going back lands on the card that opened the screen.** A `FocusCard` or a grid's `RowCard` calls `useOpenerFocus`'s `remember` as it is pressed, under its `place`, unique on the screen: the card's key in a grid or on an item page, the shelf's key and the card's on a shelf, since one title can sit under Continue watching and on its library's shelf. When the screen comes back to the front (`useIsFocused` turning true, never on a mount), the card remembered calls `requestTVFocus()` once. The opener lasts through the one cover its card opened: the next time another screen covers this one, the screen's scope (`coverScreen`) lets go of an opener no card took, so a later return from a screen no card opened (Search, See all, Play) asks for nothing, whatever order the cards and the scope hear the return in. tvOS restores the focus to the view that had it when a native stack screen comes back (`restoresFocusAfterTransition`), and the request agrees with it; it is what still lands on the card when its view mounted afresh while the screen was covered (its shelf or bucket drawn again) and what Android TV, which restores nothing, relies on. A card hears the screen turn through the navigator's `focus` and `blur` events (`useScreenTurn`), never `useIsFocused`, which drew every card on the screen again on each push and pop. Home's cards, shelves, hero and Binge shelf are `memo`s compared by `isSameDrawing` (`src/layouts/sameDrawing.ts`: data by content, callbacks as alike), so a query landing or a scroll window growing redraws only what changed, never every card while the remote waits. Each card tells the store as it is drawn and as it goes (`drawCard`), so a return whose opener's card has gone (its shelf went while the screen was covered, as Continue watching does once a spot is cleared) gives the screen its opening focus again rather than leave the remote on nothing. That waits for the navigator's `transitionEnd` on the screen (`returnScreen`, which `AppRoot`'s `screenListeners` call): on Android TV the transition that reveals a screen takes the focus from whatever was asked for before it ended, and only `react-native-screens`' own restore of the view that had it, which is gone here, survives. The card that took the focus back asks once more as that transition ends, and a last time 400 ms later (`LAST_ASK_MS`), since on tvOS the engine can refuse the ask at the transition's end too and give the remote to the screen's top left control: Home's Search, when Continue watching, added while Home was covered, pushes the card to the foot of the screen under the hero. ## Playing

- **What a platform plays is a table.** React Native has no `canPlayType`, so `canPlayFor(platform)` (`src/platform/canPlay.ts`) answers core's `planPlayback` from the platform's table, matched against core's own MIME and codec strings. `platformOf` (`src/platform/platform.ts`) takes `Platform.OS` and `Platform.isTV` as arguments, so both run under bun. Apple's table is MP4 or MOV, 8-bit H.264 or HEVC at any depth, and the audio in core's `HLS_COPY_AUDIO`; AVPlayer has no High 10 decoder and a remux copies the video, so 10-bit H.264 goes straight to the transcode. HEVC in MP4 or MOV is a maybe, since a file tagged `hev1` refuses and the index keeps no tag: while the viewer prefers direct play it counts as a yes and a refusal steps down to the remux, which re-tags it `hvc1` (see Settings). Android TV's is ExoPlayer's, the spec's generous start: MKV, MP4, MOV or WebM; 8-bit H.264 (as on Apple, since few TVs decode High 10 and a remux copies the video), and HEVC, AV1 and VP9 at any depth; AAC, AC-3, E-AC-3, Opus, Vorbis, FLAC, MP3, DTS and TrueHD, all of them sure, since the patched player decodes with FFmpeg what the TV cannot (below), so the table has no maybes. The names are core's `CONTAINERS`, `VIDEO_CODECS` and `AUDIO_CODECS`.
- **Audio is always decoded on the device.** The patch above keeps ExoPlayer off passthrough, so what the TV's own decoders cannot take (TrueHD and DTS on the Google TV Streamer, whose only Dolby decoders are AC-3 and E-AC-3) is decoded by FFmpeg, as Jellyfin's player does: the patch adds Jellyfin's build of Media3's FFmpeg decoder (`org.jellyfin.media3:media3-ffmpeg-decoder` `1.8.0+1`, made for the player's Media3 1.8.0, which a Media3 bump moves with it) and turns the extension renderers on (`EXTENSION_RENDERER_MODE_ON`), so a platform decoder still goes first and FFmpeg takes the rest, to PCM. Its experimental video renderer refuses every format, so video stays on the TV's decoders. With two audio renderers Media3 maps each track to the one that takes it (TrueHD and DTS to FFmpeg's, the rest to the platform's), so the library's audio track list and `selectedAudioTrack`, which read only the first audio renderer, would leave TrueHD out and number the rest wrongly, and `isAudioDropped` stepped every such file down to the remux: the patch lists and picks audio from `getCurrentTracks()`, every audio group in the file's order, whichever renderer has it. A sound bar gets PCM from the TV, not the film's own bitstream; Dolby Atmos's height channels go with it.
- **Dolby Vision profile 7 plays its HDR10 base layer where no decoder takes the profile,** as Plex's player does. A UHD Blu-ray remux (Game of Thrones' 4K seasons) is profile 7, dual layer; the Streamer's Dolby Vision decoders take profiles 4, 5, 8 and 9 but not 7, and Media3 1.8 falls back to plain HEVC only for 4 and 8, so it opened `c2.mtk.dvav.ser.decoder`, which failed on the first frame. The remux once copied the same Dolby Vision (`dvh1.07.06`) and failed the same way, so every such file fell to a 4K transcode on the NAS; the server now copies profile 7 as its HDR10 base layer alone (apps/raven/CLAUDE.md, "A Dolby Vision HEVC copy keeps its Dolby Vision"), which is how iPhone, iPad and Apple TV play it. The patch's `BaseLayerVideoRenderer` (in place of `DefaultRenderersFactory`'s `MediaCodecVideoRenderer`) hands the HEVC decoder a profile 7 format no Dolby Vision decoder on the device supports, and drops the RPU (NAL unit type 62) and the enhancement layer (type 63) from each sample before it is queued (`dropDolbyVisionUnits`), since MediaTek's HEVC decoder does not skip them: handed them, the Streamer sent the TV a solid pink picture, while `screencap`, which reads the decoded frame, still showed the right one, so only the TV itself shows whether the picture is right. A device that decodes profile 7 keeps Dolby Vision, and profile 8 (Foundation's WEB-DLs) was never affected.
- **ExoPlayer buffers what fits the heap.** The library has it buffer its 50 second minimum whatever that weighs (`setPrioritizeTimeOverSizeThresholds(true)`), and 50 seconds of a 4K remux at 69 Mbit/s is about 430 MB against the Streamer's 384 MB heap: Game of Thrones S02E01 thrashed the garbage collector and died of an `OutOfMemoryError` about two minutes in. Every source carries `PLAYER_BUFFER` (`src/player/playerBuffer.ts`) as its `bufferConfig`, a 15 second minimum, past which ExoPlayer's own byte budget (about 150 MB) decides; the Java heap then held near 195 MB with no blocking collections. The library's `DependingOnMemory` strategy is not the fix: it calls `Runtime.gc()` on the playback thread about once a second.
- **ExoPlayer refuses audio by leaving it out.** Given a track it can neither decode nor pass through, it plays the picture alone, or another of the file's tracks, and reports no error, so the ladder would never step down. `isAudioDropped` (`src/player/droppedAudio.ts`, tested under bun) reads the audio tracks the player lists, each saying whether it was picked. `react-native-video` 6.19.3 hands ExoPlayer the asked track (`selectedAudioTrack`) only as it loads, and the selection takes effect later on the playback thread, so `onLoad` still reports ExoPlayer's own first pick; `onAudioTracks` reports the settled one. ExoPlayer also starts its progress before it reports the load, so ticks come before the settled pick. `hearAudio` (in the same file) keeps the last list for the attempt and says when to judge it, once, at a progress tick: at once when the load's pick is already the asked one, and otherwise only after an `onAudioTracks` since the load, or once `AUDIO_SETTLE_SECONDS` (2 s) of play have passed with none, counted between ticks so a seek's jump never counts (the screen tells it of each seek): on Android TV in direct play, when the track asked for (by its place, or any track where the player was left to choose) is not the one playing, and a way is left below (`hasWayBelow`), the play counts as failed and steps down to the remux from the spot. The judgement is made once per attempt, so `hearAudio` makes it only on a tick the session can act on (`canJudge`: the session is playing, with a way below): ExoPlayer's first tick comes with the load, before the screen has drawn the playing session, and a judgement spent there left a lone DTS-HD track (Dunkirk 4K, whose pick was settled at the load) playing the picture alone for good. A forced original with no way below plays on, sound or none. A stream is never asked, since it carries only the track the session asked for, and Apple never, since its table names only audio AVPlayer decodes. The Android TV emulator (API 36) has no platform decoder for AC-3, E-AC-3, DTS, TrueHD or ALAC, which FFmpeg now decodes there as on a TV; before it, a TrueHD MKV stepped down to the remux, which played without sound, and the fixture film, whose English track is AC-3, played its AAC commentary directly when no audio language was preferred. A real TV decodes or passes most of them through.
- **The player plans through `planFor`** (`src/platform/playbackPlan.ts`, tested under bun), which calls core's `planPlayback` with the platform's table and `defaultAudio: true`, since direct play switches audio tracks itself, under the server's policy narrowed by Settings' prefs (see Settings). Subtitles never change the plan: every platform shows a file's text subtitles while it plays the file as it is (below), so Ruling 22's step to the remux is gone. `DEVICE_PLATFORM` (`src/platform/devicePlatform.ts`) names the platform.
- **Away from home a heavy file starts at the transcode, as Plex does.** Last, `planFor` hands its plan to core's `planForNetwork` with the `network` the screen read: when the play is away (the media origin in use is `public`, or there is none and the server's `remote.isOutside` says the request came from outside) and the file's `bitrate` is over `remote.limit`, the transcode moves first and the other ways stay behind it to step down to. On the LAN, with no limit, for a file under it or one whose bitrate is unknown, and for a plan with no transcode (this device allowing none), the plan is as it was. The network is `mediaAccessFor`'s `networkFor(mediaId)` (the kind of the origin the picture plays from, by the same pick and ticket its sources use, null for the server's own address, and the `remote` `getMediaOrigins` answered, null from a server that says nothing), which `ReadyPlayer` reads into the query cache (`PLAY_NETWORK_KEY`) and waits for with the policy and the tracks, since the session's ladder is fixed at its first mode. It never rejects: what it cannot read is `AT_HOME` (`@raven/core`, beside `PlayNetwork`), the server's own address held to nothing. The plan's order is set once; the size a transcode asks is decided afresh for each source (see "The away cap is a `quality`"), and the server alone holds it to the remote limit.
- **`canStream` answers for the HLS route.** The planner asks it about `streamMimeType`'s fragmented MP4. The app plays a remux or a transcode through HLS, never Media Source Extensions, and HLS audio is copied or made E-AC-3, so `canStream` is `canPlay` on every platform: a stream plays where its video plays in MP4, and both tables play MP4 and the stereo AAC `streamMimeType` names. On Android TV every video the server copies (H.264, HEVC, AV1, VP9) plays in a stream; the one audio a stream may carry that ExoPlayer's table leaves out is ALAC, which the route copies (a test pins both). That is a known gap: a remuxed ALAC file may play silent on a TV with no ALAC decoder, and `canStream` cannot see it, since `streamMimeType` names stereo AAC whatever the stream carries. The fix is the server's (make ALAC FLAC or E-AC-3 over HLS, or say what the stream carries), a follow-up outside the app.
- **Media goes by ticket.** `mediaAccessFor` (`libs/raven/native/src/servers/mediaAccess.ts`) gives the player a `{ uri, headers }` per mode: direct is core's `fileUrl`, remux and transcode its `hlsUrl` master playlist. It probes `getMediaOrigins`' origins (those core's `serverOriginOf` accepts, each given core's `MEDIA_PROBE_TIMEOUT_MS`) on first use and on each change of network, plays from core's `pickOrigin` (a transcode from a `public` origin asks the away cap as its `quality`, see Settings), keeps the `remote` the same answer carried beside the pick, holds no probe that picked none (the next source probes again, so an origin that comes back is used), and renews each video's ticket core's `TICKET_RENEW_MS` after it was read (two minutes, inside an account ticket's five; a ticket held longer opened only the file it first opened, so subtitles turned on mid-film were refused), by the app's clock, never from `expiresAt`, as the web and the desktop do. A refusal is core's `AccessRefusal` (a 423 is `locked`). The probe, the network watch and the jar are passed in, so it runs under bun: `probeFetchOf` (`mediaProbe.ts`) times a whole ping, since React Native's `fetch` answers only once the body has come, and `watchNetwork` (`networkChanges.ts`) is NetInfo's, with NetInfo's own internet check, which asks Google, turned off. Nothing logs a ticket; it is only ever in the source's address.
- **A signed-in account plays by its ticket.** `getMediaTicket` with the Bearer is an account ticket under `ready` (`apps/raven/CLAUDE.md`, the media plane), so `mediaAccessFor` needs no other mint. The source it hands out carries no header: no cookie, no Bearer. With no origin to play from, a signed-in account (`readAccessToken` is not null) plays from the server's own address with the ticket in `?t=` (`ownAddressSource`), never by its Bearer, which the native player would send as it was long after the token ended. A `401` or a `403` to the ticket (the fetch has already refreshed the token once) is core's `account` refusal in raven player's words, `accountAccessMessageOf`: "Sign in to X again." or "Your access to X was removed."; accounts being down (`unavailable`) is `unreachable`. An HLS master opened with the ticket gets the server's capability for its session, so a stream outlives the ticket's five minutes, and a direct file's ticket earns a pass for that file, so a play longer than five minutes needs no new one; what the server then lets go of is reopened (below).
- **The cookie is the fallback without accounts.** A server that lists no origin, has none answering, or answers the ticket 503 (no `RAVEN_MEDIA_SECRET`, which sign-in tells the viewer in the spec's words) plays from its own address with `cookieHeadersFor`'s headers. `react-native-video` 6.19.3 hands them to AVPlayer as `AVURLAssetHTTPHeaderFieldsKey` on the asset, an undocumented key AVFoundation applies to every request the asset makes, playlists and segments included, and to ExoPlayer as the OkHttp data source's default request properties, so one header covers direct play and HLS alike. It also passes the system's cookie store as `AVURLAssetHTTPCookiesKey`, which the app keeps empty; that the header survives beside it is still to be checked on a device. The playlists' URIs are absolute paths on that same address, so the cookie never leaves the server's API.

- **The ladder is a reducer** (`sessionReducer` in `src/player/usePlaybackSession.ts`, tested under bun). It starts at the plan's first mode and asks `mediaAccessFor` (made once per server by `src/player/mediaSources.ts`) for that mode's source; it steps down to the next mode from the spot the player had reached when the player reports `onError`, or, while a mode is left below (`hasWayBelow`), when `onLoad` has not come `LOAD_TIMEOUT_MS` (15 s) after the source was handed over. The last mode is never timed out: a software transcode on a NAS can take longer than that for its first segment, and the server waits for one up to `HLS_SEGMENT_WAIT_MS`. A remux the server refuses (its 409, keyframes too far apart) is such an error: AVPlayer gives no HTTP status to tell it apart, and the transcode is the next mode anyway. Each source is an `attempt`, and an event for an earlier one changes nothing. A plan with no mode shows the plan's problems, or plain words when it has none; a ladder run out says so first and then gives the plan's problems, as the web does; both with Back. **The server letting go of a source is no failure.** The screen's `onError`, shared by every chrome, asks `isServerDrop` (`src/player/playerErrors.ts`, tested under bun) whether the player's error carries an HTTP 401, 403, 404 or 423, read from AVPlayer's code (`URL_ERROR_HTTP_CODES`: on the iOS 27 simulator a forgotten HLS session failed, after about eighty seconds of AVPlayer retrying its segment and then its video playlist, as `NSURLErrorDomain` -1100; `CORE_MEDIA_HTTP_CODES`, the undocumented -12938, -12660 and -12937 its error log names) or from the response code in ExoPlayer's cause (`EXO_ERROR_CODES.badHttpStatus`); then the session gets `dropped` in place of `failed`. AVPlayer never reports a direct file's refused ranges (401): it retries them for a dozen seconds and then stalls for good, so a direct play that waits for data `STALL_REOPEN_MS` (10 s) with its clock standing still, neither paused by the viewer nor ended (AVPlayer says it waits at a file's end too), is `dropped` too; a stream's stall is left to its player, which reports the 404. That is the safety net for a file pass that ended: the server keeps a ticket opening its file past the ticket's five minutes. A `dropped` source that was playing opens the same mode again from the spot with a source handed out afresh: an HLS session the server ended or forgot (its 12 h deadline, an account recheck, the session cap, a restart) answers 404, and a direct file whose pass ended 401 (or stalls, on Apple), and each plays on, the reopen's refusal (a revoked account's 403 at the ticket) being the only thing shown. One dropped before it loaded, or again before it played on from where it was reopened (`reopenedAt`), steps down as any failure. A refusal shows its message, a `locked` one included, and the session asks again once the jar's cookies change.
- **Progress is the web's.** The player's events drive headless `videoReducer`, and headless `useProgressReport` (the web's `useWatchProgress` hook, lifted with its rules into `watchProgress.ts`) reports from that state to `progressSinkFor` (`src/player/progressSink.ts`): `recordPlay` once frames first flow, `saveProgress` once the clock is `SAVE_EVERY_S` (10 s) from the last save, on a pause and at the end, when the app goes to the background (`AppState`, as the web's `pagehide`) and on leaving, and after the last save has landed, headless `afterWatching` reads the item, its library, Home and Continue watching again. The server counts the play watched at the library's watched percentage from the saved spots, as for every client, so the app never compares the percentage itself. Every call is the allowlisted `ApiClient`'s.
- **Tracks by mode** (`src/player/playerTracks.ts`). The pickers list core's `audioLabel` for the file's audio tracks and, for its subtitles, only the language and SDH (`subtitleLabelOf`; no title, forced flag, sidecar or picture details), and the first picks are core's `preferredAudio` and `preferredSubtitle` from the player preferences, which a pick by hand updates. Raven drew them there once, from a position sampled four times a second, and every ten seconds the app froze for about three seconds twice over (see "A playing device does not follow its own saves"), so lines came seconds late, were skipped, or flashed by two at a time. Now a text track inside the file is picked by its place among the file's own subtitle tracks (`filePlaceFor`, pictures counted), a sidecar by the title it was handed to the player under (`sidecarTracksOf`: the server's WebVTT of every sidecar goes with the source as `textTracks`, titled by the track's id, so picking another never opens the video again; the session asks `mediaAccessFor`'s `sidecars` for their addresses with each direct source it asks for, so they carry a ticket as fresh as the source's on every reopen), and a stream's rendition by its place among the text tracks (`subtitlePlaceFor`). A file's picture tracks (Blu-ray PGS, VobSub) are ExoPlayer's too while it plays the file as it is (`canDrawPictureSubtitles`). **On iPhone, iPad and Apple TV raven draws the text** (`shouldDrawCaptions` true), in every mode: headless `useTrackCues` reads the picked track's cues from the server's WebVTT route through the allowlisted client (a window at a time for an embedded track, whole for a sidecar), core's `activeCues` picks those showing at the clock, the chrome draws them (`CaptionText`), and the player's own text tracks stay off. On the iOS 27 simulator AVPlayerLayer drew no HLS rendition it had selected, and a sidecar sideloaded as a `textTracks` entry made AVPlayer play a composition that drew nothing and turns AirPlay off, which is why Apple's stay raven's; Picture in Picture and AirPlay show no subtitles, since they leave raven's view. Anywhere a picture track cannot be drawn (a stream, an Apple device) the server burns it into the picture: the picker offers them whenever the plan holds a transcode, and a pick sends the session `burnPicked`, which moves to the transcode with the track's id (`burn`, carried to the master playlist as `?burn=`) from the spot and remembers the way it played before; picking text or Off clears it and goes back to that way. A plan with no transcode burns nothing.
- **Subtitles look the same on every video and every device.** The account's `CaptionStyle` (core's `contract/captions.ts`: one of four sizes, one of four colours) is kept on the server (`GET` and `PUT /api/caption-style`) and read through headless `useCaptionStyle(api)`, which also keeps the last known look in the player preferences for the first frame and for a server out of reach. Where raven draws (`CaptionText`), the text wears the colour and `captionSizeOf`'s size behind a dark edge, with no plate and no bold (the face has one weight); where ExoPlayer draws, `playerSubtitleStyleOf` (`src/player/captionLook.ts`) hands the same to the player as `subtitleStyle`, and the patch makes its subtitle view ignore each file's own styles, italics included. A TV's medium is `TV_CAPTION_BASE`. The d-pad chrome raises ExoPlayer's subtitles clear of the controls through the style's `paddingBottom`, which the player takes in pixels. A picture track is a picture and keeps its own look.
- **A playing device does not follow its own saves.** Each save of the spot came back on the event stream as a `viewing` event, and `afterWatched` then read every active query again: on a TV, where Home stays mounted under the player, about seventy requests every ten seconds, whose answers held the JS thread for about three seconds, twice. `Playing` now says it is on screen (`useWatching`, `src/stores/watching.ts`), `useAppQueries` hands that to `serverEventsFor` as `isWatching`, and a `viewing` event is let pass while it is true; the progress sink's `afterWatching` reads everything again as the player closes.
- **Quality starts with Direct play** (`src/player/qualityOptions.ts`, tested under bun). The chromes' third picker, beside audio and subtitles (the `settings` icon, "Quality"), always shows, and its first option is always "Direct play (Original quality)" with the file's bitrate; then each size core's `offeredQualities` gives under the server's `maxHeight` (the `playbackSettingsQuery` the policy comes from), largest first, as its `STREAM_QUALITIES` label and `formatBitrate`, offered only when the plan holds a transcode. Direct play sends the session `directPicked`, which plays the file itself from the spot whatever the plan started with, putting direct play first again where the plan left it out (a failure then steps down as ever) and dropping any size and burn. A size sends `qualityPicked`, which, as `burnPicked` does, moves to the transcode from the spot and remembers the way it played before (`stepBeforeTranscode`, shared with the burn). The session hands the size to `mediaAccessFor` as `SourceRequest['quality']`, which a transcode asks in place of the away cap's; with none picked the away cap stands. A size picked while ExoPlayer draws a picture track burns that track too, since a transcode carries none.

## Music

- **The queue is the shared store's.** `useAudioQueue` (`@raven/ui/headless`) holds it, as on the web and the desktop; `MusicHost` (`src/music/MusicHost.tsx`), mounted once in `AppRoot` above the routes, plays it. An iPhone or iPad plays through `@raven/audio` (`libs/raven/audio`, a local Expo module: `AVQueuePlayer` with Now Playing and the remote commands), driven by `@raven/native`'s `useNativeAudioHost` (Wren's too) over `@raven/ui`'s `useWindowedAudioHost`, the desktop's driver too: it hands the player a window of two tracks, the playing one and the next, so the seam plays in the background, and steps the store when the player says `advanced`. `nativePlayer.ts` runs the window's changes in order and drops one the queue moved past while its ticket was on its way. The lock screen's controls come back as `remote` events, which `runRemoteCommand` carries out on the store. A TV plays through `react-native-video` out of sight (`VideoAudioHost`), one track at a time, and never calls `@raven/audio`, which looks its native module up on first use.
- **A track plays by its ticket**, the video's way: `useNativeAudioHost` takes `mediaSourcesFor` and builds each item with `@raven/native`'s `audioItemOf` (Wren's too), the file in direct mode and its length from the server, since AVFoundation rounds a FLAC's up to whole blocks. `audioItemOf` asks core's `canPlayAudio` first, so a track AVPlayer cannot decode (Opus in WebM) plays from the server's AAC transcode (`trackSource`) rather than failing in the player. A track downloaded to the device plays from its file (`trackPlanFor`, `src/downloads/downloadVisibility.ts`, whose `read` thunk gives it the entries, the unlock and the disk as each track plays); any other streams the file itself on any network.
- **The bar.** `NowPlayingBar` (`src/music/NowPlayingBar.tsx`) sits under the screens while a track plays, off the film player and Now Playing (`useIsBarShown`), and keeps the bottom inset for itself, so `AppRoot` gives the screens above it none. ## Settings

- **`/settings` keeps to the device, and for the owner to the server too** (`app/settings.tsx`, `src/screens/Settings.tsx`, laid out by `Settings.touch` and `Settings.focus` over `settingsKit.ts`). Its own rows ask no server anything; it asks `GET /api/me` (`getMe`, through headless `accountQuery`) who is signed in, and only the approved owner gets the Admin sections below. Under the thumb it opens from a gear (`SETTINGS_ENTRY`, U+2699 with the text presentation selector, so no emoji) beside Search in Home's header; on a TV from a Settings plate beside Search in Home's top row. The TV layout takes every length from `TV_SIZES`, and its switches are plates that say On or Off (`accessibilityRole="switch"`), since tvOS has no switch. The theme and the away cap are `SettingsChoice` rows, laid out as the toggles are (the label at the start, the value at the end), opening the `Picker`'s own list: `openPickerSheet`'s action sheet under the thumb, `PickerList`'s `Modal` list (`usePickerList`) on a TV.
- **Subtitles.** The one section kept on the server, for the account on every device: Size and Colour, two `SettingsChoice` rows over core's `CAPTION_SIZES` and `CAPTION_COLOURS`, saved through headless `useCaptionStyle` and shown before the server answers.
- **Account.** Settings shows who is signed in and a Sign out, which clears the account session (`useAccountSession`) and sends the viewer back to sign-in. The app talks to the one server in `@raven/native`'s `src/servers/ravenServer.ts`, so there is no list to manage.
- **The prefs are `useAppPrefs`** (`src/stores/appPrefs.ts`): the theme (core's `THEMES`, which every screen wears: see Themes), prefer direct play, allow transcoding and the away-from-home maximum height (core's `MAX_HEIGHTS`, the heights the server's own cap offers: 2160, 1080 or 720 lines, 1080 by default, the server's own default). They are one JSON value in AsyncStorage under `raven-app-prefs`, losable as the player prefs are, and each value read back is guarded on its own: one the store cannot use falls back to its default and the rest stand.
- **The prefs narrow the server's policy and never widen it.** The player reads the two playback choices and passes them to `planFor` as `prefs`, and the away cap reaches `mediaAccessFor` as a reader (`awayMaxHeight`), injected by the `mediaSourcesFor` binding as `readCookies` is, so the session ladder never carries it; the pure code reads no store. Allow transcoding off turns the server's `on` into `remuxOnly` before core's planner, so the plan holds no transcode, and a plan left with no way adds `TRANSCODING_OFF_HERE` to its problems; a server that only remuxes or converts nothing stays so. Prefer direct play decides the maybes: each play table names them by codec, in every container it plays (Apple's HEVC, for the `hev1` tag; Android TV has none), and `canPlayFor`'s `canPlaySurely` is `canPlay` over the table with them taken out (`surelyOf`). Preferred (the default), a maybe is tried as it is and a refusal steps down; not preferred, the plan starts at the remux, unless no other way is left, when the file is still tried as it is. A stream never meets a maybe (a remux re-tags HEVC `hvc1`, and its audio is copied or made E-AC-3), so `canStream` is unchanged. The web has no counterpart: its direct play is the server's `directPlay` and the browser's own `canPlayType`, so this stays in the app.
- **The away cap is a `quality`.** The server's HLS route takes no height, only one of core's `STREAM_QUALITIES` as `quality`, and only for a transcode (it answers 400 for a remux). So `mediaAccessFor` asks a transcode played from the `public` origin `pickOrigin` picked for the size at Settings' cap height with the fewest bits (`awayQualityOf`: `low1080` at 8 Mb/s, `low720` at 2 Mb/s), since the cap is there to save data away from home and must never ask for more than the server would spend by default (its `medium` quality aims at 8 Mb/s). That is the only size the device asks: it asks none at 4K (the sizes stop at 1080p), none from a LAN origin or from the server's own address (even one reached from outside), and none for a remux or direct play. The server's remote limit is not the device's to apply: core's `planForNetwork` only moves a heavy file's transcode first (above), and the server's `streamSizeFor` holds every transcode away from home to the limit by the request's address (apps/raven/CLAUDE.md, "Remote access"), so a request that asks too much, or asks nothing, is held anyway. The source request names only the video (`SourceRequest['media']` is its `id`), so the session ladder carries no size. The server's own `maxHeight` still caps the frame (`capHeight`). A size also sets a bitrate: libx264 keeps its CRF under it as a ceiling, and VideoToolbox and VAAPI take it as their target. A height parameter on the server would cap the frame alone; that is the server's follow-up.
- **The owner's Admin sections are the web's Admin page** (`src/screens/AdminSettings.tsx`, with `AdminRemoteAccess`, `AdminLibraries` and `AdminUsers` beside it, the words in `adminCopy.ts`), in its order and with its names, after the device's own rows, which every account keeps, the theme among them: Admin (Reset to defaults, asked twice), Playback (Play the original file, Server conversion, Transcode size, Transcode quality, Hardware acceleration, the encoder in use, tone mapping and Find intros and credits), Display (Movie titles), Remote Access (to read only, on every device: the status, then the private and public address in the fixed-width face, `CODE_FONT`, and the remote limit, each a `SettingsFact`; turning it on or off and changing it are the web's and the desktop's alone, so `setRemoteAccess` is not among `APP_OWNER_CALLS`), Library scans (what runs, Cancel all running scans) and then each library's Quick scan, Full scan, Scan intros and credits, Merge duplicate albums, Update ratings and Match again, each long one its own Cancel while it runs, and Users (the accounts by access, a `SettingsChoice` for the web's tabs, Approve and Remove access, which asks first). Each saves as the web's does, through headless `useOptimisticMutation`, `memberStatusEdits`, `afterRescan` and `afterRematch`, and invalidates what the web invalidates. A refusal shows in a `SettingsLine` and puts the change back. The web's Server section (the fixed server's name and address, no setting), its admin lock (the admin password, which the app never asks) and adding, editing or deleting a library (a folder browser and the library dialog) are not in the app.
- **TV focus.** Settings opens with the remote on Sign out (`SettingsButtonProps['isOpener']`), once, the Admin sections' buttons asking for nothing: anything on the page taking the focus spends it. Home's Settings plate, a `PlateButton` holding its view through `ref`, remembers itself as the opener (`useOpenerFocus`), so Back from Settings lands on it, on Android TV too.

## Themes

- **The palette is `themes.scss`, never a copy.** `appTheme.ts` reads each theme's colours from `@raven/ui/designTokens`' `themeTokens` (core's `parseThemes` over `themes.scss`, inlined at build) and the fixed ones from `designTokens` (`globals.scss`), and names what the screens paint with through the names in `src/theme/tokenNames.ts`, which imports nothing so `app.config.ts` can read it: `PALETTE_TOKENS` (ground, raised, text, muted, accent and the rest, each a token every theme redefines) and `OVER_PICTURE_TOKENS` (what the page's ground, raised, quiet, line, track, text and muted become over the video: the web player's stage, `--color-picture-glass`, `--color-bark-faint`, `--color-on-picture` and `--color-on-picture-soft`). `APP_THEMES` makes one `AppTheme` per theme as the module loads: its id, its `palette`, its `overPicture` palette (the palette with `OVER_PICTURE_TOKENS` laid over it, so the played line and the rest stay the theme's, as the web's `--color-leaf-bright` does) and its `tone`, core's light or dark. A token the stylesheets drop fails the app as it loads. `appTheme.test.ts` reads `themes.scss` and `globals.scss` themselves, not the build, and checks every theme's palette against them, Patina's ground among them, so neither a stale build nor a parse can drift. `nativeTokens` turns CSS's translucent `rgb(r g b / a%)` into `rgba()`, for the picture's glass.
- **`useTheme(selector)`** (`src/theme/useTheme.ts`) reads Settings' pick in `useAppPrefs` through `appThemeOf`, so a component re-renders only when its slice changes, and a pick repaints every screen at once; there is no context. Each theme is one object for good, so `useTheme((theme) => theme.palette)` is stable. `themeNow()` reads it outside a render (the touch picker's sheet, at a press).
- **A layout's styles are `themedStyles((colours) => StyleSheet.create(...))`**, built once per theme, on the page and over the video, as the module loads; the component calls the hook it returns (`const styles = useStyles()`), or `useStyles({ isOverPicture })` for the set built from the theme's `overPicture` palette, for a shared control that may sit over the video. What is only ever drawn over the video (the three player chromes, the captions, the TV's `PlayerNotice`) builds with `pictureStyles` instead, whose hook is always that set: there is one palette, worn on the page or over the picture, and no separate picture colours. No layout keeps a colour constant: a colour is the palette's or it is `transparent`. The shared sets are hooks too: `useTouchFormStyles`, `useTvFormStyles`, `useToneStyles`, `usePlateStyles`.
- **The logo is vector art, in one of three looks.** `Logo` (`src/layouts/Logo.tsx`) draws `RAVEN_MARK` (`src/theme/brand/ravenMark.ts`: the path, the eye and the colours of the web's `raven-mark-on-*.svg`) through react-native-svg, so it is sharp at any size on any screen, where a bundled picture pixelated on a TV. `brand.test.ts` keeps the path and the colours to the web's files, and the app's `test` target names those files among its Nx inputs, so a change to the web's marks reruns it rather than replaying a cached pass. `LOGO_LOOKS` gives it a little variety: the brand's ink for the ground's tone with its red eye (`inked`), the theme's leaf with the eye (`leaf`), or the text colour alone (`mono`); `LAUNCH_LOOK` is picked once as the app starts, so every screen of a run wears the same one and the next run may wear another. Home's title row and every form (sign-in, a rename) wear it. The Apple TV's icon and Top Shelf images are `scripts/tv_apple_icons.sh`'s (`bun run icons:tvos`): each icon size a back layer, the ground, and a front layer, the mark, for tvOS's parallax, and the Top Shelf the mark and the wordmark, into `assets/images/tv_apple/`, which config-tv's `appleTVImages` builds into `TVAppIcon.brandassets` at a TV prebuild. The Android TV launcher's tile is `scripts/tv_banner.sh`'s (`bun run banner:tv`): the mark and the wordmark in Young Serif drawn with ImageMagick at every density into `assets/images/tv_banner/`, which `plugins/withTvBannerDensities.ts` copies into each `drawable-<density>` after config-tv has copied the one xhdpi file (`assets/images/tv_banner.png`) everywhere; the plugin is applied before the plugins list, since the last mod added runs first.
- **The system's look follows the tone.** `AppRoot` follows the theme (`followTheme`) into `Appearance.setColorScheme`, so alerts, action sheets, keyboards and tvOS's focused fields are light or dark with it, and sets the status bar's style; the touch picker's sheet passes the tone as `userInterfaceStyle` too.
- **No wrong first frame.** `expo-splash-screen` (`58.0.10`, the version Expo 58.0.23's list names) keeps the splash up: `AppRoot` calls `preventAutoHideAsync` as it loads, draws nothing until `loadStores` has read the prefs, and calls `hideAsync` in an effect once the loaded tree has committed, so the first frame after a relaunch is the theme picked, never the default on its way to it, and only then follows the theme into the system's look. A splash call that fails is ignored, since the next frame is raven's either way. The system cannot know the pick, so `app.config.ts` gives the splash, and Android's window under the app (`android.backgroundColor`), the default theme's `--color-night`, read from `themeTokens` through `PALETTE_TOKENS.ground`: a frame that slips through is the default's dark, never white. iOS's counterpart, `ios.backgroundColor`, is read only by `expo-system-ui`, which the app does not install; there the splash covers the window until it is hidden, and React Native's own root follows the tone `Appearance` is set to. A stored theme that is no theme, or a file that cannot be read, is the default.
- **The player is dark in every theme**, as the web's (`Player.module.scss`, its controls and settings menu): the stage ground, the on-picture text and time labels, the picture's glass under every button (the touch chrome's skips and its large Play, Android TV's Play and Back plates, a raised Back, which `TouchBack`'s `isRaised` draws from the `overPicture` palette), under the audio and subtitle chips, and under the captions, and the faint track; only the played line (`played`, the theme's `--color-leaf-bright`) and the focused thumb's ring on Android TV take the theme. A picker or tool button over the video takes `isOverPicture` (`PickerProps`, `ToolButtonProps`, `PlateButton`), which draws it from the `overPicture` palette with its focus ring in the on-picture colour, and what it opens is dark too: the touch sheet asks for `userInterfaceStyle` dark, and the TV's `PickerList` is the picture's glass on the stage's shade. A TV plate's edge is `transparent` until it has the focus, so a translucent glass plate shows no second coat round it. Both TVs' `PlayerNotice` (nothing to play yet, or refused) is dark too, as the web's page for a video that cannot play. The status bar over the player is light. `Player.render.test.tsx` and `Player.dpad.render.test.tsx` check the chips, Play, Back and the TV's list under Patina.

## The allowlist and the end to end flows

- **The app calls only core's `APP_CLIENT_CALLS`** (`libs/raven/core/src/appClientCalls.ts`): the viewer reads, the spec's writes plus `unlockAdmin` and the PIN's `unlock` and `lock`, the ticket and the media plane, each as a method and a `:name` path template, through PR 9's screens, and the owner's own, `APP_OWNER_CALLS` (Settings' Admin sections: the playback and display settings' writes, Remote Access to read, the members, and a library's scans, ratings, markers, album merge and match), spread into the list. `apiFor` wraps its fetch in `allowlistedFetch` (`libs/raven/native/src/servers/allowlist.ts`), which throws before the request on any other method and path (`appClientCallOf` matches them; a dot segment never does), so the server never hears of it. `@raven/server`'s `appClients.test.ts` checks the list against the server's route marks: every entry is a real route, none outside `APP_OWNER_CALLS` is `@AdminOnly()` or kept for the owner by the account gate, every entry of `APP_OWNER_CALLS` is, and the only writes are the spec's and the owner's. The server stays the authority: each owner call answers anyone else 403. A screen that needs a new route adds it there first. Pictures, the event stream and the player's sources are fetched natively, not by the `ApiClient`, so `cookieHeadersFor` checks their URLs the same way and throws before it hands one its cookies, and `mediaAccessFor` checks a ticketed source's URL with `checkAppCall`; a source that cannot be built, the jar unreadable or a URL refused, is a refusal, so the player always hears back.
- **`e2e/` holds Maestro flows, against `@raven/server`'s `serve:fixture`** (a real accountless server on `http://127.0.0.1:8490` with an open film library holding an MKV and an open series library holding an MKV episode and an MP4 one with an English sidecar). The build names it with `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN`. `signIn.yaml` launches the app clean on the fixture, `home.yaml` finds the film on Home, `library.yaml` opens each library from its shelf's See all, sorts the films by date added from the action sheet, and finds no file-size sort for the series, `item.yaml` opens the film's page, marks it watched and takes the mark off again (so the fixture is left as found), and goes from the series to its season and its episode, `play.yaml` plays the film from its page (its MKV through the HLS remux, on the cookie, since the fixture lists no media origin), pauses it, goes back and clears the saved spot with a mark and its undoing, and `search.yaml` searches every library from Home's header and opens the series it finds finds nothing for a word no title holds, and searches the film library from its own box. A field is tapped as the element below its label, since Maestro picks the label's text first.
- **Touch flows press Back through `steps/back.yaml`, never `tapOn: Back`.** Back sits where iOS draws its banners, and a fresh simulator posts an Apple Intelligence follow-up (`com.apple.icloud.gm`) minutes in: a press that lands on that banner opens Settings and leaves raven in the background (the run `library.yaml` failed on, with "See all in Series" not found). The step presses Back and, when Settings shows "Return to Raven", goes back and presses it again.
- **A flow finds a card by its shelf, never by a name alone.** The hero rotates through the fixture's titles, so "Kestrel Point" or "Lantern Bay" on its own may be the hero's slide: a touch flow scrolls to the card below its shelf's title (`steps/shelfCard.touch.yaml`, a `scrollUntilVisible` to the `TITLE` it is handed `below:` its `SHELF`), since on an iPhone the hero pushes the shelves off the screen, and Home counts as ready once the Films title shows (`signIn.yaml`). Every touch scroll to a target passes `centerElement: true`: iOS reports a view scrolled under the iPhone's tab bar as on screen, so a scroll that stops there leaves the tap on the bar (it opened More in place of See all). On a TV the side menu has rows named Continue watching, Films and Series, so the TV flows find the Continue watching shelf by its key, the `testID` every focus shelf carries on its title and cards together (`id: in-progress`), since the remote on a card below can scroll the title off the screen.
- **One folder, two inputs.** Maestro runs only the top of `e2e/`, so the sub-flows sit in `e2e/steps/`. A flow only the thumb can drive is tagged `touch` and one only the remote can drive `dpad`; `e2e` runs `--platform ios --exclude-tags dpad` and `e2e:android-tv` `--platform android --exclude-tags touch`, so `signIn.yaml` and `home.yaml` run on both and each run picks its own device even with the other booted. The Android TV emulator reaches the computer's loopback as `10.0.2.2`, but `e2e:android-tv` first runs `adb reverse tcp:8490 tcp:8490`, so the bundled `127.0.0.1:8490` reaches the fixture there too and the fixture keeps listening on the loopback only.
- **The Android TV flow is `play.dpad.yaml`, driven only by the remote's keys** (`pressKey: Remote Dpad ...`, `Back`, `Remote Media Play Pause`) and checked by what has the focus (`focused: true`): open the fixture, Home with the focus on the hero's Play and Down to the film (`steps/heroToFilm.dpad.yaml`), its page with the focus on Play, Play, pause, right on the line skips ten seconds (the line's spoken value, `Position, 0:15 of 1:00`, is read with `copyTextFrom` and the spot ten seconds on worked out in `evalScript`, since the repo keeps no JavaScript file for `runScript`), Back to a page offering to resume from exactly that spot, Back to Home with the film under Continue watching and the focus on its card below the Films title, then Watched and back to clear the spot, so the fixture is left as found. A run stopped part way can leave the film under Continue watching, so `play.dpad.yaml` first clears the spot when Home shows that shelf (`steps/clearSpot.dpad.yaml`, which it also ends with), and `home.yaml` moves down to the series' shelf on a TV, where the hero and the films push it below the screen. The pause is the remote's play and pause key rather than select, since the controls fade five seconds after a press and a hierarchy read on the emulator can take longer than that, and while paused they stay. The film is sixty seconds long, so the flow keeps moving.
- **Maestro cannot drive tvOS.** Its XCTest driver (2.11.0) is built for iPhone and iPad only and refuses to install on an Apple TV simulator ("not built to support this device family"), so the flows run on the iPhone simulator. They need the development variant, for plain http to the loopback.
- **`bun run app:deploy:tvos` puts raven on the paired Apple TV with nothing to click** (`scripts/deploy_tvos.sh`): it reads the Apple Development team off the keychain's certificate (its OU), regenerates the tvOS project with `APPLE_TEAM_ID` set, which `app.config.ts` writes as `ios.appleTeamId` so the project carries the team and Xcode never asks for it, builds the signed Release for `generic/platform=tvOS` (`-allowProvisioningUpdates -allowProvisioningDeviceRegistration`, so a new TV is registered and the profile made), waits for the paired Apple TV (`APPLE_TV` names one when several are paired; a pairing id is not a destination, the 40-character hardware UDID is), installs and launches. `APP_VARIANT` is `development` unless set. A Personal Team's profile lasts seven days; run it again to renew.
- **The real Apple TV has a test of its own, `tvos-e2e/DevicePlaybackTests.swift`,** run against the installed, signed-in app and the real server, never the fixture: it opens each video named in `RAVEN_DEVICE_MEDIA_IDS` (`TEST_RUNNER_RAVEN_DEVICE_MEDIA_IDS` to `xcodebuild test`, comma separated) by its link (`raven://play/<id>`, `?from=start` or `?at=`, opened by `XCUIDevice.shared.system`, since the app's own `open` waits on accessibility a Release build never reports) and drives every way a viewer plays: from the start, pause and play (the picture holds, then moves), two skips forward and one back (the scrubber's Position value), leave and resume past the spot, start over, and resume again. Each step waits for the opening mark ("Opening the video") to go, checks the clock runs and that the middle of the screen is lit, and attaches a screenshot named for the step and the way it played. Without the variable the class skips, so CI's fixture run is untouched. It moves the account's saved spots. The test target is built for tvOS 16.4, the app's own (`withTvRemoteTests`), so it runs on any Apple TV the app does: `xcodebuild test -project ios/Raven.xcodeproj -scheme RavenRemoteTests -destination id=<the TV's hardware UDID> -only-testing:RavenRemoteTests/DevicePlaybackTests` with the team's signing.
- **Apple TV starts every video by a seek of the app's, as iPhone and iPad do** (`PLATFORM_TRAITS`' `seeksToResume` in `src/platform/platform.ts`, read as `IS_SEEKING_TO_RESUME`; `startUp.ts`): `react-native-video` applies a `startPosition` of 0 as well, and its seek and play around it left AVPlayer waiting to play for good, so on Apple TV every start, from the beginning and from a spot, Direct play and Remux alike, sat on the opening mark with a black screen (the device test found it still opening after 90 seconds). Until the resume seek lands the player's progress ticks are not where the viewer is (AVPlayer says 0:00), so they move neither the saved spot nor the spot a step down the ladder starts from: before, a stalled 10:00 resume stepped down to a transcode from 0:00 and saved that.
- **AVPlayer can play the sound without the picture, and say nothing.** HEVC under the `hev1` tag in an MP4 (The Dog Stars' 4K WEB-DL, Dolby Vision over HDR10) plays its audio with a black screen and no error, so the ladder never stepped down. `watchPicture` (`src/player/missingPicture.ts`, tested under bun) hears `onReadyForDisplay`, which the library raises once the picture layer has a frame, and the clock: a direct play on iPhone, iPad or Apple TV whose clock has run `NO_PICTURE_SECONDS` (4) with nothing drawn counts as failed and, with a way below, steps down to the remux, which re-tags it `hvc1`. Each attempt is watched afresh; streams and Android TV are not watched.
- **TV chapters.** The player reads the file's chapters (`markersQuery`, `getMarkers`, never waited on) and hands them to the chrome (`PlayerChromeProps['chapters']`). On both TVs a slim Chapters strip sits under the buttons (`ChaptersBand`, `src/layouts/PlayerChapters.dpad.tsx`): Down from the buttons reaches it through the focus engine, and reached it opens into the row of chapters (place, name or "Chapter 3", start), the remote on the one playing (`chapterAt`); select jumps there and gives the line the focus back, and the row folds as the focus goes back up to the buttons or the line. A file without chapters draws nothing. The scrubber marks them too (`chapterMarksOf`, `src/layouts/chapterMarks.ts`, tested under bun): a hairline cut in the line where each chapter after the first begins, and the chapter playing a shade lighter than the rest of the track, so its length reads at a glance.
- **The Apple TV's flow is an XCUITest, `tvos-e2e/RemoteFlowTests.swift`,** driven by `XCUIRemote`: open Home on the fixture, where the focus starts on the hero's Play, Down to the film and select it, Play, twenty seconds of the remux, Menu to the page (now offering Resume), Menu to Home, where the film is under Continue watching and the focus is on its card below it, and Menu on Home sends raven to the background. It then marks the film watched and back, as `play.yaml` does, so the iPhone flows that follow in CI find the fixture as it was. It names the app by its bundle id and drives whatever build is installed, so it never builds the app.
- **`ios/` is generated, so a config plugin adds the test.** `plugins/withTvRemoteTests.ts` joins only a TV prebuild (`EXPO_TV`, read by `src/config/tvPrebuild.ts` as config-tv reads it): it copies `tvos-e2e/*.swift` into `ios/RavenRemoteTests/`, adds a tvOS UI test target of that name with no app target and no dependency on the app (so building it builds nothing else), and writes a shared `RavenRemoteTests` scheme. The `xcode` package ships no types, so the plugin guards the project down to the methods it calls. Each `prebuild:tvos` makes it afresh, and so does a prebuild without `--clean`, since Expo 58 writes the project file anew either way; the mod also returns early on a project that already has the target, copying only the Swift, so a mod run twice on one project adds no second. `prebuild:ios` leaves it out.
- **`e2e:tvos` runs it** (`xcodebuild test` on `ios/Raven.xcodeproj`'s `RavenRemoteTests` scheme, with `DEVELOPER_DIR` as the other Apple scripts): after `APP_VARIANT=development EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN=http://127.0.0.1:8490 build:tvos`, install the build on the simulator named `Apple TV 4K (3rd generation)`, or the one `TVOS_SIMULATOR` names, and start `serve:fixture`. Its result bundle is in `build/tvos-e2e/Logs/Test`. A run stopped before its clean-up leaves the film under Continue watching, which a fresh `serve:fixture` clears. CI runs it after the tvOS build on a fresh `raven-tv` simulator, against the fixture server the iPhone flows then reuse, in place of the old launch check, and uploads the result bundle when a step fails.
- **Each `build:*` runs its `prebuild:*` first:** bun runs a script's `pre` script before it, so a build always regenerates its native project, and both build environment values reach it. The Nx inputs include `APP_VARIANT` and `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN`, so a cached production build cannot stand in for the fixture build. CI checks the pods after each Apple build, since `expo prebuild` exits 0 when `pod install` fails.

## TypeScript configs

- Two tsconfigs, and `typecheck` runs both. `tsconfig.json` checks the app (`src/`, `app/`, `index.ts`) with React Native's types only, so a Node or Bun global in screen code fails the typecheck. `tsconfig.node.json` checks what runs under Node or Bun: the three configs and the bun tests (`src/**/*.test.ts`), with Bun's types. The render tests stay in `tsconfig.json`, since they import their globals from `@jest/globals`.
- `app.config.ts`, `metro.config.ts` and `babel.config.ts` are the only configs; there is no JavaScript file. Expo loads `app.config.ts` and `metro.config.ts` with its own require hook, which transpiles them with `typescript`. Babel loads `babel.config.ts` through Node's own type stripping, so Metro and jest need Node 22.18 or newer.
- Expo's hook reads no tsconfig `paths`, and Node adds no `.ts`, so `app.config.ts` imports `./src/config/tvPrebuild.ts` and the other modules it shares with the app by relative path and extension. That one file is exempt from the `@/` rule in `.oxlintrc.json`. The build number and the variant come from `@raven/native/headless` (`buildNumberOf`, `isDevelopmentVariant`, `BUILD_ENV`), which Wren's config reads too.
- `version` comes from `package.json`, which `scripts/bump_version.sh` bumps with the rest. `ios.buildNumber` and `android.versionCode` come from `GITHUB_RUN_NUMBER`, and are `1` on a local build.

## Toolchain

- **watchman.** Without it Metro serves stale bundles after a change. `start` checks for it first and stops when it is missing: `brew install watchman`.
- **Xcode and CocoaPods.** `xcode-select` on this Mac points at the Command Line Tools, so the Apple scripts use `DEVELOPER_DIR` when the environment sets it (CI picks its Xcode that way) and `/Applications/Xcode.app/Contents/Developer` when it does not. Prebuild runs `pod install`: `brew install cocoapods`.
- **Android.** The SDK is in `~/Library/Android/sdk` (`ANDROID_HOME`), the TV emulator is the AVD `raven_tv`, and Gradle runs on Android Studio's bundled JDK (`JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`).
- `prebuild:tvos` and `prebuild:ios` write the same `ios/` folder; each Apple build runs its own prebuild first, so it never builds the other platform's project.
- **Maestro** for `e2e` and `e2e:android-tv`: `brew tap mobile-dev-inc/tap`, then `brew install mobile-dev-inc/tap/maestro` (2.11.0, on Homebrew's OpenJDK). The formula installs only its newest release, so CI's iPhone and Android TV jobs download that release's zip by version and checksum instead, and start the fixture server in a step of their own. `e2e` points Maestro at Xcode through `DEVELOPER_DIR` like the other Apple scripts; without it, Maestro finds no simulator. `e2e:android-tv` needs the emulator running (`emulator -avd raven_tv`) with the development-variant APK installed, and finds `adb` under `ANDROID_HOME`, which it requires (`~/Library/Android/sdk` on this Mac, the runner's own in CI).
- **CI's Android TV run** is `📺 App on Android TV` on `ubuntu-24.04`: KVM through a udev rule, an `android-tv` API 36 x86_64 AVD on the `tv_1080p` profile (960 by 540 dp, as the local `raven_tv` AVD that `ci:app:android-tv` makes; an older one made on `tv_4k` is reused as it is) made and booted once by `reactivecircus/android-emulator-runner` on a pinned emulator build and kept with its snapshot in the Actions cache, under a key naming the system image's revision, the emulator build, the cores, the RAM and the options (a snapshot from anything else cold boots), the fixture server in the background, then the APK installed and `app:e2e:android-tv` run inside the runner's emulator step. CI builds the APK for x86_64 alone (`ORG_GRADLE_PROJECT_reactNativeArchitectures`, an Nx input of `build:android-tv`), so its artifact runs on an emulator, not a TV.
- **CI's app caches are saved on main only.** `app-caches.yml` builds the three platforms on main (when the lockfile or the native config changes, weekly, and by hand) and saves ccache's objects, CocoaPods' and Gradle's downloads, Gradle's build cache, Homebrew's and apt's packages and the AVD; the PR's app jobs restore them and save nothing, since a PR's caches are its alone. Both set up through the same actions, `.github/actions/raven-app-setup` (Bun, Node, the caches, ffmpeg, ccache, the build environment, the install and the libraries) and `raven-android-avd` (the emulator's settings, KVM and the AVD), so the two never build differently. The Apple builds compile through ccache (`USE_CCACHE=1`, which Expo's Podfile reads), and Android's CMake uses it whenever it is installed.

## Downloads

- **Touch only.** `/downloads` (`src/screens/Downloads.tsx`, `DownloadsLayout`) is in the touch side menu; the layouts' `canDownload` puts Download on the item pages (movie, episode, season, show), the touch album page draws Download as the last of its `IconPlate`s, and the touch playlist layout draws `DownloadChip`. The TVs' kit (`Downloads.focus.tsx`) draws none.
- **The store is `useDownloads` (`src/stores/downloads.ts`),** persisted to AsyncStorage under `raven.downloads`, guarded on read (`entriesOf`), with the disk and servers injected (`configureDownloads`, `DOWNLOAD_DEVICE`). The downloads belong to an account, as Wren's do (`ownerId`, read back through `@raven/native`'s `savedOwnerOf`, and `keepFor` over its `ownerDecisionOf`): downloads saved before they had owners read back with none, and `AppRoot` lets the account read back claim them as the stores load; another account signing in removes them, files too, and a sign-out keeps them. The disk is `@raven/native`'s `deviceDiskFor` with its `DISK_TRANSFERS.task` (`src/downloads/downloadDisk.ts`), whose paths (`folderOf`, `inFolder`, `DOWNLOADS_FOLDER`), reconcile (`reconcileDownloads`, `keepReconciled`) and every size, read through `byteCountOf` since iOS hands one over as a BigInt, are shared with Wren. The store holds the actions and one `updateEntry({ entry, change })`, which writes back only onto the entry still current by its `stamp`; the work is beside it in `src/downloads/`: `downloadRun.ts` (`fetchOne` over a `RunContext`: pictures, the server's copy, the source by ticket, a video's tracks, then the bytes, ending in a `done` or `failed` status), `prepareAhead.ts` (`isPreparingAhead` in the store says it runs), `reconcileDisk.ts`, and `entryOf` in `downloadEntries.ts` beside the guard. The running fetches' `AbortController`s are store state (`controllers`). Files are `downloads/<serverId>/<mediaId>/media.<ext>` under the documents, `.part` until whole, with `art.jpg` beside it. One at a time, in the queue's order: each entry has a `place` (lowest first; `entriesOf` ranks entries saved before places in the order the queue ran then), `download` appends, and `move({ key, before })` puts a queued entry before another or last, never the one downloading, which stays first. While one downloads, `prepareAhead` asks the server for the next `PREPARE_AHEAD` (2) queued copies every `PREPARE_AHEAD_POLL_MS` (5 s) and writes the answer onto the queued status (`preparing`: the copy's progress, 1 once ready, null unknown), so a copy is made before its turn; only two, since the server converts two at once and its cache evicts the least recently served copy to make room. Each group records the library it was asked from (`group.library`: id, name, icon and whether it was locked then, from `downloadLibraryOf` over `librariesQuery`; `refreshLocks` rewrites the lock as the server lists it), so Downloads groups by library and hides a locked library's entries offline. A relaunch queues what it stopped again from nothing (`resume`, called by `AppRoot` once the servers are read), and a finished file gone from disk fails. Bytes and speeds live in `useDownloadProgress`, never written; speed is core's `downloadSpeed.ts` (smoothed, none after 3 s quiet), shared with the desktop's Downloads page. What Downloads shows is built by `downloadsPage.ts` (`downloadsPageOf`; a `FinishedGroup` is `video` or `music`, the music one carrying its tracks and queue source), the Download buttons by `downloadControl.ts` (`downloadControlOf`), and what a lock hides by `downloadVisibility.ts` (`visibleEntriesOf`, `downloadedVideoOf`, `trackPlanFor`). The touch layout is `Downloads.touch.tsx` over `DownloadRows.touch.tsx` (the running and finished rows) and `DownloadChip.touch.tsx` (the music pages' Download).
- **Which bytes** (`videoWayOf`): the original when AVPlayer plays it for sure, else the server's MP4 copy (`GET /api/media/:id/device-download`, polled every 2 s while `preparing`, then `copySource` by ticket), else no Download. A track is its file, or AAC where `canPlayAudio` says no.
- **A long press on a card opens the TV card menu under the thumb.** One menu model serves both: `src/cardMenu/CardMenu.tsx` reads what the card's `subject` stands for and builds its options through the hooks in `src/cardMenu/useMenuOptions.ts` (`useItemMenuOptions`, `useVideoMenuOptions`, `useAlbumMenuOptions`), each mark through the same headless hooks the item page uses, so it shows at once everywhere; the words and the builders are `src/cardMenu/menuOptions.ts` (`CARD_MENU_COPY`, `downloadOptionOf` over the page's `DownloadButton`, `linkOptionOf`, tested under bun). The options are Download (or Cancel download, Retry download, Remove download, by the button's `action`; a blocked one is a faint Download with why under it), Mark watched or unwatched, Add to or Remove from favourites where the library allows, a show's Binge, then the ways up `videoLinksOf` (`src/queries/itemLinks.ts`, read by `useVideoLinks`) finds: an episode's "Go to" its show and its season (the season once the show's page names it), a movie's "View saga" when its library lists it in one. Two renderers draw it, a `CardMenuKit` (`src/layouts/cardMenuKit.ts`): the TV's `CardMenu.focus` list, which `useTvCard` hands the menu, and the touch `CardMenu.touch`, which `useTouchCard` (`src/cardMenu/useTouchCard.tsx`, giving every touch card its `onLongPress` and `menu`) hands it: once the title is read it opens the system's sheet (`openPickerSheet`) with the options it can offer and the blocked ones' reasons as the message, then closes. Only the touch kits offer Download (`canDownload`, which the card menu and downloads kits of each kind take from `CAN_DOWNLOAD` in `src/layouts/downloadKind.ts`), and nothing reads `Platform.isTV` for it. A show's or season's card downloads every episode this device can take, filed under its first episode's library; a file with no page (a tutorials library's) downloads under its own name with its thumbnail (`fileTargetOf`). What a Download button or menu line stands for is a `DownloadTarget` (`src/downloads/downloadTargets.ts`: `movieTargetOf`, `episodeTargetOf`, `fileTargetOf`, `seasonTargetOf`, `showTargetOf`, `albumTargetOf`, `playlistTargetOf`, tested under bun), which `useDownloadButton` takes, with the library `useDownloadLibrary` (`src/queries/useDownloadLibrary.ts`) finds, on the pages and in the menu alike.
- **Playing a download:** the Player finds a done video (`downloadedVideoOf`) and plays its `file://` in direct mode (`localWayOf` in `playWay.ts`), from the server's spot when it answers within `LOCAL_PATIENCE_MS`, else the media the download kept; progress still goes to the server and fails quietly offline.
