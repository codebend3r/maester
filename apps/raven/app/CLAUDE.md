# Claude context for raven's device app

`@raven/app` is raven on iPhone, iPad, Apple TV and Android TV. The rules that apply to it are in the root `CLAUDE.md` and in `apps/raven/CLAUDE.md` ("App"); this file holds what only the app needs.

## Pins

- **`react-native` is `npm:react-native-tvos@0.88.0-0`.** The fork has no separate stable 0.88 tag: `0.88.0-0` is its stable release (npm's `latest` and `0.88-stable` tags point at it), the `-0` suffix is how the fork names every release, and its release candidates are `-0rcN`. Its peer is `react ^19.3.0`, so the app's React is the repo's `19.3.0`.
- **Expo is `58.0.14`, the version the spike ran.** Every other Expo package (`expo-keep-awake` `58.0.3` among them), and React Native's own (`react-native-screens`, `react-native-safe-area-context`, `@react-native-community/netinfo`), is pinned to the version Expo 58.0.14's `bundledNativeModules.json` names. `react-native-video` is `6.19.3`, the version the spike played HLS with. A bump moves them together: take the new Expo's list, never `expo install`'s ranges.
- **The root `package.json` overrides `react-native` to the fork for the whole workspace.** `react-native-reanimated`, `react-native-worklets` and `react-native-gesture-handler` arrive because bun installs the required peers of `expo-router`'s drawer (`react-native-drawer-layout`), and the first two take `react-native` `0.86 - 0.88`, a range that excludes a prerelease such as `0.88.0-0`. Without the override bun installs upstream React Native beside the fork. The override also pins gesture-handler to Expo 58.0.14's `3.3.0`, where the peer would otherwise float to the newest.
- **The app uses neither the drawer nor the JS stack**, so `expo.autolinking.exclude` in `package.json` keeps those three out of the native projects. They stay installed, since bun installs a package's required peers and the root has no way to skip one.

## Bun's package store

Bun links the workspace in isolated mode: each package sits in `node_modules/.bun/<name>@<version>/node_modules/<name>` and sees only what it declares. Two things in the store require `react-native` without declaring it, and find nothing there, because the fork's folder is named `react-native-tvos`:

- React Native's jest preset, loaded by jest-expo.
- The fork's own podspecs, which `require.resolve('react-native')` from inside the store during `pod install`.

So `test:screens` and the Apple prebuilds set `NODE_PATH=$PWD/node_modules`, the app's own `node_modules`, where `react-native` links to the fork. It is absolute because `pod install` runs in `ios/`.

`react-native-svg`'s podspec finds React Native's version by resolving `react-native` and reading `react-native/package.json` beside it; Node resolves the link to the fork's store folder, whose sibling is not named `react-native`, so the Apple prebuilds also set `REACT_NATIVE_NODE_MODULES_DIR=$PWD/node_modules`, the podspec's own fallback. Without it `pod install` fails with "no implicit conversion of nil into String".

The jest config in `package.json` also lets Babel through `node_modules/.bun`, as jest-expo's default lets pnpm's `.pnpm` through. Babel's output imports `@babel/runtime` from the app's own files, so the app depends on it directly.

## Intl and the shared layer

- **What Hermes has.** On the Apple TV simulator and the Android TV emulator, RN 0.88's Hermes has `Intl.getCanonicalLocales`, `NumberFormat`, `DateTimeFormat` and `Collator`, and they handle every option core passes. It has no `Locale`, `PluralRules`, `RelativeTimeFormat` or `DisplayNames`. So `src/polyfills.ts` loads formatjs's `getcanonicallocales`, `locale`, `pluralrules`, `relativetimeformat` and `displaynames` with their `en` data, in that order, and no `numberformat` or `datetimeformat`.
- **Hermes has no `Array.prototype.toSorted`** (it has `toReversed`, `toSpliced` and `with`), and core sorts with it, so `src/polyfills.ts` also installs `installToSorted` (`src/arrayToSorted.ts`) where the engine lacks it. Opening a grouped library crashed the Release build without it; jest runs on Node, which has it, so only a build on a simulator shows such a gap.
- **`polyfill.js`, not `polyfill-force.js`.** Each entry installs itself only when the engine lacks the constructor or its English data, so a Hermes that gains one keeps its own, and nothing is applied twice.
- **The `.js` subpaths.** formatjs's package `exports` list each polyfill and locale file only with its `.js`. Without it Metro warns and falls back to the files, so `src/polyfills.ts` is exempt from the no-extension import rule in `.oxlintrc.json`.
- **Metro reads `@raven/core` and `@raven/ui` through Bun's workspace links** to their built `dist`, so `start`, `test:screens` and the `prebuild:*` and `build:*` targets depend on `^build`, which builds both first (`app.config.ts` reads the launch colour from `@raven/ui/designTokens` too). Both are ES modules and `@raven/ui`'s peers resolve from its own `node_modules`, which link to the same store folders as the app's, so there is one React.

## Servers and sessions

- **The app holds each server's cookies, never the system.** Every call goes through `apiFor(server)` (`src/servers/serverClient.ts`), whose fetch (`serverFetch.ts`) sends `credentials: 'omit'`. On iOS and tvOS that turns off `HTTPShouldHandleCookies`, and on Android OkHttp gets no cookie jar, so the shared store neither keeps nor sends anything. The app adds both of core's `SERVER_COOKIES` (`raven_unlock`, then `raven_admin`) from its own jar and applies what `set-cookie` says back, both only for the server's own `/api/`, the cookies' path: a media origin never gets them, and a response a redirect took elsewhere (its `url`) sets nothing. React Native follows redirects natively with the headers it was given and has no `redirect: 'manual'`, so the request itself cannot be held back; raven's API never redirects.
- **Sign-in asks what the web asks, then what the server asks.** The account's email and password go to Supabase through the fixed raven server's public auth config, then the PIN when `getLock` says the server has one, then the admin password only when `getAdminLock` says the legacy admin lock still holds. Each secret step has Not now and Sign out, and the last step goes back down to Home (`dismissTo`) rather than stacking another. The app calls `unlock` and `unlockAdmin` (both `@ForViewers()`) and never an `@AdminOnly()` route. An end to end build sets `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN` to its accountless fixture and begins at the PIN.
- **`set-cookie` arrives folded.** React Native hands several `Set-Cookie` headers over as one value joined with `, `, and an `Expires` date holds a comma too, so `readServerCookies` splits only at a comma followed by `name=`. A cookie with an empty value or `Max-Age=0` is cleared and leaves the jar; the last word on each one wins.
- **Everything that must last is in `expo-secure-store`.** Each server's cookies are one JSON value under `raven.cookie.<serverId>`; the server list and the active id are one JSON value under `raven.servers` (`src/servers/activeServerStore.ts`). Both are guarded when read. The keychain on Apple keeps them on tvOS too, where AsyncStorage's caches folder may be emptied, and the keystore keeps them on Android. Only the player prefs, Settings' prefs (`useAppPrefs`) and the library views (`useLibraryViews`) are in AsyncStorage. `AppRoot` loads every store before any route renders.
- **A failing keychain degrades, never fails.** A store call that throws reads as empty and saves nothing, so the app works for the run and forgets on relaunch.
- **Simulator builds are signed ad hoc.** The keychain refuses an app with no signature ("A required entitlement is not present"), so `build:ios` and `build:tvos` pass `CODE_SIGN_IDENTITY=-` rather than turning signing off.
- **The fixed server id names its secure-store keys.** `RAVEN_SERVER` keeps one valid UUID for the server list and cookie jar, so its PIN survives a relaunch. A real build pins that server while stores load; an end to end build leaves the fixture absent until both legacy unlocks have passed.
- **The jar's changes take turns per server.** Two responses that set cookies at once each read what the one before left, so neither writes over the other.
- **Plain http is for the development variant.** `APP_VARIANT=development` at prebuild sets `NSAllowsLocalNetworking` and Android's `usesCleartextTraffic`. Expo's template allows local networking in every build, so `app.config.ts` writes the whole `NSAppTransportSecurity` dictionary, which a release build keeps strict. Debug builds against Metro need the development variant too. The fixture build also sets `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN=http://127.0.0.1:8490`, which Expo writes into its bundle.
- **A form's buttons take a tone,** the web's `Button` tones: `primary` for the one action a step is for, `quiet` (a moss fill) for another way on, `ghost` (no fill) for a way out. Focus turns any button's edge to the text colour, drawn twice as thick on a TV (`SIZES.tvFocusRing`). Every control has the web's `--radius-md`; tvOS draws a focused text field as its own pill-shaped plate, so the TV field clips it to that radius. Android's text input pads itself top and bottom, so the TV field sets its own and lines up with the plate buttons beside it, its 1 pt edge aside.
- **Menu on tvOS's keyboard cancels the edit.** The native field goes back to what it held, but React Native reported every key as it was typed and reports nothing on the cancel, so the TV field takes the text it ends editing with (`onEndEditing`) as the field's value: what it shows is what Continue sends. Sign-in's fields and the search box are one TV field, `TvTextField` (`src/layouts/tvControls.tsx`).
- **React Native prop values are written inline** (`behavior="padding"`, `returnKeyType="go"`): each prop's own union type checks them, as an `as const` object would.

## Queries, pictures and events

- **One query client for the app's life, emptied on a server switch.** `AppRoot` wraps the routes in `QueryClientProvider` with headless `createQueryClient()`, and `clearOnServerSwitch` (`src/queries/serverCache.ts`) calls `clear()` from inside zustand's `set` whenever the active id changes, before React renders again. Every server answers under the same keys, so this is what keeps one server's answers off another's screen. A client keyed per server would remount the navigator on the activation in the middle of sign-in. TanStack binds each `useQuery` observer to the client it first saw, so a screen that reads a server reads it through `useAppQueries()`, which re-renders it on a switch and builds fresh queries; Home also keys its body on the server id.
- **`useAppQueries()`** (`src/queries/useAppQueries.ts`) gives the active server's `api`, `ravenQueriesFor(api)` and `useServerEvents`, made once per server (`lastPerServer`). The folder is `queries/`, not `data/`: the root `.gitignore` ignores every `data/`, raven's `DATA_DIR`.
- **A 423 opens `/unlock`.** `createQueryClient` raises the headless unlock prompt on a refusal for a locked library; `useUnlockRoute` closes it and pushes the PIN screen, which calls `unlock`, invalidates every query and goes back.
- **Pictures are React Native's `Image` with the server's cookies.** Posters, backdrops and thumbnails are on the API (`PrivateBy`, not the media plane), so a locked library's need the cookie, and `cookieHeadersFor` adds it for the server's own `/api/` only. `expo-image` would add a native module for caching the versioned URLs do not need yet.
- **The jar says when it changes.** Every write or forget bumps `useCookieVersion` (`src/stores/cookieVersion.ts`), and `useServerCookies` reads the jar again on each bump, so pictures carry a new unlock cookie at once. A card remembers which picture and headers failed, so new headers ask again.
- **Server events ride `react-native-sse`**, adapted to headless `ServerEventSource` by `eventSourceFor` (`src/servers/eventSource.ts`). It opens once the jar has read the cookies and passes them as headers. The library retries only an error status, never a refused or reset connection, so the adapter reopens after every `error` itself (1 s, doubling to 30 s, back to 1 s only once a connection has held for 5 s, so a proxy that accepts and resets each one is not asked every second), closes in the background and opens again on return (telling headless it dropped, so it reads everything again), and keeps the stream through `inactive` (Control Center, a call), which is not the background, and never holds two connections or any after `close`. The library's XHR keeps React Native's default `withCredentials = true`, so the system jar is consulted for the stream; it stays empty, since every other request omits credentials and `/api/events` sets no cookie. `AppRoot` mounts the stream once per active server.
- **A library has two pages.** `/library/[id]` (`LibraryPages` in `src/screens/Library.tsx`) opens on Continue watching, the library's own `GET /api/libraries/:id/in-progress` as wide cards like Home's shelf (`continueSectionsOf`), while anything in it is in progress, so a show is picked up in one press; with nothing in progress, or handed a search (`?q=`), it opens on the library itself, the listing sorted, laid out and searched as before. One `ToolButton` first in the toolbar, named for where it goes ("Library", "Continue watching"), is the press between them; the choice lasts while the page is open. Both pages wear the library's icon beside its name (`GridProps['icon']`, `libraryIconOf`, the same the side menu's pinned row wears).
- **A library's sort, view and grouping are this device's.** The web saves a viewer's change to the server (`PUT /api/libraries/:id/view`, `@ForViewers()`) for everyone, but that write is not one of the spec's, so `APP_CLIENT_CALLS` leaves it out. `useLibraryViews` (`src/stores/libraryViews.ts`) keeps a choice per server and library in AsyncStorage, guarded when read; the screen lays it over the server's settings and passes both through core's `coherentSettings`, so a choice the library's type cannot show gives way to its own.
- **Pickers are the platform's.** Touch screens (only iPhones and iPads) use `ActionSheetIOS`, a popover anchored on the chip on an iPad; tvOS has none (React Native builds `RCTActionSheetManager` out of it), so TVs use a `Modal` list with focus on the current option, closed by Menu or Back.
- **A list on a TV needs a height of its own.** The fork wraps a `FlatList`'s ScrollView in a `TVFocusGuideView` that takes no style, so `flex: 1` never reaches it and the list draws 1 pt tall. `Grid.focus` measures the room under its header and draws the list only once it has it, which also lets the first card mount asking for the focus and take it.
- **Moving the remote's focus on purpose.** `hasTVPreferredFocus` on a view that mounts asks before the view is in the window, and the fork's retry for that takes only the first time, so a card a jump lands on calls `requestTVFocus()` once mounted (`src/layouts/tvFocus.ts`, a guard, since the fork adds the method outside React Native's types). It does so once per jump: `useJumpFocus` asks only for a jump count newer than the grid's handled one, so the card never pulls the focus back as it mounts again (scrolled back to, its bucket reopened, a new sort). A view the remote must start on as it mounts (a form step's first field, the search screen's field, the player's catcher) also asks once mounted, through `useFocusOnMount` (`src/layouts/focus.ts`): on Android TV `hasTVPreferredFocus` alone left a sign-in step with nothing focused. Preferred focus is for the opening only, until anything on the screen has had the focus (a card, or a control in the header, whose focus bubbles up to it), so a card drawn later, after a sort, once a search finds some, or when Home's shelves are read again, leaves the viewer where they are.
- **One screen's focus is one store.** Each TV screen's opening focus and its opener live in `useScreenFocus` (`src/stores/screenFocus.ts`), by the route's key (`useRoute().key`), since the layout and every card on the screen read them. `src/layouts/focus.ts` holds the hooks: the screen's outermost focus layout (`Shelves`, `Grid`, `ItemLayout`, `SearchLayout`, `SettingsPage`) takes `useScreenFocusScope()` once, which gives its `isOpening` and `settle` and forgets the screen with the layout; a part inside it (each `Shelf`) reads `useOpeningFocus()`.
- **Going back lands on the card that opened the screen.** A `FocusCard` or a grid's `RowCard` calls `useOpenerFocus`'s `remember` as it is pressed, under its `place`, unique on the screen: the card's key in a grid or on an item page, the shelf's key and the card's on a shelf, since one title can sit under Continue watching and on its library's shelf. When the screen comes back to the front (`useIsFocused` turning true, never on a mount), the card remembered calls `requestTVFocus()` once. The opener lasts through the one cover its card opened: the next time another screen covers this one, the screen's scope (`coverScreen`) lets go of an opener no card took, so a later return from a screen no card opened (Search, See all, Play) asks for nothing, whatever order the cards and the scope hear the return in. tvOS restores the focus to the view that had it when a native stack screen comes back (`restoresFocusAfterTransition`), and the request agrees with it; it is what still lands on the card when its view mounted afresh while the screen was covered (its shelf or bucket drawn again) and what Android TV, which restores nothing, relies on. Each card tells the store as it is drawn and as it goes (`drawCard`), so a return whose opener's card has gone (its shelf went while the screen was covered, as Continue watching does once a spot is cleared) gives the screen its opening focus again rather than leave the remote on nothing. That waits for the navigator's `transitionEnd` on the screen (`returnScreen`, which `AppRoot`'s `screenListeners` call): on Android TV the transition that reveals a screen takes the focus from whatever was asked for before it ended, and only `react-native-screens`' own restore of the view that had it, which is gone here, survives.
- **Rows are focus bands.** Each shelf's row of cards and each part of a TV item page (the heading with its actions, the seasons or episodes with their heading, the versions, the cast) sits in a `FocusBand` (`src/layouts/FocusBand.tsx`), the fork's `TVFocusGuideView` with `autoFocus`, as wide as the screen. Down or Up into it from anywhere lands on its first control, then on the one the remote last left there; without it tvOS moved by geometry, and Down from a show's Play, which sits right of the poster, skipped the seasons' first card for the cast below. A shelf's title row, with a library's See all, stays outside its band, so Down or Up into the band lands on a card, not on See all; the remote reaches See all by geometry, as before. A band never holds a `FlatList` (see the list height above); jsx-a11y's `no-autofocus` is set to `ignoreNonDOM` in `.oxlintrc.json`, since the prop is the guide's, not the DOM's.
- **Menu is the navigator's.** The fork leaves its Menu recognizer off unless `TVEventControl.enableTVMenuKey()` turns it on, so UIKit has the press: the native stack (`react-native-screens`' `UINavigationController`) pops the screen on top, AVPlayerViewController first hides its transport or a panel, the TV picker's `Modal` closes, and on Home, the stack's root, the press goes on to tvOS, which leaves raven for the home screen. The app neither turns the menu key on nor listens through `BackHandler`, and `.oxlintrc.json` refuses either import from `react-native` anywhere in it: either would take the press from UIKit, so Home could not leave and the player's own Menu would break. Android TV's back button reaches React Navigation's own `BackHandler` listener, which pops or, at the root, leaves the app.
- **The touch jump strip fits its slot.** Each mark gets the web's share (a 27th of the room, at most 40rem over 27) and never less than a finger can press; where they cannot all fit, as on a phone held sideways, neighbouring marks are gathered into one (`src/layouts/jumpMarks.ts`). Rows, bucket headings, captions and the strip's marks grow with the viewer's text size (`linesHeightOf`), and the grid and strip keep clear of the side insets.
- **A card goes where the web's would.** Each card carries a `RouteTarget` (`src/routes.ts`), read off core's `cardDestination`: a matched video's item page, naming its library and, for a card a movie was split onto, its file (`/item/[id]?library=&file=`, the web's `?library=` and `?file=`), or the player for a file with no page; a show's page names neither. The item page keeps to that library's files and card through core's `libraryFiles`. Play and Resume push `/play/[mediaId]` with `?at=` set to the spot the page shows (`secondsOf` reads it back); a card or a version row names none, and the player starts where the server last saved, by core's `resumeAtFor`, the web's and the desktop's rule.
- **Item pages mark through the headless hooks that take the client.** The app holds several servers, so it calls `useServerMediaMutations`, `useServerWatchedToggle` and `useServerItemFavourite` with the active one's `api`; a hook picked off the session object at render is not one the hooks rule accepts. A movie's or an episode's Watched and Favourite show at once (their edits patch the item's page); a show's or season's Watched waits for the server, as on the web. On a TV the page's first action, Play or Resume, takes the remote's focus as it opens and lets go once anything on the page has had it, so a button that changes after a mark leaves the viewer where they are. While a show's next episode is read (`isPlayPending`), a TV draws no action and no row, so Play is there from the first and nothing else is on screen for tvOS to give the opening focus to; under the thumb the marks are drawn at once and Play once it is known, as on the web. The TV's cast tiles take the focus only so the row scrolls; they stay inert until the app has a person page. An episode's page adds Next (`nextOf`, "Next S01E02"), the episode after it in its show as `GET /api/media/:id/next?session=show` names it (`nextInSessionQuery`, which a film never asks), and on a row of its own below (`links`, so neither row runs off a TV's screen) the links up (`ITEM_ACTIONS.link`, the ghost tone, read as a link): "Go to" its show, and "Go to" its season once the show's page, read for the backdrop anyway, has said which item that is, since an episode names its season only by number. Every action is its icon (`ItemAction['icon']`, the web's drawings through `Icon`) with its few words beside it where it has any (`text`: Resume's spot, Next's code, a link's name), and a mark on is filled in the primary tone rather than ticked; the label read aloud says the whole. An episode's hero wears its show's title art (`ItemHero['logo']`, larger than the player's) over its place in short, `episodeMarkOf` ("S02 · E05"; "Special 5"), which the player's heading uses too; without art the show's name stands in the eyebrow.
- **Every search box is headless `useSearch`'s**, as the web's are: it asks once typing pauses for core's `SEARCH_DELAY_MS` or at once when the keyboard sends it, never on each key, and a cleared box asks nothing (headless's `homeSearchQuery('')` is a `skipToken`). The layouts' `SearchField` draws it: under the thumb with the keyboard's Search key and a clear button, `/search` opening with the keyboard up on its field, on a TV as a field the remote selects to open the platform's keyboard, taking the text it ends editing with as sign-in's field does. `/search` searches every library through `homeSearchQuery` and lays out what it finds as Home's library shelves (`libraryShelvesOf`, over core's `withLibraries`), whose See all opens the library on the search (`?q=`, as the web's link does). A library's own box is the web's: the server searches (`listMedia` and `listShows` take it as `q`), so no call joins `APP_CLIENT_CALLS`. On a TV the search screen opens with the remote on its field, once, and Home draws its Search and Settings entries only with its shelves, so the first card keeps the opening focus. "Nothing matches" waits for the server's answer to this search: while it is read, the last search's answer stands in (`keepPreviousData`) and says nothing of this one.
- **TV layouts are drawn for 1920 points and sized to the screen.** Apple TV's window is 1920 by 1080 points; a 1080p Android TV's is 960 by 540 dp, where every card, row, gap, font and ring would stand twice as large. So the TV layouts (the `.focus` variants, `FocusCard`, `tvControls`, `PlayerNotice.focus`, `PlayerChrome.dpad`) take their lengths from `TV_SIZES` and `tvSize` (`src/theme/tvSizes.ts`), the shared scale times `tvScaleOf` (`src/theme/tvScale.ts`, tested under bun): the window's width over `TV_DESIGN_WIDTH`, read once since a TV's window keeps its size. It is 1 on Apple TV, so nothing there moves, and the touch layouts never read it. The card picture, used by both, takes its corner `radius` from the caller, and the caption its `fontSize`. The forms' shared styles are made at each scale (`useTouchFormStyles`, `useTvFormStyles` in `formStyles.ts`), and each form kit carries its own hook as `useFormStyles`, whose lines (`note`, `notice`, `error`) sign-in and the PIN screen draw, so on a TV every length the app draws is sized to the screen.
- **Motion follows the system.** `followReduceMotion` keeps `useReduceMotion` in step with `AccessibilityInfo`; a focused TV card grows to 1.08 over 150 ms only when motion is allowed, and at once otherwise.

## Playing

- **What a platform plays is a table.** React Native has no `canPlayType`, so `canPlayFor(platform)` (`src/platform/canPlay.ts`) answers core's `planPlayback` from the platform's table, matched against core's own MIME and codec strings. `platformOf` (`src/platform/platform.ts`) takes `Platform.OS` and `Platform.isTV` as arguments, so both run under bun. Apple's table is MP4 or MOV, 8-bit H.264 or HEVC at any depth, and the audio in core's `HLS_COPY_AUDIO`; AVPlayer has no High 10 decoder and a remux copies the video, so 10-bit H.264 goes straight to the transcode. HEVC in MP4 or MOV is a maybe, since a file tagged `hev1` refuses and the index keeps no tag: while the viewer prefers direct play it counts as a yes and a refusal steps down to the remux, which re-tags it `hvc1` (see Settings). Android TV's is ExoPlayer's, the spec's generous start: MKV, MP4, MOV or WebM; 8-bit H.264 (as on Apple, since few TVs decode High 10 and a remux copies the video), and HEVC, AV1 and VP9 at any depth; AAC, AC-3, E-AC-3, Opus, Vorbis, FLAC and MP3, and DTS and TrueHD as a maybe, which counts as a yes as a browser's does while the viewer prefers direct play: the planner offers the original file with the remux after it, and a refusal steps down to the remux, whose audio the server makes E-AC-3. The names are core's `CONTAINERS`, `VIDEO_CODECS` and `AUDIO_CODECS`.
- **ExoPlayer refuses audio by leaving it out.** Given a track it can neither decode nor pass through, it plays the picture alone, or another of the file's tracks, and reports no error, so the ladder would never step down. `isAudioDropped` (`src/player/droppedAudio.ts`, tested under bun) reads the audio tracks the player lists, each saying whether it was picked. `react-native-video` 6.19.3 hands ExoPlayer the asked track (`selectedAudioTrack`) only as it loads, and the selection takes effect later on the playback thread, so `onLoad` still reports ExoPlayer's own first pick; `onAudioTracks` reports the settled one. ExoPlayer also starts its progress before it reports the load, so ticks come before the settled pick. `hearAudio` (in the same file) keeps the last list for the attempt and says when to judge it, once, at a progress tick: at once when the load's pick is already the asked one, and otherwise only after an `onAudioTracks` since the load, or once `AUDIO_SETTLE_SECONDS` (2 s) of play have passed with none, counted between ticks so a seek's jump never counts (the screen tells it of each seek): on Android TV in direct play, when the track asked for (by its place, or any track where the player was left to choose) is not the one playing, and a way is left below (`hasWayBelow`), the play counts as failed and steps down to the remux from the spot. A forced original with no way below plays on, sound or none. A stream is never asked, since it carries only the track the session asked for, and Apple never, since its table names only audio AVPlayer decodes. The Android TV emulator (API 36) decodes no AC-3, E-AC-3, DTS, TrueHD or ALAC: there a TrueHD MKV stepped down to the remux, which plays without sound, and the fixture film, whose English track is AC-3, played its AAC commentary directly when no audio language was preferred. A real TV decodes or passes most of them through.
- **The player plans through `planFor`** (`src/platform/playbackPlan.ts`, tested under bun), which calls core's `planPlayback` with the platform's table and `defaultAudio: true`, since direct play switches audio tracks itself, under the server's policy narrowed by Settings' prefs (see Settings), and then applies Ruling 22 wherever the chrome draws no cues (`shouldDrawCaptions` false, which the screen passes in: Apple TV's system transport; Android TV's chrome draws them): a file with any text subtitle track (a sidecar or an embedded one; picture tracks have no rendition) drops direct play while another way is left, so it starts at the remux, whose subtitles are HLS renditions the system's player lists and draws. The fact lives once, in the chrome kit, so the plan and the subtitles never disagree. Direct play stays when it is the only way (the server converts nothing, or forces the original). It needs the tracks, which core's planner never sees, so it lives in the app and core's contract is unchanged; `DEVICE_PLATFORM` (`src/platform/devicePlatform.ts`) names the platform.
- **`canStream` answers for the HLS route.** The planner asks it about `streamMimeType`'s fragmented MP4. The app plays a remux or a transcode through HLS, never Media Source Extensions, and HLS audio is copied or made E-AC-3, so `canStream` is `canPlay` on every platform: a stream plays where its video plays in MP4, and both tables play MP4 and the stereo AAC `streamMimeType` names. On Android TV every video the server copies (H.264, HEVC, AV1, VP9) plays in a stream; the one audio a stream may carry that ExoPlayer's table leaves out is ALAC, which the route copies (a test pins both). That is a known gap: a remuxed ALAC file may play silent on a TV with no ALAC decoder, and `canStream` cannot see it, since `streamMimeType` names stereo AAC whatever the stream carries. The fix is the server's (make ALAC FLAC or E-AC-3 over HLS, or say what the stream carries), a follow-up outside the app.
- **Media goes by ticket.** `mediaAccessFor` (`src/servers/mediaAccess.ts`) gives the player a `{ uri, headers }` per mode: direct is core's `fileUrl`, remux and transcode its `hlsUrl` master playlist. It probes `getMediaOrigins`' origins (those core's `serverOriginOf` accepts, each given core's `MEDIA_PROBE_TIMEOUT_MS`) on first use and on each change of network, plays from core's `pickOrigin` (a transcode from a `public` origin asks the away cap's `quality`, see Settings), holds no probe that picked none (the next source probes again, so an origin that comes back is used), and renews each video's ticket core's `MEDIA_TICKET_RENEW_MS` after it was read, by the app's clock, never from `expiresAt`, as the web and the desktop do. A refusal is core's `AccessRefusal` (a 423 is `locked`). The probe, the network watch and the jar are passed in, so it runs under bun: `probeFetchOf` (`mediaProbe.ts`) times a whole ping, since React Native's `fetch` answers only once the body has come, and `watchNetwork` (`networkChanges.ts`) is NetInfo's, with NetInfo's own internet check, which asks Google, turned off. Nothing logs a ticket; it is only ever in the source's address.
- **A signed-in account plays by its ticket.** `getMediaTicket` with the Bearer is an account ticket under `ready` (`apps/raven/CLAUDE.md`, the media plane), so `mediaAccessFor` needs no other mint. The source it hands out carries no header: no cookie, no Bearer. With no origin to play from, a signed-in account (`readAccessToken` is not null) plays from the server's own address with the ticket in `?t=` (`ownAddressSource`), never by its Bearer, which the native player would send as it was long after the token ended. A `401` or a `403` to the ticket (the fetch has already refreshed the token once) is core's `account` refusal in raven player's words, `accountAccessMessageOf`: "Sign in to X again." or "Your access to X was removed."; accounts being down (`unavailable`) is `unreachable`. An HLS master opened with the ticket gets the server's capability for its session, so a stream outlives the ticket's five minutes, and a direct file's ticket earns a pass for that file, so a play longer than five minutes needs no new one; what the server then lets go of is reopened (below).
- **The cookie is the fallback without accounts.** A server that lists no origin, has none answering, or answers the ticket 503 (no `RAVEN_MEDIA_SECRET`, which sign-in tells the viewer in the spec's words) plays from its own address with `cookieHeadersFor`'s headers. `react-native-video` 6.19.3 hands them to AVPlayer as `AVURLAssetHTTPHeaderFieldsKey` on the asset, an undocumented key AVFoundation applies to every request the asset makes, playlists and segments included, and to ExoPlayer as the OkHttp data source's default request properties, so one header covers direct play and HLS alike. It also passes the system's cookie store as `AVURLAssetHTTPCookiesKey`, which the app keeps empty; that the header survives beside it is still to be checked on a device. The playlists' URIs are absolute paths on that same address, so the cookie never leaves the server's API.

- **The ladder is a reducer** (`sessionReducer` in `src/player/usePlaybackSession.ts`, tested under bun). It starts at the plan's first mode and asks `mediaAccessFor` (made once per server by `src/player/mediaSources.ts`) for that mode's source; it steps down to the next mode from the spot the player had reached when the player reports `onError`, or, while a mode is left below (`hasWayBelow`), when `onLoad` has not come `LOAD_TIMEOUT_MS` (15 s) after the source was handed over. The last mode is never timed out: a software transcode on a NAS can take longer than that for its first segment, and the server waits for one up to `HLS_SEGMENT_WAIT_MS`. A remux the server refuses (its 409, keyframes too far apart) is such an error: AVPlayer gives no HTTP status to tell it apart, and the transcode is the next mode anyway. Each source is an `attempt`, and an event for an earlier one changes nothing. A plan with no mode shows the plan's problems, or plain words when it has none; a ladder run out says so first and then gives the plan's problems, as the web does; both with Back. **The server letting go of a source is no failure.** The screen's `onError`, shared by every chrome, asks `isServerDrop` (`src/player/playerErrors.ts`, tested under bun) whether the player's error carries an HTTP 401, 403, 404 or 423, read from AVPlayer's code (`URL_ERROR_HTTP_CODES`: on the iOS 27 simulator a forgotten HLS session failed, after about eighty seconds of AVPlayer retrying its segment and then its video playlist, as `NSURLErrorDomain` -1100; `CORE_MEDIA_HTTP_CODES`, the undocumented -12938, -12660 and -12937 its error log names) or from the response code in ExoPlayer's cause (`EXO_ERROR_CODES.badHttpStatus`); then the session gets `dropped` in place of `failed`. AVPlayer never reports a direct file's refused ranges (401): it retries them for a dozen seconds and then stalls for good, so a direct play that waits for data `STALL_REOPEN_MS` (10 s) with its clock standing still, neither paused by the viewer nor ended (AVPlayer says it waits at a file's end too), is `dropped` too; a stream's stall is left to its player, which reports the 404. That is the safety net for a file pass that ended: the server keeps a ticket opening its file past the ticket's five minutes. A `dropped` source that was playing opens the same mode again from the spot with a source handed out afresh: an HLS session the server ended or forgot (its 12 h deadline, an account recheck, the session cap, a restart) answers 404, and a direct file whose pass ended 401 (or stalls, on Apple), and each plays on, the reopen's refusal (a revoked account's 403 at the ticket) being the only thing shown. One dropped before it loaded, or again before it played on from where it was reopened (`reopenedAt`), steps down as any failure. A refusal shows its message; a `locked` one raises the headless unlock prompt, so `useUnlockRoute` pushes `/unlock` as for any 423, and the session asks again once the jar's cookies change.
- **Progress is the web's.** The player's events drive headless `videoReducer`, and headless `useProgressReport` (the web's `useWatchProgress` hook, lifted with its rules into `watchProgress.ts`) reports from that state to `progressSinkFor` (`src/player/progressSink.ts`): `recordPlay` once frames first flow, `saveProgress` once the clock is `SAVE_EVERY_S` (10 s) from the last save, on a pause and at the end, when the app goes to the background (`AppState`, as the web's `pagehide`) and on leaving, and after the last save has landed, headless `afterWatching` reads the item, its library, Home and Continue watching again. The server counts the play watched at the library's watched percentage from the saved spots, as for every client, so the app never compares the percentage itself. Every call is the allowlisted `ApiClient`'s.
- **Tracks by mode** (`src/player/playerTracks.ts`). The pickers list core's `audioLabel` and `subtitleLabel` for the file's audio tracks and its text subtitles, and the first picks are headless `preferredAudio` and `preferredSubtitle` from the player preferences, which a pick by hand updates. Direct play switches among the file's own audio tracks through `selectedAudioTrack`, by their place among AVPlayer's or ExoPlayer's, which keep the file's order; a stream (remux or transcode) carries the one audio track the session asked for, so picking another reloads the master playlist from the spot with `audio=`.
- **Under the thumb and on Android TV raven draws the subtitles, in every mode** (`shouldDrawCaptions`, which the layouts' index exports with the chrome), as the web's player does, so on both a file with subtitles plays as it is: headless `useTrackCues` reads the picked track's cues from the server's WebVTT route through the allowlisted client (a window at a time for an embedded track, whole for a sidecar), core's `activeCues` picks those showing at the clock, and the chrome draws them with core's `cueRuns`. The player's own text tracks stay off (`selectedTextTrack` disabled). On the iOS 27 simulator AVPlayerLayer drew no HLS rendition it had selected, though its legible output had the cue, and `react-native-video` 6.19.3 reports a cue's text but never its end (it drops the empty update), so the cue would stay on screen; and a sidecar sideloaded as a `textTracks` entry made AVPlayer play a composition of the file's first video and audio tracks that drew nothing and turns AirPlay off. Drawn by raven, a sidecar plays in direct play with every audio track and AirPlay intact. Picture in Picture and AirPlay show no subtitles, since they leave raven's view.
- **Picture in Picture and AirPlay.** `enterPictureInPictureOnLeave` and `allowsExternalPlayback` are on, and the chrome has a Picture in Picture button. PiP needs the audio background mode, which `react-native-video`'s config plugin sets (`enableBackgroundAudio`); `playInBackground` stays off, so leaving the app without PiP pauses. `ignoreSilentSwitch="ignore"`, so the silent switch never mutes a film. `expo-keep-awake` keeps the screen on while frames flow.
- **On Apple TV the system draws the subtitles.** AVPlayerViewController on the tvOS 27 simulator draws a selected HLS WebVTT rendition in the system's own style, sidecar and embedded alike, and takes it off when the cue ends; its Subtitles panel lists the master playlist's renditions by the server's names (`English (File)`). So `shouldDrawCaptions` is false there: the screen's `captionsFor` reads no cues, and picks the preferred track's rendition by its place among the text tracks (`subtitlePlaceFor`, the master's order) or, with subtitles off in the preferences, leaves the choice to the system (forced tracks, the system's subtitle settings). A pick in the panel is the system's: it is not written back to the preferences, and a reload (a step down the ladder) picks the preferred track again.
- **The screen is the same on every platform; the chromes own the video.** `Player.tsx` hands the chrome a `VideoSurface` (`src/layouts/playerKit.ts`, `react-native-video`'s own props): the source, the events, `paused` and the track picks. Each chrome draws the `Video` with what only its platform takes: the touch chrome turns `controls` off and adds Picture in Picture, AirPlay and `ignoreSilentSwitch`; Apple TV's turns `controls` on and adds the info panel's metadata; Android TV's turns `controls` off. The two TVs differ only here, so the layouts' index picks the chrome by `DEVICE_PLATFORM` (`PLAYER_CHROMES`) where every other layout goes by `Platform.isTV`. What the chromes share is beside them: `PlayerNotice.focus.tsx` (both TVs' page while there is nothing to play), `PlayerCaption.tsx` (the cues raven draws, touch and Android TV) and `playerKit.ts` (the scrubber's share and its screen reader actions).
- **Apple TV's chrome** is `src/layouts/PlayerChrome.focus.tsx`: the video under AVPlayerViewController's transport (`controls`), which the Siri Remote drives (a swipe or a press scrubs, a click on the edge skips ten seconds, the info panel and the Audio and Subtitles panels), with nothing of raven's over it, so the transport owns the focus. The info panel shows the title, the synopsis (the item's `summary`, which the screen reads before it hands over the source, since a source that changes once playing reloads the video) and the poster or frame grab, passed as the source's `metadata`. `react-native-video` fetches that picture with `URLSession.shared` and no headers, so a locked library's shows none. The stream carries one audio track (the server's master lists no audio renditions), so the Audio panel offers only it; direct play lists the file's own. Menu leaves the player, hiding the transport bar or a panel first when one is up, and the leave saves the spot. While it opens, the player shows the loading screen (`Loading`, the mark and a spinner, with Back under the thumb); while there is nothing to play (refused, no way left) the title art (`PlayerNotice`, the show's or a film's own, from `usePlayerHeading`), its place and name, and the line stand centred on the screen with Back, a `PlateButton` that takes the remote's focus once.
- **Android TV's chrome** is `src/layouts/PlayerChrome.dpad.tsx`: raven's controls over ExoPlayer, driven by the d-pad through the fork's `useTVEventHandler` (one listener for the chrome's life, which reads the latest answer, since the hook subscribes again whenever its listener changes). The fork's Android helper sends a press only as the key coming up (its key-down events are off unless a feature flag turns them on) and a key held past 300 ms as its long name (`longRight`), once down and once up, so `pressedKeyOf` (`src/layouts/remoteKeys.ts`, tested under bun) counts a key as it comes up, one skip per press: the emulator showed nothing at all while it counted key-downs. A held left or right is a hold (`heldSeekOf`): while the key is down the playhead runs, faster the longer it is held (`holdStepOf`, through `holdReducer` in `heldSeek.ts` and the `useHeldSeek` hook), and the video seeks there once as it comes up. The fork types the action as a string, but Android sends its `KeyEvent`'s, a number. `remoteAnswerOf` says what a press does. The title is along the top; along the bottom the time and the scrubber, then Play or Pause, the audio and subtitle pickers (the TV's `Modal` lists) and Back, each a plate showing the web's icon (`PlateButton`'s icon face) and said by its name. The title along the top is the show's title art (or its name), its season and episode, then the episode's name with its length in a chip (`usePlayerHeading`). The scrubber takes the remote's focus once each time the controls appear (`hasTVPreferredFocus` until it has had it, which is what takes while the screen slides in, and `requestTVFocus` whenever the controls turn visible, including a press that catches them fading out, while they are still drawn and the hidden state's catcher, which held the focus, goes), and while it has it, left and right seek ten seconds (`SKIP_SECONDS`) and a press plays or pauses; on the buttons, left and right move the focus. Rewind, fast forward and the play keys work wherever the focus is. A seek before the video has loaded is not taken, since the player would lose it. The controls fade after `controlsLingerSeconds` while the video plays, over 200 ms or at once when the system asks for less motion, and are drawn until the fade ends; they stay up while it is paused, opening or ended, and while a picker's list is open (the TV picker's `onOpenChange`), since hiding them would close it. Hidden, a full-screen button holds the focus, because Android hands a key to no view when none is focused; any key brings the controls back, and left and right still seek. The cues sit above the controls while they show and near the bottom once they go. Back, the hardware key or the button, leaves the player, and the leave saves the spot. An episode's Next (`PlayerChromeProps['next']`, between Pause and the pickers, said as "Next episode S01E02 Half Loop") plays the show's next in turn in this video's place (`router.replace`, so Back still goes to the page that pressed Play), and with the player preferences' `autoplay` on (its default) the next plays by itself as this one ends; off, the controls stay up on Next. The touch chrome offers the same as a tool button; Apple TV's system transport has no place for it yet.
- **The touch chrome** is `src/layouts/PlayerChrome.touch.tsx`. ## Settings

- **`/settings` keeps to the device** (`app/settings.tsx`, `src/screens/Settings.tsx`, laid out by `Settings.touch` and `Settings.focus` over `settingsKit.ts`). It asks no server anything, so `APP_CLIENT_CALLS` is unchanged. Under the thumb it opens from a gear (`SETTINGS_ENTRY`, U+2699 with the text presentation selector, so no emoji) beside Search in Home's header; on a TV from a Settings plate beside Search in Home's top row. The TV layout takes every length from `TV_SIZES`, and its switches are plates that say On or Off (`accessibilityRole="switch"`), since tvOS has no switch. The theme and the away cap are `SettingsChoice` rows, laid out as the toggles are (the label at the start, the value at the end), opening the `Picker`'s own list: `openPickerSheet`'s action sheet under the thumb, `PickerList`'s `Modal` list (`usePickerList`) on a TV.
- **Account.** Settings shows who is signed in and a Sign out, which clears the account session (`useAccountSession`) and sends the viewer back to sign-in. The app talks to the one server in `src/servers/ravenServer.ts`, so there is no list to manage.
- **The prefs are `useAppPrefs`** (`src/stores/appPrefs.ts`): the theme (core's `THEMES`, which every screen wears: see Themes), prefer direct play, allow transcoding and the away-from-home maximum height (core's `MAX_HEIGHTS`, the heights the server's own cap offers: 2160, 1080 or 720 lines, 1080 by default, the server's own default). They are one JSON value in AsyncStorage under `raven-app-prefs`, losable as the player prefs are, and each value read back is guarded on its own: one the store cannot use falls back to its default and the rest stand.
- **The prefs narrow the server's policy and never widen it.** The player reads the two playback choices and passes them to `planFor` as `prefs`, and the away cap reaches `mediaAccessFor` as a reader (`awayMaxHeight`), injected by the `mediaSourcesFor` binding as `readCookies` is, so the session ladder never carries it; the pure code reads no store. Allow transcoding off turns the server's `on` into `remuxOnly` before core's planner, so the plan holds no transcode, and a plan left with no way adds `TRANSCODING_OFF_HERE` to its problems; a server that only remuxes or converts nothing stays so. Prefer direct play decides the maybes: each play table names them by codec, in every container it plays (Apple's HEVC, for the `hev1` tag; Android TV's DTS and TrueHD), and `canPlayFor`'s `canPlaySurely` is `canPlay` over the table with them taken out (`surelyOf`). Preferred (the default), a maybe is tried as it is and a refusal steps down; not preferred, the plan starts at the remux, unless no other way is left, when the file is still tried as it is. A stream never meets a maybe (a remux re-tags HEVC `hvc1`, and its audio is copied or made E-AC-3), so `canStream` is unchanged. The web has no counterpart: its direct play is the server's `directPlay` and the browser's own `canPlayType`, so this stays in the app.
- **The away cap is a `quality`.** The server's HLS route takes no height, only one of core's `STREAM_QUALITIES` as `quality`, and only for a transcode (it answers 400 for a remux). So `mediaAccessFor` asks a transcode played from a `public` origin (the one `pickOrigin` picked: away from home) for the size at the cap's height with the fewest bits (`low1080` at 8 Mb/s, `low720` at 2 Mb/s), since the cap is there to save data away from home and must never ask for more than the server would spend by default (its `medium` quality aims at 8 Mb/s). It asks none at 4K, where the sizes stop at 1080p, none from a LAN or tailnet origin or the server's own address, and none for a remux or direct play. The server's own `maxHeight` still caps the frame (`capHeight`). A size also sets a bitrate: libx264 keeps its CRF under it as a ceiling, and VideoToolbox and VAAPI take it as their target. A height parameter on the server would cap the frame alone; that is the server's follow-up.
- **TV focus.** Settings opens with the remote on Sign out, once: anything on the page taking the focus spends it. Home's Settings plate, a `PlateButton` holding its view through `ref`, remembers itself as the opener (`useOpenerFocus`), so Back from Settings lands on it, on Android TV too.

## The allowlist and the end to end flows

- **The app calls only core's `APP_CLIENT_CALLS`** (`libs/raven/core/src/appClientCalls.ts`): the viewer reads, the spec's writes plus `unlockAdmin`, the ticket and the media plane, each as a method and a `:name` path template, through PR 9's screens. `apiFor` wraps its fetch in `allowlistedFetch` (`src/servers/allowlist.ts`), which throws before the request on any other method and path (`appClientCallOf` matches them; a dot segment never does), so the server never hears of it. `@raven/server`'s `appClients.test.ts` checks the list against the server's route marks: every entry is a real route, none is `@AdminOnly()`, and the only writes are the spec's. A screen that needs a new route adds it there first. Pictures, the event stream and the player's sources are fetched natively, not by the `ApiClient`, so `cookieHeadersFor` checks their URLs the same way and throws before it hands one its cookies, and `mediaAccessFor` checks a ticketed source's URL with `checkAppCall`; a source that cannot be built, the jar unreadable or a URL refused, is a refusal, so the player always hears back.
- **`e2e/` holds Maestro flows, against `@raven/server`'s `serve:fixture`** (a real accountless server on `http://127.0.0.1:8490` with a locked film library holding an MKV and an open series library holding an MKV episode and an MP4 one with an English sidecar, PIN `1357`, the test admin password). The build names it with `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN`. `signIn.yaml` goes through both unlocks (by the thumb on iOS, `steps/signIn.touch.yaml`, and by the remote on Android, `steps/signIn.dpad.yaml`, picked by Maestro's `when: platform`), `home.yaml` finds the locked film on Home, `library.yaml` opens each library from its shelf's See all, sorts the films by date added from the action sheet, and finds no file-size sort for the series, `item.yaml` opens the film's page, marks it watched and takes the mark off again (so the fixture is left as found), and goes from the series to its season and its episode, `play.yaml` plays the film from its page (its MKV through the HLS remux, on the cookie, since the fixture lists no media origin), pauses it, goes back and clears the saved spot with a mark and its undoing, and `search.yaml` searches every library from Home's header and opens the series it finds (the server's search leaves locked libraries out, the films' among them), finds nothing for a word no title holds, and searches the film library from its own box. A field is tapped as the element below its label, since Maestro picks the label's text first.
- **One folder, two inputs.** Maestro runs only the top of `e2e/`, so the sub-flows sit in `e2e/steps/`. A flow only the thumb can drive is tagged `touch` and one only the remote can drive `dpad`; `e2e` runs `--platform ios --exclude-tags dpad` and `e2e:android-tv` `--platform android --exclude-tags touch`, so `signIn.yaml` and `home.yaml` run on both and each run picks its own device even with the other booted. The PIN and admin password live once, in `signIn.yaml`'s `env`. The Android TV emulator reaches the computer's loopback as `10.0.2.2`, but `e2e:android-tv` first runs `adb reverse tcp:8490 tcp:8490`, so the bundled `127.0.0.1:8490` reaches the fixture there too and the fixture keeps listening on the loopback only.
- **The Android TV flow is `play.dpad.yaml`, driven only by the remote's keys** (`pressKey: Remote Dpad ...`, `Back`, `Remote Media Play Pause`) and checked by what has the focus (`focused: true`): sign in, the film focused on Home, its page with the focus on Play, Play, pause, right on the line skips ten seconds (the line's spoken value, `Position, 0:15 of 1:00`, is read with `copyTextFrom` and the spot ten seconds on worked out in `evalScript`, since the repo keeps no JavaScript file for `runScript`), Back to a page offering to resume from exactly that spot, Back to Home with the film under Continue watching and the focus on its card below the Films title, then Watched and back to clear the spot, so the fixture is left as found. A field is typed into as on the platform: the step opens with the remote on its field (the flow checks it, so it checks `useFocusOnMount` below), select opens the keyboard, then `inputText` inside a `retry` that clears it and checks what it shows (a secret by one dot a character) before Enter sends it as a key of its own (`steps/field.dpad.yaml`). A run stopped part way can leave the film under Continue watching, so `play.dpad.yaml` first clears the spot when Home shows that shelf (`steps/clearSpot.dpad.yaml`, which it also ends with), and `home.yaml` moves down to the series' shelf on a TV, where Continue watching can push it below the screen. The pause is the remote's play and pause key rather than select, since the controls fade five seconds after a press and a hierarchy read on the emulator can take longer than that, and while paused they stay. The film is sixty seconds long, so the flow keeps moving.
- **Maestro cannot drive tvOS.** Its XCTest driver (2.11.0) is built for iPhone and iPad only and refuses to install on an Apple TV simulator ("not built to support this device family"), so the flows run on the iPhone simulator. They need the development variant, for plain http to the loopback.
- **The Apple TV's flow is an XCUITest, `tvos-e2e/RemoteFlowTests.swift`,** driven by `XCUIRemote` and the platform's keyboard (`typeText`): sign in through both unlocks, select the film on Home, Play, twenty seconds of the remux, Menu to the page (now offering Resume), Menu to Home, where the film is under Continue watching and the focus is on its card below it, and Menu on Home sends raven to the background. It then marks the film watched and back, as `play.yaml` does, so the iPhone flows that follow in CI find the fixture as it was. It names the app by its bundle id and drives whatever build is installed, so it never builds the app.
- **`ios/` is generated, so a config plugin adds the test.** `plugins/withTvRemoteTests.ts` joins only a TV prebuild (`EXPO_TV`, read by `src/config/tvPrebuild.ts` as config-tv reads it): it copies `tvos-e2e/*.swift` into `ios/RavenRemoteTests/`, adds a tvOS UI test target of that name with no app target and no dependency on the app (so building it builds nothing else), and writes a shared `RavenRemoteTests` scheme. The `xcode` package ships no types, so the plugin guards the project down to the methods it calls. Each `prebuild:tvos` makes it afresh, and so does a prebuild without `--clean`, since Expo 58 writes the project file anew either way; the mod also returns early on a project that already has the target, copying only the Swift, so a mod run twice on one project adds no second. `prebuild:ios` leaves it out.
- **`e2e:tvos` runs it** (`xcodebuild test` on `ios/raven.xcodeproj`'s `RavenRemoteTests` scheme, with `DEVELOPER_DIR` as the other Apple scripts): after `APP_VARIANT=development EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN=http://127.0.0.1:8490 build:tvos`, install the build on the simulator named `Apple TV 4K (3rd generation)`, or the one `TVOS_SIMULATOR` names, and start `serve:fixture`. Its result bundle is in `build/tvos-e2e/Logs/Test`. It unlocks only when the app asks, so it also runs on a simulator already unlocked; a run stopped before its clean-up leaves the film under Continue watching, which a fresh `serve:fixture` clears. CI runs it after the tvOS build on a fresh `raven-tv` simulator, against the fixture server the iPhone flows then reuse, in place of the old launch check, and uploads the result bundle when a step fails.
- **Each `build:*` runs its `prebuild:*` first:** bun runs a script's `pre` script before it, so a build always regenerates its native project, and both build environment values reach it. The Nx inputs include `APP_VARIANT` and `EXPO_PUBLIC_RAVEN_BYPASS_ORIGIN`, so a cached production build cannot stand in for the fixture build. CI checks the pods after each Apple build, since `expo prebuild` exits 0 when `pod install` fails.

## TypeScript configs

- Two tsconfigs, and `typecheck` runs both. `tsconfig.json` checks the app (`src/`, `app/`, `index.ts`) with React Native's types only, so a Node or Bun global in screen code fails the typecheck. `tsconfig.node.json` checks what runs under Node or Bun: the three configs and the bun tests (`src/**/*.test.ts`), with Bun's types. The render tests stay in `tsconfig.json`, since they import their globals from `@jest/globals`.
- `app.config.ts`, `metro.config.ts` and `babel.config.ts` are the only configs; there is no JavaScript file. Expo loads `app.config.ts` and `metro.config.ts` with its own require hook, which transpiles them with `typescript`. Babel loads `babel.config.ts` through Node's own type stripping, so Metro and jest need Node 22.18 or newer.
- Expo's hook reads no tsconfig `paths`, and Node adds no `.ts`, so `app.config.ts` imports `./src/config/buildNumber.ts` and `./src/config/appVariant.ts` by relative path and extension. That one file is exempt from the `@/` rule in `.oxlintrc.json`.
- `version` comes from `package.json`, which `scripts/bump_version.sh` bumps with the rest. `ios.buildNumber` and `android.versionCode` come from `GITHUB_RUN_NUMBER`, and are `1` on a local build.

## Toolchain

- **watchman.** Without it Metro serves stale bundles after a change. `start` checks for it first and stops when it is missing: `brew install watchman`.
- **Xcode and CocoaPods.** `xcode-select` on this Mac points at the Command Line Tools, so the Apple scripts use `DEVELOPER_DIR` when the environment sets it (CI picks its Xcode that way) and `/Applications/Xcode.app/Contents/Developer` when it does not. Prebuild runs `pod install`: `brew install cocoapods`.
- **Android.** The SDK is in `~/Library/Android/sdk` (`ANDROID_HOME`), the TV emulator is the AVD `raven_tv`, and Gradle runs on Android Studio's bundled JDK (`JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`).
- `prebuild:tvos` and `prebuild:ios` write the same `ios/` folder; each Apple build runs its own prebuild first, so it never builds the other platform's project.
- **Maestro** for `e2e` and `e2e:android-tv`: `brew tap mobile-dev-inc/tap`, then `brew install mobile-dev-inc/tap/maestro` (2.11.0, on Homebrew's OpenJDK). The formula installs only its newest release, so CI's iPhone and Android TV jobs download that release's zip by version and checksum instead, and start the fixture server in a step of their own. `e2e` points Maestro at Xcode through `DEVELOPER_DIR` like the other Apple scripts; without it, Maestro finds no simulator. `e2e:android-tv` needs the emulator running (`emulator -avd raven_tv`) with the development-variant APK installed, and finds `adb` under `ANDROID_HOME`, which it requires (`~/Library/Android/sdk` on this Mac, the runner's own in CI).
- **CI's Android TV run** is `📺 App on Android TV` on `ubuntu-24.04`: KVM through a udev rule, an `android-tv` API 36 x86_64 AVD on the `tv_1080p` profile (960 by 540 dp, as the local `raven_tv` AVD that `ci:app:android-tv` makes; an older one made on `tv_4k` is reused as it is) made and booted once by `reactivecircus/android-emulator-runner` on a pinned emulator build and kept with its snapshot in the Actions cache, under a key naming the system image's revision, the emulator build, the cores, the RAM and the options (a snapshot from anything else cold boots), the fixture server in the background, then the APK installed and `app:e2e:android-tv` run inside the runner's emulator step. CI builds the APK for x86_64 alone (`ORG_GRADLE_PROJECT_reactNativeArchitectures`, an Nx input of `build:android-tv`), so its artifact runs on an emulator, not a TV.
- **CI's app caches are saved on main only.** `app-caches.yml` builds the three platforms on main (when the lockfile or the native config changes, weekly, and by hand) and saves ccache's objects, CocoaPods' and Gradle's downloads, Gradle's build cache, Homebrew's and apt's packages and the AVD; the PR's app jobs restore them and save nothing, since a PR's caches are its alone. Both set up through the same actions, `.github/actions/raven-app-setup` (Bun, Node, the caches, ffmpeg, ccache, the build environment, the install and the libraries) and `raven-android-avd` (the emulator's settings, KVM and the AVD), so the two never build differently. The Apple builds compile through ccache (`USE_CCACHE=1`, which Expo's Podfile reads), and Android's CMake uses it whenever it is installed.
