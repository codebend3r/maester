# Claude context for raven's device app

`@raven/app` is raven on iPhone, iPad, Apple TV and Android TV. The rules that apply to it are in the root `CLAUDE.md` and in `apps/raven/CLAUDE.md` ("App"); this file holds what only the app needs.

## Pins

- **`react-native` is `npm:react-native-tvos@0.88.0-0`.** The fork has no separate stable 0.88 tag: `0.88.0-0` is its stable release (npm's `latest` and `0.88-stable` tags point at it), the `-0` suffix is how the fork names every release, and its release candidates are `-0rcN`. Its peer is `react ^19.3.0`, so the app's React is the repo's `19.3.0`.
- **Expo is `58.0.14`, the version the spike ran.** Every other Expo package, and React Native's own (`react-native-screens`, `react-native-safe-area-context`), is pinned to the version Expo 58.0.14's `bundledNativeModules.json` names. A bump moves them together: take the new Expo's list, never `expo install`'s ranges.
- **The root `package.json` overrides `react-native` to the fork for the whole workspace.** `react-native-reanimated`, `react-native-worklets` and `react-native-gesture-handler` arrive because bun installs the required peers of `expo-router`'s drawer (`react-native-drawer-layout`), and the first two take `react-native` `0.86 - 0.88`, a range that excludes a prerelease such as `0.88.0-0`. Without the override bun installs upstream React Native beside the fork. The override also pins gesture-handler to Expo 58.0.14's `3.3.0`, where the peer would otherwise float to the newest.
- **The app uses neither the drawer nor the JS stack**, so `expo.autolinking.exclude` in `package.json` keeps those three out of the native projects. They stay installed, since bun installs a package's required peers and the root has no way to skip one.

## Bun's package store

Bun links the workspace in isolated mode: each package sits in `node_modules/.bun/<name>@<version>/node_modules/<name>` and sees only what it declares. Two things in the store require `react-native` without declaring it, and find nothing there, because the fork's folder is named `react-native-tvos`:

- React Native's jest preset, loaded by jest-expo.
- The fork's own podspecs, which `require.resolve('react-native')` from inside the store during `pod install`.

So `test:screens` and the Apple prebuilds set `NODE_PATH=$PWD/node_modules`, the app's own `node_modules`, where `react-native` links to the fork. It is absolute because `pod install` runs in `ios/`.

The jest config in `package.json` also lets Babel through `node_modules/.bun`, as jest-expo's default lets pnpm's `.pnpm` through. Babel's output imports `@babel/runtime` from the app's own files, so the app depends on it directly.

## Intl and the shared layer

- **What Hermes has.** On the Apple TV simulator and the Android TV emulator, RN 0.88's Hermes has `Intl.getCanonicalLocales`, `NumberFormat`, `DateTimeFormat` and `Collator`, and they handle every option core passes. It has no `Locale`, `PluralRules`, `RelativeTimeFormat` or `DisplayNames`. So `src/polyfills.ts` loads formatjs's `getcanonicallocales`, `locale`, `pluralrules`, `relativetimeformat` and `displaynames` with their `en` data, in that order, and no `numberformat` or `datetimeformat`.
- **Hermes has no `Array.prototype.toSorted`** (it has `toReversed`, `toSpliced` and `with`), and core sorts with it, so `src/polyfills.ts` also installs `installToSorted` (`src/arrayToSorted.ts`) where the engine lacks it. Opening a grouped library crashed the Release build without it; jest runs on Node, which has it, so only a build on a simulator shows such a gap.
- **`polyfill.js`, not `polyfill-force.js`.** Each entry installs itself only when the engine lacks the constructor or its English data, so a Hermes that gains one keeps its own, and nothing is applied twice.
- **The `.js` subpaths.** formatjs's package `exports` list each polyfill and locale file only with its `.js`. Without it Metro warns and falls back to the files, so `src/polyfills.ts` is exempt from the no-extension import rule in `.oxlintrc.json`.
- **Metro reads `@raven/core` and `@raven/ui` through Bun's workspace links** to their built `dist`, so `start`, `test:screens` and the `build:*` targets depend on `^build`, which builds both first. Both are ES modules and `@raven/ui`'s peers resolve from its own `node_modules`, which link to the same store folders as the app's, so there is one React.

## Servers and sessions

- **The app holds each server's cookies, never the system.** Every call goes through `apiFor(server)` (`src/servers/serverClient.ts`), whose fetch (`serverFetch.ts`) sends `credentials: 'omit'`. On iOS and tvOS that turns off `HTTPShouldHandleCookies`, and on Android OkHttp gets no cookie jar, so the shared store neither keeps nor sends anything. The app adds both of core's `SERVER_COOKIES` (`raven_unlock`, then `raven_admin`) from its own jar and applies what `set-cookie` says back, both only for the server's own `/api/`, the cookies' path: a media origin never gets them, and a response a redirect took elsewhere (its `url`) sets nothing. React Native follows redirects natively with the headers it was given and has no `redirect: 'manual'`, so the request itself cannot be held back; raven's API never redirects.
- **Sign-in asks what the desktop asks.** The address, then the PIN when `getLock` says the server has one, then, after a PIN, the admin password when `getAdminLock` says the admin lock holds and can be turned off: while it holds, the PIN opens nothing and locked libraries stay hidden. Each step has Not now. The app calls `unlock` and `unlockAdmin` (both `@ForViewers()`) and never an `@AdminOnly()` route.
- **`set-cookie` arrives folded.** React Native hands several `Set-Cookie` headers over as one value joined with `, `, and an `Expires` date holds a comma too, so `readServerCookies` splits only at a comma followed by `name=`. A cookie with an empty value or `Max-Age=0` is cleared and leaves the jar; the last word on each one wins.
- **Everything that must last is in `expo-secure-store`.** Each server's cookies are one JSON value under `raven.cookie.<serverId>`; the server list and the active id are one JSON value under `raven.servers` (`src/servers/activeServerStore.ts`). Both are guarded when read. The keychain on Apple keeps them on tvOS too, where AsyncStorage's caches folder may be emptied, and the keystore keeps them on Android. Only the player prefs are in AsyncStorage. `AppRoot` loads both stores before any route renders.
- **A failing keychain degrades, never fails.** A store call that throws reads as empty and saves nothing, so the app works for the run and forgets on relaunch.
- **Simulator builds are signed ad hoc.** The keychain refuses an app with no signature ("A required entitlement is not present"), so `build:ios` and `build:tvos` pass `CODE_SIGN_IDENTITY=-` rather than turning signing off.
- **Server ids** are `expo-crypto`'s `randomUUID`; `serverList.ts` checks the shape, since the id names the secure-store key. The list keeps at most core's `SERVERS_CAP`, the desktop's cap, and a new server starts with core's `serverNameFor` as its name.
- **The jar's changes take turns per server.** Two responses that set cookies at once each read what the one before left, so neither writes over the other.
- **Plain http is for the development variant.** `APP_VARIANT=development` at prebuild sets `NSAllowsLocalNetworking` and Android's `usesCleartextTraffic`. Expo's template allows local networking in every build, so `app.config.ts` writes the whole `NSAppTransportSecurity` dictionary, which a release build keeps strict. Debug builds against Metro need the development variant too.
- **A form's buttons take a tone,** the web's `Button` tones: `primary` for the one action a step is for, `quiet` (a moss fill) for another way on, `ghost` (no fill) for a way out. Focus turns any button's edge to the text colour, drawn twice as thick on a TV (`SIZES.tvFocusRing`). Every control has the web's `--radius-md`; tvOS draws a focused text field as its own pill-shaped plate, so the TV field clips it to that radius.
- **Menu on tvOS's keyboard cancels the edit.** The native field goes back to what it held, but React Native reported every key as it was typed and reports nothing on the cancel, so the TV field takes the text it ends editing with (`onEndEditing`) as the field's value: what it shows is what Continue sends.
- **React Native prop values are written inline** (`behavior="padding"`, `returnKeyType="go"`): each prop's own union type checks them, as an `as const` object would.

## Queries, pictures and events

- **One query client for the app's life, emptied on a server switch.** `AppRoot` wraps the routes in `QueryClientProvider` with headless `createQueryClient()`, and `clearOnServerSwitch` (`src/queries/serverCache.ts`) calls `clear()` from inside zustand's `set` whenever the active id changes, before React renders again. Every server answers under the same keys, so this is what keeps one server's answers off another's screen. A client keyed per server would remount the navigator on the activation in the middle of sign-in. TanStack binds each `useQuery` observer to the client it first saw, so a screen that reads a server reads it through `useAppQueries()`, which re-renders it on a switch and builds fresh queries; Home also keys its body on the server id.
- **`useAppQueries()`** (`src/queries/useAppQueries.ts`) gives the active server's `api`, `ravenQueriesFor(api)` and `useServerEvents`, made once per server (`lastPerServer`). The folder is `queries/`, not `data/`: the root `.gitignore` ignores every `data/`, raven's `DATA_DIR`.
- **A 423 opens `/unlock`.** `createQueryClient` raises the headless unlock prompt on a refusal for a locked library; `useUnlockRoute` closes it and pushes the PIN screen, which calls `unlock`, invalidates every query and goes back.
- **Pictures are React Native's `Image` with the server's cookies.** Posters, backdrops and thumbnails are on the API (`PrivateBy`, not the media plane), so a locked library's need the cookie, and `cookieHeadersFor` adds it for the server's own `/api/` only. `expo-image` would add a native module for caching the versioned URLs do not need yet.
- **The jar says when it changes.** Every write or forget bumps `useCookieVersion` (`src/stores/cookieVersion.ts`), and `useServerCookies` reads the jar again on each bump, so pictures carry a new unlock cookie at once. A card remembers which picture and headers failed, so new headers ask again.
- **Server events ride `react-native-sse`**, adapted to headless `ServerEventSource` by `eventSourceFor` (`src/servers/eventSource.ts`). It opens once the jar has read the cookies and passes them as headers. The library retries only an error status, never a refused or reset connection, so the adapter reopens after every `error` itself (1 s, doubling to 30 s, back to 1 s only once a connection has held for 5 s, so a proxy that accepts and resets each one is not asked every second), closes in the background and opens again on return (telling headless it dropped, so it reads everything again), and keeps the stream through `inactive` (Control Center, a call), which is not the background, and never holds two connections or any after `close`. The library's XHR keeps React Native's default `withCredentials = true`, so the system jar is consulted for the stream; it stays empty, since every other request omits credentials and `/api/events` sets no cookie. `AppRoot` mounts the stream once per active server.
- **A library's sort, view and grouping are this device's.** The web saves a viewer's change to the server (`PUT /api/libraries/:id/view`, `@ForViewers()`) for everyone, but that write is not one of the spec's, so `APP_CLIENT_CALLS` leaves it out. `useLibraryViews` (`src/stores/libraryViews.ts`) keeps a choice per server and library in AsyncStorage, guarded when read; the screen lays it over the server's settings and passes both through core's `coherentSettings`, so a choice the library's type cannot show gives way to its own.
- **Pickers are the platform's.** Touch screens (only iPhones and iPads) use `ActionSheetIOS`, a popover anchored on the chip on an iPad; tvOS has none (React Native builds `RCTActionSheetManager` out of it), so TVs use a `Modal` list with focus on the current option, closed by Menu or Back.
- **A list on a TV needs a height of its own.** The fork wraps a `FlatList`'s ScrollView in a `TVFocusGuideView` that takes no style, so `flex: 1` never reaches it and the list draws 1 pt tall. `Grid.focus` measures the room under its header and draws the list only once it has it, which also lets the first card mount asking for the focus and take it.
- **Moving the remote's focus on purpose.** `hasTVPreferredFocus` on a view that mounts asks before the view is in the window, and the fork's retry for that takes only the first time, so a card a jump lands on calls `requestTVFocus()` once mounted (`src/layouts/tvFocus.ts`, a guard, since the fork adds the method outside React Native's types). It does so once per jump: `useJumpFocus` asks only for a jump count newer than the grid's handled one, so the card never pulls the focus back as it mounts again (scrolled back to, its bucket reopened, a new sort). Preferred focus is for the opening only, until anything on the screen has had the focus (a card, or a control in the header, whose focus bubbles up to it), so a card drawn later, after a sort or once a search finds some, leaves the viewer where they are.
- **The touch jump strip fits its slot.** Each mark gets the web's share (a 27th of the room, at most 40rem over 27) and never less than a finger can press; where they cannot all fit, as on a phone held sideways, neighbouring marks are gathered into one (`src/layouts/jumpMarks.ts`). Rows, bucket headings, captions and the strip's marks grow with the viewer's text size (`linesHeightOf`), and the grid and strip keep clear of the side insets.
- **A card goes where the web's would.** Each card carries a `RouteTarget` (`src/routes.ts`), read off core's `cardDestination`: a matched video's item page, naming its library and, for a card a movie was split onto, its file (`/item/[id]?library=&file=`, the web's `?library=` and `?file=`), or the player for a file with no page; a show's page names neither. The item page keeps to that library's files and card through core's `libraryFiles`. `/play/[mediaId]` says the player is still to come until PR 6 brings it.
- **Item pages mark through the headless hooks that take the client.** The app holds several servers, so it calls `useServerMediaMutations`, `useServerWatchedToggle` and `useServerItemFavourite` with the active one's `api`; a hook picked off the session object at render is not one the hooks rule accepts. A movie's or an episode's Watched and Favourite show at once (their edits patch the item's page); a show's or season's Watched waits for the server, as on the web. On a TV the page's first action, Play or Resume, takes the remote's focus as it opens and lets go once anything on the page has had it, so a button that changes after a mark leaves the viewer where they are. While a show's next episode is read (`isPlayPending`), a TV draws no action and no row, so Play is there from the first and nothing else is on screen for tvOS to give the opening focus to; under the thumb the marks are drawn at once and Play once it is known, as on the web. The TV's cast tiles take the focus only so the row scrolls; they stay inert until the app has a person page.
- **Every search box is headless `useSearch`'s**, as the web's are: it asks once typing pauses for core's `SEARCH_DELAY_MS` or at once when the keyboard sends it, never on each key, and a cleared box asks nothing (headless's `homeSearchQuery('')` is a `skipToken`). The layouts' `SearchField` draws it: under the thumb with the keyboard's Search key and a clear button, `/search` opening with the keyboard up on its field, on a TV as a field the remote selects to open the platform's keyboard, taking the text it ends editing with as sign-in's field does. `/search` searches every library through `homeSearchQuery` and lays out what it finds as Home's library shelves (`libraryShelvesOf`, over core's `withLibraries`), whose See all opens the library on the search (`?q=`, as the web's link does). A library's own box is the web's: the server searches (`listMedia` and `listShows` take it as `q`), so no call joins `APP_CLIENT_CALLS`. On a TV the search screen opens with the remote on its field, once, and Home draws its Search entry only with its shelves, so the first card keeps the opening focus. "Nothing matches" waits for the server's answer to this search: while it is read, the last search's answer stands in (`keepPreviousData`) and says nothing of this one.
- **Motion follows the system.** `followReduceMotion` keeps `useReduceMotion` in step with `AccessibilityInfo`; a focused TV card grows to 1.08 over 150 ms only when motion is allowed, and at once otherwise.

## Playing

- **What a platform plays is a table.** React Native has no `canPlayType`, so `canPlayFor(platform)` (`src/platform/canPlay.ts`) answers core's `planPlayback` from the platform's table, matched against core's own MIME and codec strings. `platformOf` (`src/platform/platform.ts`) takes `Platform.OS` and `Platform.isTV` as arguments, so both run under bun. Apple's table is MP4 or MOV, H.264 or HEVC, and the audio in core's `HLS_COPY_AUDIO`. HEVC in MP4 counts as a yes though a file tagged `hev1` refuses, since the index keeps no tag: the ladder steps down to the remux, which re-tags it `hvc1`. Android TV answers as Apple does until it has a table of its own.
- **`canStream` answers for the HLS route.** The planner asks it about `streamMimeType`'s fragmented MP4. The app plays a remux or a transcode through HLS, never Media Source Extensions, and HLS audio is copied or made E-AC-3, so `canStream` is `canPlay`: a stream plays where its video plays in MP4.

## The allowlist and the end to end flows

- **The app calls only core's `APP_CLIENT_CALLS`** (`libs/raven/core/src/appClientCalls.ts`): the viewer reads, the spec's writes plus `unlockAdmin`, the ticket and the media plane, each as a method and a `:name` path template, through PR 9's screens. `apiFor` wraps its fetch in `allowlistedFetch` (`src/servers/allowlist.ts`), which throws before the request on any other method and path (`appClientCallOf` matches them; a dot segment never does), so the server never hears of it. `@raven/server`'s `appClients.test.ts` checks the list against the server's route marks: every entry is a real route, none is `@AdminOnly()`, and the only writes are the spec's. A screen that needs a new route adds it there first. Pictures and the event stream are fetched natively, not by the `ApiClient`, so `cookieHeadersFor` checks their URLs the same way and throws before it hands one its cookies; the native players' URLs (PR 6) should get their headers the same way.
- **`e2e/` holds Maestro flows, against `@raven/server`'s `serve:fixture`** (a real server on `http://127.0.0.1:8490` with a locked film library and an open series library, PIN `1357`, the test admin password). `signIn.yaml` signs in through both unlocks, `home.yaml` finds the locked film on Home, `library.yaml` opens each library from its shelf's See all, sorts the films by date added from the action sheet, and finds no file-size sort for the series, `item.yaml` opens the film's page, marks it watched and takes the mark off again (so the fixture is left as found), tries Play, and goes from the series to its season and its episode, and `search.yaml` searches every library from Home's header and opens the series it finds (the server's search leaves locked libraries out, the films' among them), finds nothing for a word no title holds, and searches the film library from its own box. A field is tapped as the element below its label, since Maestro picks the label's text first.
- **Maestro cannot drive tvOS.** Its XCTest driver (2.11.0) is built for iPhone and iPad only and refuses to install on an Apple TV simulator ("not built to support this device family"), so the flows run on the iPhone simulator, and CI checks the Apple TV build by launching it and finding it still running. They need the development variant, for plain http to the loopback.
- **Each `build:*` runs its `prebuild:*` first:** bun runs a script's `pre` script before it, so a build always regenerates its native project, and `APP_VARIANT` reaches both. CI checks the pods after each Apple build, since `expo prebuild` exits 0 when `pod install` fails.

## TypeScript configs

- Two tsconfigs, and `typecheck` runs both. `tsconfig.json` checks the app (`src/`, `app/`, `index.ts`) with React Native's types only, so a Node or Bun global in screen code fails the typecheck. `tsconfig.node.json` checks what runs under Node or Bun: the three configs and the bun tests (`src/**/*.test.ts`), with Bun's types. The render tests stay in `tsconfig.json`, since they import their globals from `@jest/globals`.
- `app.config.ts`, `metro.config.ts` and `babel.config.ts` are the only configs; there is no JavaScript file. Expo loads `app.config.ts` and `metro.config.ts` with its own require hook, which transpiles them with `typescript`. Babel loads `babel.config.ts` through Node's own type stripping, so Metro and jest need Node 22.18 or newer.
- Expo's hook reads no tsconfig `paths`, and Node adds no `.ts`, so `app.config.ts` imports `./src/config/buildNumber.ts` and `./src/config/appVariant.ts` by relative path and extension. That one file is exempt from the `@/` rule in `.oxlintrc.json`.
- `version` comes from `package.json`, which `scripts/bump_version.sh` bumps with the rest. `ios.buildNumber` and `android.versionCode` come from `GITHUB_RUN_NUMBER`, and are `1` on a local build.

## Toolchain

- **watchman.** Without it Metro serves stale bundles after a change. `start` checks for it first and stops when it is missing: `brew install watchman`.
- **Xcode and CocoaPods.** `xcode-select` on this Mac points at the Command Line Tools, so the Apple scripts use `DEVELOPER_DIR` when the environment sets it (CI picks its Xcode that way) and `/Applications/Xcode.app/Contents/Developer` when it does not. Prebuild runs `pod install`: `brew install cocoapods`.
- **Android.** The SDK is in `~/Library/Android/sdk` (`ANDROID_HOME`), the TV emulator is the AVD `raven_tv`, and Gradle runs on Android Studio's bundled JDK (`JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"`).
- `prebuild:tvos` and `prebuild:ios` write the same `ios/` folder; each Apple build runs its own prebuild first, so it never builds the other platform's project.
- **Maestro** for `e2e`: `brew tap mobile-dev-inc/tap`, then `brew install mobile-dev-inc/tap/maestro` (2.11.0, on Homebrew's OpenJDK). The formula installs only its newest release, so CI downloads that release's zip by version and checksum instead. `e2e` points Maestro at Xcode through `DEVELOPER_DIR` like the other Apple scripts; without it, Maestro finds no simulator.
