# @raven/audio

raven's music player for iPhones, iPads and Android phones, behind the contract in `src/index.ts`: `AVQueuePlayer` on iOS, with Now Playing and the remote commands through MediaPlayer.framework, and Media3's ExoPlayer on Android, with a `MediaLibrarySession` for the notification and the media buttons. The queue lives in the app's shared store; the native player holds a window of two tracks, the playing one and the next, so a track starts gaplessly in the background, and tells the app when it moved on.

The TVs play music through `react-native-video` and never call this module. The pod still builds for tvOS, since the app's tvOS target autolinks every Apple module, and the native side does nothing until the first `setWindow`. `@raven/app`'s Android autolinking excludes it (`expo.autolinking.android.exclude`), so the Android TV APK holds no media service of this module's.

`setWindow` opens the playing item at `start` seconds (an audiobook's saved spot, 0 for music): the seek waits until the item is ready to play, as AVFoundation requires of a seek with a completion handler, and the state events and Now Playing report that spot until it lands. `setRate` sets how fast every item plays (an audiobook's speed; 1 for music), kept across items and windows, with `MPNowPlayingInfoPropertyPlaybackRate` and the default rate on Now Playing; each item keeps a voice's pitch (`timeDomain`).

The cover the lock screen shows is fetched with no headers, so a library unlocked by the cookie fallback shows none there. The car's covers carry the answer's headers (below).

## Android

- **The player lives in a service.** `RavenAudioService`, a `MediaLibraryService` declared in `android/src/main/AndroidManifest.xml` (`foregroundServiceType="mediaPlayback"`), owns the one ExoPlayer and the session, so music plays on in the background. The module binds it with a `MediaController` on the first `setWindow` and drives the player directly, in the same process. Until the service is up, `ServiceGate` holds every call and runs them in order, and each call's promise settles only once it took effect, as on iOS; a call before any window has nothing to act on. When the service goes away, the next `setWindow` binds it again.
- **The window is `AudioWindow`.** It is plain Kotlin, tested on the JVM (`AudioWindowTest`, and `ServiceGateTest` for the calls held while the service starts): it holds the playing item and the next, drops a finished item as the player moves on, sends `advanced` on a transition the player made by itself, and `ended`, with a pause, after the last item. `setWindow` opens the first item at `start` through ExoPlayer's own start position.
- **Each item has its own headers.** Every item gets its own `DefaultHttpDataSource.Factory().setDefaultRequestProperties(headers)`, since items carry different tickets, under a `DefaultDataSource`, which also opens a `file://` track. The title, artist, album, cover and the server's duration go to the session through `MediaMetadata`.
- **The session forwards every command.** The notification's and the media buttons' play, pause, next, previous, seek and stop reach JS as `remote` events, through a `ForwardingSimpleBasePlayer` that does not apply them, since the queue lives in JS. Audio focus and headphones coming out are ExoPlayer's, and their pause reaches JS through `state`.
- **Android Auto browses the service.** `RavenAudioService`'s `onGetChildren` asks `BrowseBridge` (below) for a parent's children and lists them as `MediaItem`s, a node that is not playable as a folder; `onGetItem` names the root or one of the last 1,000 nodes the car was shown. Only the app itself, Android Auto, the system UI and Google's assistant may browse (`canBrowse` in `BrowseCallers.kt`): any other app that binds the service may drive playback but lists nothing and makes JS fetch nothing.
- **A chosen node plays through JS.** It arrives as a `MediaItem` with only its id, so `onAddMediaItems` sends `playFromBrowse` and hands the items back, and `RemotePlayer` takes no queue from a controller: JS fills its queue and opens the window as it would for any play. Auto follows the choice with Play, which would resume the old queue before JS has the new one, so the one Play within 5 s of a choice is swallowed (`PlayAfterBrowse`).
- **Covers go through `RavenArtworkProvider`,** as `content://` addresses, the kind Auto loads, each keyed by a hash of its address. A downloaded `file://` cover is read from disk; a server's is fetched once with the answer's headers into the cache folder, on the provider's own thread, so no list waits on a cover. Each fetch writes a temporary file of its own and moves it into place. The folder keeps at most 200 covers and 50 MB, the least recently read going first.
- **Media3 is pinned to 1.8.0**, `react-native-video` 6.19.3's (`RNVideo_media3Version`), so the workspace builds against one Media3; a bump of either moves both.
- **Tests:** in a prebuilt Wren (`bunx nx run @raven/music:prebuild:android`), `./gradlew :raven-audio:testDebugUnitTest` from `apps/raven/music/android`. `BrowseCacheTest` covers the bridge on the JVM, with the real `org.json` (a test dependency, since Android's is a stub there).

## CarPlay and Android Auto

Both cars read one browse tree, which the app's JS builds (ruling 10 of the plan; `@raven/native`'s `browseTree.ts`), over one bridge:

- **Native asks, JS answers.** A car's request for a parent's children becomes an `onAudioEvent` of type `browse` (`{ requestId, parentId }`), and JS replies with `audioPlayer.answerBrowse({ requestId, nodes, artworkHeaders })`: the `BrowseNode`s, and the headers (the server's cookies, the account's token) native sends with each of the answer's http covers. A chosen playable node becomes `{ type: 'playFromBrowse', id }`, which JS plays with `playTracks`. An app that passes `useNativeAudioHost` no `car` answers nothing. The contract is also importable as `@raven/audio/contract`, which loads no native module, so bun's tests can read it.
- **Another account's lists go.** `audioPlayer.clearBrowseCache()` forgets every kept list (and on Android the nodes shown); Wren calls it when another account's sign-in removes the downloads.
- **Three seconds, then the cache.** The bridge (`BrowseBridge.kt` on Android, `RavenBrowse.swift` on iOS, the same rules on both) keeps each parent's last answer as JSON, in `SharedPreferences` or `UserDefaults`, without its headers. When JS has not answered within 3 s (the app not yet running, as when the car starts it), or no module is alive to ask, the car gets that answer, and with none one node, "Open Wren on your phone", whose copy lives natively since JS cannot be asked. An answer that comes late is kept and announced (`notifyChildrenChanged` on Android; CarPlay reloads that list), so the car shows it next.
- **CarPlay is `RavenCarPlay.swift`,** a `CPTemplateApplicationSceneDelegate` built for iOS alone (the pod still builds for tvOS, which has no CarPlay, and `CarPlay` is an iOS-only framework in the podspec). It shows a `CPTabBarTemplate` with a `CPListTemplate` per folder the root lists (Albums, Playlists, Downloads), each filled through the bridge. A playable node plays and pushes `CPNowPlayingTemplate.shared`, which reads the Now Playing info and remote commands the module already sets; a folder opens as a list of its own. Each list shows at once, and each cover arrives on its own: a `file://` one from disk, a server's with the answer's headers. Now Playing is pushed only when a module is alive to play the choice. The scene is declared by Wren's `withCarPlay` plugin, as `RavenAudio.RavenCarPlay`, only in a build with `WREN_CARPLAY=1`, so the device app, and Wren by default, never make one; the Swift builds either way.

The native code builds only inside an Expo prebuild of `@raven/app` or `@raven/music`, which autolinks this package by its `expo-module.config.json`.
